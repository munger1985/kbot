# 步骤 1 详细设计：表基础约定与根聚合

## 已冻结的隔离与关联原则

Domain 是 KC 的顶层租户与强制隔离边界，Collection 与 Domain 为一对多：每个 Collection 只属于一个 Domain，任何 KC 入库、Discovery、Evidence、任务和删除操作都不能跨 Domain。

Agent–Collection Binding 是同一 Domain 内的多对多关系；它不改变 Domain–Collection 的一对多关系。一个 Agent 如需在未来获得跨 Domain 能力，应由上层 Agent 组合多个 Domain 作用域内的 Agent/结果实现；KC 不接受跨 Domain `collection_ids`，不合并跨 Domain Evidence，也不建立跨 Domain Relation。

KC 的数据几乎全部由后台服务写入，APEX 仅做受限读取。因此不采用高成本的 Scope 复合外键。`app_id`、`domain_id` 只存在于 Collection；下游写命令由 KC Application Service 解析目标 Collection 并写入 `collection_id`。所有读查询先解析 Domain 内允许的 Collection，再以 `collection_id` 过滤。增加一致性巡检任务，检查下游行的 `collection_id` 指向不存在父对象等异常，并告警/隔离异常数据。

## 所有 KC 表的基础列

| 字段类别 | 约定 |
| --- | --- |
| 主键 | `NUMBER(38) GENERATED BY DEFAULT ON NULL AS IDENTITY` |
| Scope | 仅 Collection 保存非空 `app_id NUMBER(38)`、`domain_id NUMBER(38)`；下游表保存非空 `collection_id NUMBER(38)` |
| 时间 | `created_at/updated_at TIMESTAMP(6) WITH TIME ZONE`，默认 `SYSTIMESTAMP` |
| 审计 | `created_by/updated_by VARCHAR2(256)`；服务身份使用稳定前缀，如 `svc:knowledge-core` |
| 并发 | 可变聚合根使用 `row_version NUMBER(19) DEFAULT 1 NOT NULL` 做乐观锁 |
| JSON | `CLOB` + `IS JSON` 约束，匹配现有 `OracleJSON` ORM 兼容层 |
| 状态 | `VARCHAR2` 枚举与 `CHECK` 约束，不复用 V1 数值状态码 |

内部关联使用 ID 列与必要的普通索引，而非全量外键。删除、版本切换和任务结果只能通过 KC 服务完成；数据库巡检与应用测试共同防止孤儿数据。

## `KBOT_KC_COLLECTION`

| 字段 | 类型/规则 | 说明 |
| --- | --- | --- |
| `collection_id` | `NUMBER(38)` PK identity | 内部稳定标识 |
| `app_id`, `domain_id` | 非空 `NUMBER(38)` | APEX 物理过滤与 Domain Scope |
| `collection_key` | `VARCHAR2(64)` 非空、不可变 | API 路由与 Portal 配置键 |
| `display_name` | `VARCHAR2(256)` 非空 | APEX 展示名称 |
| `description` | `VARCHAR2(1000)` 可空 | 管理说明 |
| `status` | `VARCHAR2(24)` 非空 | `ACTIVE/DISABLED/DELETING/DELETION_FAILED` |
| `default_security_level` | `NUMBER(3)` 非空 | Bundle/Document 默认值，具体内容可收紧不可放宽 |
| `metadata_json` | JSON CLOB 可空 | 低频扩展字段 |
| `row_version` + 审计列 | 基础约定 | 管理面乐观锁与审计 |

约束与索引：`UK(app_id, domain_id, collection_key)`；`CHECK status`；B-tree 索引 `(app_id, domain_id, status, display_name)` 供 APEX 列表与 Scope 查询。`collection_key` 不支持重命名；Collection 删除按既定 `COLLECTION_PURGE` 流程物理清除。

## `KBOT_KC_COLLECTION_BINDING`

| 字段 | 类型/规则 | 说明 |
| --- | --- | --- |
| `binding_id` | `NUMBER(38)` PK identity | Binding 标识 |
| `collection_id` | 非空 `NUMBER(38)` | 通过 Collection 自动关联 App/Domain Scope |
| `consumer_type` | `VARCHAR2(32)` 非空 | 首期仅 `AGENT`，预留其他消费者 |
| `consumer_id` | `VARCHAR2(128)` 非空 | 使用字符串兼容数字 Agent ID 与未来消费者 |
| `status` | `VARCHAR2(16)` 非空 | `ACTIVE/REVOKED` |
| `note` | `VARCHAR2(1000)` 可空 | 管理备注，不参与检索 |
| 审计列 | 基础约定 | 不需要 `row_version` |

约束与索引：`UK(consumer_type, consumer_id, collection_id)`；`CHECK consumer_type/status`；索引 `(consumer_type, consumer_id, status)` 供 Skill 读取 Agent 允许范围；索引 `(collection_id, status)` 供删除保护检查。Binding 不存权重、Primary、Top-K 或 rerank 参数；所有 ACTIVE Collection 平权。

## 读写不变量

- 创建 Collection 时，`app_id` 仅从 `base.toml` 注入；Domain 从认证 Scope 校验。
- 创建/更新 Bundle 等下游对象时，只写目标 `collection_id`；App/Domain Scope 由该 Collection 自动关联，不能由请求体覆盖。
- Agent Binding 必须在同一 Domain 内；DISABLED Collection 保留 Binding 但 Skill 自动跳过。
- APEX 直连读取通过 Collection join 使用 `app_id + domain_id` 条件，或使用封装该 join 的 `KBOT_KC_V_*` 视图；禁止直写 KC 表。
