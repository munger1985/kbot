# 步骤 1 实施细化：KC Schema 迁移计划

## 原则

KC 与 V1 共用 Oracle Schema，但使用完全独立的 `KBOT_KC_*` 表、索引和视图。迁移只新增对象；在 V2 稳定验收前不修改、不删除 V1 表。所有 DDL 通过版本化迁移脚本执行，应用启动只检查 Schema 版本，不自动建表或删表。

下游表只保存 `collection_id`，不重复 `app_id/domain_id`，也不建立高成本 Scope 复合外键。KC Application Service 负责 Scope 对齐，一致性巡检负责发现孤儿/错 Scope 行。

## 建表顺序

```text
1. Collection / Binding / Ingestion Receipt
2. Bundle / Bundle Revision / Document / Revision Document Member / Document Version
3. Parse View / Ingestion Job
4. Evidence（直接包含 Parser 工件追溯字段）
5. Discovery Object / Relation
6. 索引、APEX 只读视图、一致性巡检与清理任务所需对象
```

每张表采用 `NUMBER(38) GENERATED BY DEFAULT ON NULL AS IDENTITY`、`TIMESTAMP(6) WITH TIME ZONE` 审计列、显式字符串状态 `CHECK` 和 JSON CLOB `IS JSON` 约束。可变聚合根使用 `row_version`；不可变事实行不需要暴露更新接口。

## 迁移分组

| 迁移 | 新增对象 | 关键验证 |
| --- | --- | --- |
| `001_kc_roots` | `KBOT_KC_COLLECTION`、`KBOT_KC_COLLECTION_BINDING`、`KBOT_KC_INGESTION_RECEIPT` | Collection 的 App/Domain/key 唯一性、Binding 删除保护、Receipt 幂等键 |
| `002_kc_ingestion_aggregates` | Bundle、Revision、Document、Member、Document Version、Parse View（含工件/质量清单）、Job | 来源唯一性、不可变版本、CONTENT/可选 MANIFEST 角色、成员唯一性、View 状态、工件可回放和 Job 租约 |
| `003_kc_evidence` | Evidence（含 `source_spans/locator/provenance`） | View 内 Evidence key 唯一性、Atom/span 可追溯、类型和状态约束 |
| `004_embedding_model_dimension` | AI model dimension guardrails | Collection 绑定模型与全局向量维度一致 |
| `005_kc_retrieval_index` | Evidence/Discovery 向量索引支持 | 当前视图、模型身份和输入 hash 可校验 |
| `006_kc_discovery_object` | Discovery Object | 当前 Revision 可见性、Profile 投影 |
| `007_kc_relation` | Relation | 当前 Revision 内的确定性/可回溯关系依据 |
| `008_kc_indexes_views`（后续） | Oracle Text、优化索引、APEX 只读视图 | 先完成数据验收，再由 DBA 在线构建 |

Receipt 属于 API 运行支持表，仍在第一批创建，因为 multipart 受理在没有它时无法安全幂等/补偿。

项目仍处于开发状态，因此 `001`–`003` 直接表达当前唯一基线，不维护未发布 Schema 的兼容补丁。`002/003`、Entity、批次 DTO 与 complete 校验必须始终同步变更。

`002` 的 Member 角色基线必须包含中性 `CONTENT`；MANIFEST 是 Adapter 可选且每 Revision 至多一个，不再是通用强制成员。KM Asset Intake 可生成 MANIFEST，普通文件组可以只有一个或多个 CONTENT。

## 索引与在线构建

先创建约束和管理/状态 B-tree 索引，再在样本数据验证后创建 Oracle Text/Vector 索引。Oracle 向量维度必须与 `base.toml` 一致；所有可用 Embedding 模型的 `embedding_dimension` 和实际服务响应都必须通过该维度校验。模型身份则由 Collection 绑定并写入索引行快照；近似检索算法和中文 lexer 由 Oracle 版本及 DBA 验证冻结。

所有检索 SQL 都显式过滤 `ACTIVE` 状态和当前 Revision，不能依赖索引本身排除 STAGED/DELETING 数据。若 Oracle Vector 索引不能支持所需状态过滤，先使用正确的过滤 + 精确/候选查询，性能优化通过评测后单独迁移。

## APEX 只读视图

创建最小只读视图而非让 APEX 直接扫描 KC 基表，例如：

- `KBOT_KC_V_COLLECTION`：Collection 管理列表，直接暴露 `app_id/domain_id`。
- `KBOT_KC_V_BUNDLE_CURRENT`：Bundle join 当前 Revision、状态和安全展示字段。
- `KBOT_KC_V_MEMBER_STATUS`：当前 Revision 附件目录、处理状态和受限错误摘要。
- `KBOT_KC_V_DISCOVERY_CARD`：当前可见 Bundle/Document 卡片，不暴露 profile 向量或内部 URI。

所有视图以 Collection join 强制 `app_id + domain_id` 条件，APEX 只授予视图 `SELECT`，不授予 `KBOT_KC_*` 基表 DML。Evidence 正文、对象 URI、Job payload 和模型/提示词配置不进入 APEX 通用视图。

## 回滚与数据修复

新增 Schema 迁移的回滚优先是停止 V2 应用、保留新增表和数据，修复后重跑；不在首次部署自动 `DROP TABLE`。只有确认没有 V2 数据或已完成归档的非生产环境，才允许执行对应 down migration。

生产数据修复必须通过 KC 管理命令：禁用 Collection、重试 Job、补传 Member、重解析 View 或 `COLLECTION_PURGE`。禁止 DBA/页面直接修改 Evidence、Revision 指针或状态来“修好”数据；这会破坏不可变版本和引用可追溯性。

## DDL 验收

- 空 Schema 可按顺序完整升级；重复执行迁移安全失败或幂等跳过。
- 迁移后可创建同 Domain 多 Collection、同 Collection 多 Bundle/Revision、多 Member 和重解析 View。
- APEX 视图跨 Domain 查询为空，且无法写 KC 基表。
- 约束/索引能拦截重复来源、重复 Member、重复 Evidence key 与重复 Receipt key。
- 禁用/删除/清理和 Job 租约的集成测试不依赖任何 V1 表。
