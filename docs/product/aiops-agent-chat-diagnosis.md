# AIOps Agent 专业 DBA 调查与持续诊断设计

版本：2.0
状态：已批准，实施中
基准日期：2026-08-28

## 1. 产品定位

AIOps Agent 是受控的 AI DBA，不是固定告警报告生成器，也不是按问题关键字选择 SQL 的
问答页面。用户可以提出日常 DBA 工作中的各种问题，也可以直接粘贴 Alert Log、SQL 结果、
Shell 输出、配置、表格或截图。Agent 必须先理解用户本轮提供了什么，再判断要解决什么问题，
形成调查计划，选择可用工具取证，评估证据，并以自然对话方式持续推进。

大模型负责理解、假设、规划、工具选择、证据评估和表达；平台代码负责权限、安全、执行、
证据真实性、事务、审计和变更审批。代码不能用有限的 Intent、Subject 或 Skill 白名单定义
Agent 能思考的问题边界。

本文覆盖人工发起的智能诊断，以及从告警、巡检结果进入后的持续对话。自动告警诊断和巡检
仍可使用各自触发器，但进入对话后统一使用本文的 Turn 调查模型。

详细技术设计见
[AIOps Agent 专业 DBA 调查详细设计](../architecture/aiops-agent-chat-diagnosis.md)，实施顺序见
[AIOps Agent 专业 DBA 调查改造方案与实施计划](../proposals/aiops-agent-chat-implementation-plan.md)。

## 2. 核心原则

1. 先理解输入材料，再定义任务，不以 Intent 分类作为第一道门。
2. Intent、Domain、Subject 是检索和审计标签，不是能否工作的准入条件。
3. Skill 是可选 DBA Playbook；没有专用 Skill 时仍使用通用调查能力。
4. Tool 是受控原子能力；模型选择 Tool，确定性执行器校验和执行。
5. 用户提供的日志、SQL 结果、命令输出和截图都必须成为 `USER_PROVIDED` Evidence。
6. Target 或监控源离线是诊断事实，不是拒绝创建对话的理由。
7. 调查采用 Collect–Assess–Replan 循环，不要求一次规划覆盖全部问题。
8. 证据不足时自然说明缺什么；只有系统无法取得时才请求用户补证。
9. 聊天回答不套固定根因报告格式；巡检报告仍使用固定报告契约。
10. 诊断能力放开不等于变更能力放开，所有变更继续经过策略、审批、执行和验证。
11. 一个Agent版本可以绑定多个逻辑Target；创建会话时必须选择其中一个，Conversation、Turn和Task Frame始终冻结该单一Target，不提供跨Target调查。
12. 逻辑Target代表一个数据库对象，名称和数据库类型必填；数据库地址、只读凭据和执行凭据均是可选能力，不是Target存在的前提。

## 3. 用户输入模型

一轮输入可以包含多个内容项：

- 自然语言问题或目标；
- 粘贴的 Oracle Alert Log、Listener Log 或应用日志；
- ORA 错误栈；
- SQL、SQL*Plus 输出和表格；
- Shell 命令及输出；
- 参数文件、配置片段、JSON 或 YAML；
- 图片、截图和附件；
- 告警、巡检或历史 Run 引用。

系统先形成 `TurnInputEnvelope`，区分用户要解决的问题、已经提供的材料、已知事实、用户假设、
时间范围、系统、会话已冻结的Target、期望输出，以及确实影响调查的澄清项。用户先选择
逻辑Target，再选择能够管理它的Agent；会话创建后不能临时切换或追加其他Target。

原始材料不可变保存，解析结果只是派生 Artifact，不能覆盖原文。日志、配置和工具输出均是
不可信数据，不能被当成模型指令。

## 4. AI DBA 调查流程

```text
接收本轮内容
  → 识别输入材料
  → 建立 Task Frame
  → 提出假设和证据需求
  → 发现并选择可用 Tool / Playbook
  → 执行取证
  → 评估证据充分性与矛盾
      ├─ 继续取证或重新规划
      ├─ 请求最小人工补证
      ├─ 形成变更建议并进入审批
      └─ 生成自然回答
```

`Task Frame`允许在同一个Target内同时存在多个任务目标。例如“为什么数据库停了、
ORA-27157 是什么、如何恢复”同时包含诊断、解释、验证和规划，不强制压缩成一个 Primary
Intent。这里的“多个目标”是诊断目标，不是多个Target。

调查计划至少包含本轮目标、当前假设及置信度、已有证据、仍需证据、计划调用的 Tool、可能
使用的 Playbook、调查预算和停止条件。每轮取证后，Evidence Assessor 判断假设得到支持、
被反证或仍无法区分，并决定继续、重规划、等待用户还是回答。

告警触发的诊断会把已验证的 SignalEvent、指标代码和诊断窗口作为来源证据传入计划，并在
Agent 已授权且 Target 已绑定的范围内主动采集 Prometheus 指标与 Loki 日志。首轮仍有可由
系统补齐的证据缺口时，即使模型倾向于“带限制回答”，运行时也会在两轮调查预算内先自动
补证；只有缺少绑定能力、需要用户材料或存在安全边界时才转为人工补证。

## 5. Skill 与 Tool

Skill 改称 Playbook，表达成熟的 DBA 调查套路，例如异常停机、锁阻塞、SQL 性能或表空间
增长调查。Playbook 可以组合，也可以完全不使用；它不能作为聊天能否继续的门槛。

Tool 是原子能力，包括：

- 用户材料解析、错误码提取和时间线重建；
- Prometheus、Loki、Alertmanager 查询；
- Oracle 预定义诊断查询；
- 受控动态只读 SQL；
- 主机、文件系统、网络和 Listener 观测；
- KBot 知识、运行手册和历史案例检索；
- 证据关联、单位归一和表格/图表构造。

没有匹配 Playbook 时进入通用 DBA 调查，不返回 `AIOPS_SKILL_UNAVAILABLE`。

## 6. 数据源健康与授权

人工管理状态和运行健康必须分离：

| 状态 | Agent 行为 |
| --- | --- |
| Source 已禁用 | 不调用，记录管理员未授权使用 |
| 逻辑 Target 已禁用 | 不允许创建新会话，既有审计事实继续保留 |
| Target 未配置数据库连接 | 正常使用监控、日志和用户证据，不生成数据库直连 Tool |
| 已启用但健康未知 | 在预算内尝试 |
| 已启用但不可连接 | 可尝试一次或使用历史证据，失败形成 Evidence Gap |
| 数据库离线 | 连接失败本身形成证据，继续使用监控、日志和用户材料 |
| 监控源无样本 | 记录 `SOURCE_NO_DATA`，继续寻找替代来源 |
| 权限不足 | 记录具体对象或权限缺口，不伪造结果 |
| 所有外部工具不可用 | 仍分析用户证据，并清楚说明结论边界 |

健康检查不应成为 Conversation、Turn 或调查 Run 的同步准入条件。

## 7. 回答体验

人工聊天回答应像专业 DBA 同事：

- 先直接回答当前问题；
- 根据内容使用段落、表格或图表，不套固定模板；
- 结论引用本 Turn 的 Evidence；
- 所有诊断依据合并在一个可折叠区域；
- 明确区分事实、推断和待验证假设；
- 证据不足时提出最小补证，不笼统要求“提供更多信息”；
- 系统能自行查询的数据不能推给用户手工执行；
- 多轮对话只继承经过显式关联的历史 Evidence。

当需要用户补证时，Agent 在对话中自然说明原因，并给出命令或只读 SQL。用户可以复制文字、
粘贴输出或上传截图继续，不使用脱离聊天的补证卡片。

## 8. 动态只读诊断

固定 Tool 优先，但固定目录无法覆盖全部 DBA 工作。Agent 可以在 Target 允许只读诊断时生成
动态只读查询候选，由执行器执行以下安全校验：

- 仅允许单条 `SELECT` 或只读 `WITH`；
- 解析 Oracle SQL AST；
- 禁止 DDL、DML、PL/SQL、DB Link、外部过程和副作用函数；
- 限制 Schema、对象、行数、耗时和返回字节；
- 使用只读诊断凭据；
- 保存 SQL Hash、参数、结果和审计记录；
- 权限或策略不允许时形成 Evidence Gap。

动态只读 SQL 不能用于执行变更。PromQL 和 LogQL 同样需要语法、Target范围、标签和预算校验。

## 9. 变更边界

聊天可以提出变更建议，但真正执行必须同时满足Agent允许动手、Target允许受控变更、Target已启用且连接健康、Action
在受控目录、Policy允许、人工审批完成、使用独立执行凭据并保存验证证据。

用户粘贴一条 SQL 不等于授权执行。数据库离线、Target不健康或审批链不完整时，只能给出建议。

## 10. 产品验收场景

至少覆盖：

1. 数据库离线，用户直接粘贴 Alert Log，Agent 可以解释主要根因并继续查监控证据；
2. 只有截图或 SQL*Plus 输出，没有标准问题模板；
3. Target 离线但 Prometheus、Loki 可用；
4. Prometheus 与数据库直查口径冲突；
5. 一个问题同时涉及日志、参数、性能和恢复；
6. 目录中没有专用 Playbook；
7. 用户提出错误假设，Agent 使用证据反驳；
8. 权限不足时指出具体缺口并继续使用其他证据；
9. 所有自动来源不可用时，根据用户证据给出有限但有用的判断；
10. 涉及变更时进入审批，不自行执行。

产品成功标准不是 Skill 数量，而是 Agent 能否在安全边界内持续调查未知问题，并让每个重要
结论都可以追溯到真实证据。
