# AIOps 功能介绍与 PPT 生成说明

## 文档用途

本文用于指导生成一份面向管理者、运维负责人、DBA 和应用负责人的 AIOps 产品
介绍 PPT。内容依据当前 KBot 4.0 AIOps 代码、公开接口、权限模型和产品设计整理，
重点回答四个问题：

1. AIOps 解决什么业务问题；
2. AIOps 已经具备哪些功能；
3. 不同角色在业务中如何使用；
4. 系统如何保证诊断和执行过程可信、可控、可追溯。

PPT 应以业务流程和使用价值为主，不展开数据库表、接口字段和内部类名。不得虚构
客户数量、故障压降比例、节省工时或识别准确率等未经验证的数据。

## 一句话定位

KBot AIOps 是面向 Oracle 和 MySQL 数据库运维的智能诊断与处置平台：它把监控
告警、数据库只读诊断、运维知识和人工补充证据汇聚到一个可追溯的处理流程中，
帮助团队完成“发现问题、分析根因、形成方案、审批执行、验证效果、沉淀报告”的
闭环。

它不是一个只会回答问题的聊天机器人，也不是可以绕过审批直接修改生产数据库的
自动化脚本平台。它的核心价值是让 AI 分析能力运行在明确的数据边界、权限边界和
执行护栏之内。

## AIOps 解决的业务问题

传统数据库运维常见以下痛点：

- 监控指标、数据库状态、操作手册和沟通记录分散，排障需要在多个系统之间切换；
- 告警只能说明“出现异常”，不能直接说明原因、影响和下一步动作；
- 根因判断依赖少数专家经验，分析过程难复用，结论缺少证据链；
- 数据库暂时不可连接时，自动诊断容易中断，人工补充的数据又难纳入统一记录；
- 变更建议和实际执行之间缺少审批、权限、参数及版本约束；
- 命令执行成功经常被误认为故障已解决，缺少处理前后的同口径验证；
- 日常巡检、故障复盘和周报大量依赖人工整理，历史过程难以审计。

AIOps 将这些分散活动组织为统一的运维 Run，并保存每一步任务、证据、判断、审批、
执行和报告，使一次处理既能解决当前问题，也能形成可复盘的组织资产。

## 业务角色与职责

系统内置三类 AIOps 应用角色，并可将私有 AIOps Agent 单独授权给指定用户或角色。

| 角色 | 主要职责 | 典型操作 |
| --- | --- | --- |
| 运维操作员 | 维护运行所需资源并处理日常任务 | 管理 Target、监控源、策略和巡检计划，发起或查看诊断 Run，补充证据 |
| 审批人 | 对高风险数据库操作进行独立把关 | 查看根因、证据、风险和回滚方案，逐条批准或拒绝变更提案 |
| 管理员 | 管理 AIOps 应用、成员和 Agent | 分配成员角色，配置私有 Agent 及其授权，管理全部 AIOps 资源 |

拥有 AIOps 使用权限且取得某个私有 Agent 授权的用户，可以使用该 Agent 发起持续
对话。角色权限与 Agent 授权是两道独立控制：有应用权限不等于自动获得所有 Agent。

## 功能全景

### 1. 运维对象与凭据管理

- 管理 Oracle、MySQL 数据库 Target，并记录环境、主备角色、连接信息和运行状态；
- 区分诊断凭据和执行凭据：只读诊断可用不代表允许变更；
- 凭据由平台统一加密托管，Agent 和浏览器不接触数据库明文密码；
- 支持凭据轮换、移除、连接健康状态以及 Target 的启用、维护和停用；
- 一个 Target 可绑定多个监控源，并设置主来源、补充来源、优先级和指标映射。

### 2. 多源监控接入

- 接入 Prometheus、Zabbix 和 Oracle Enterprise Manager；
- 支持监控源配置、健康检查、凭据轮换和 Webhook 密钥轮换；
- Webhook 接入包含签名校验、防重放、去重、幂等和外部 Target 映射；
- 当前标准指标覆盖可用性、CPU、连接数、连接利用率、事务吞吐、响应延迟、存储
  使用率、剩余与最大容量、错误率等基础运维信号；
- 多来源数据统一保留时间窗口、单位、来源和质量信息，避免脱离上下文比较指标。

### 3. 三种主要业务入口

#### 对话诊断

适合即时排障、性能咨询和多轮追问。用户描述现象后，AIOps 冻结本次分析的 Target、
时间窗口、策略和 Agent 版本，采集监控与数据库证据，再给出结论或最小补证请求。
同一会话可以连续追问，历史过程不会因为 Agent 后续升级而改变。

#### 告警自动诊断

Prometheus、Zabbix 或 OEM 告警进入平台后，系统完成验签、映射、去重和落库；达到
策略条件时自动创建诊断 Run。告警流程不等待人工补证，证据不足时如实输出部分
报告或“不足以判断”，而不是生成确定性结论。

#### 定时巡检

巡检计划支持日报、周报和 Cron 表达式，并包含时区、任务重叠和错过调度策略。
一次调度会冻结计划与目标清单，再按 Target 分别执行诊断，最后形成日巡检或周巡检
结果。计划先以暂停状态创建，绑定有效 Target 后再启用，避免误触发空计划。

### 4. 证据驱动的根因分析

AIOps 将分析材料区分为四种可信来源：

| 证据类型 | 业务含义 |
| --- | --- |
| 系统验证证据 | 来自监控适配器或只读数据库执行器的直接观测 |
| 用户提供证据 | 用户回贴的 SQL 结果、文本、CSV、HTML 或截图 |
| 知识引用 | 来自运维 SOP 或历史知识的机制说明和处理经验 |
| 模型推断 | AI 形成的假设、摘要和因果推断 |

运维知识可以解释“某种现象通常为什么发生”，但不能单独证明当前实例就是该原因。
系统围绕候选假设保存支持证据、反证和数据缺口，并将根因分为四级：

- 已确认：有直接证据，时间顺序与机制一致，关键替代假设已排除；
- 很可能：多项证据一致，但仍缺少一项直接验证；
- 可能：只能解释部分现象，或仍有较强的替代原因；
- 无法判断：证据不足、相互冲突，或无法区分关键假设。

只有“已确认”或“很可能”的根因才允许形成定向变更提案。

### 5. 数据库只读诊断

Oracle 和 MySQL 当前均提供六类版本化诊断工具：实例身份、活动会话、阻塞链、存储
容量、长事务和复制状态。模型只能选择已登记的工具及参数，不能把任意生成的 SQL
直接交给数据库执行。

只读执行器对模板版本、目标类型、超时、最大行数和敏感字段进行控制。这样既保留
AI 选择诊断路径的灵活性，又避免自由 SQL 带来的越权和不可预测风险。

### 6. 人机协同补充证据

当 Chat 场景中数据库无法直连或证据不足时，系统可以创建人工补证请求：

1. 给出范围受控、仅供人工执行的只读 SQL 或数据请求；
2. 用户在自己有权限的环境中执行并回贴结果；
3. 系统保留原文、来源和内容摘要，将其标记为“用户提供证据”；
4. 原诊断 Run 从等待状态恢复，继续分析；
5. 用户也可以跳过请求，系统会基于已有证据给出受限结论。

会话还支持上传图片、纯文本、CSV 和 HTML 文件。图片可根据 Agent 的能力配置使用
OCR 或视觉模型提取信息，但提取结果仍标记为模型生成证据，不会伪装成系统直采数据。

### 7. 私有 AIOps Agent

管理员可以为不同运维场景创建私有 Agent，并配置：

- 监控源和诊断策略；
- 可选的固定 Target 与巡检计划；
- 语言模型、视觉能力、业务指令和运行参数；
- Agent 状态和不可变版本；
- 面向指定用户或角色的使用授权。

因此，同一套平台可以形成面向核心库、测试库、值班排障或专项巡检的不同 Agent，
同时保持权限和配置相互隔离。

### 8. 策略、建议与受控变更

策略决定是否允许 Agent 形成可执行提案、允许的最高风险、动作类型、告警自动观察
阈值和冷却时间。资源或策略不满足时，AIOps 只生成建议，不会尝试执行。

当前自动执行能力严格限定为 Oracle/MySQL 的高风险会话终止或断开，用于处理已确认
的阻塞或异常会话。流程为：

```text
根因判断 → 动作计划 → 策略校验 → 待审批提案
         → 单条人工批准 → 一次性执行授权 → 执行器复核
         → 执行 → 效果验证 → 对比报告
```

每条命令必须单独审批。审批绑定 Target 版本、模板、参数、策略、提案内容摘要和过期
时间；其中任一内容改变，原审批即失效。多命令方案严格串行，上一条执行和验证完成
后才进入下一条审批。其他变更建议目前由人工执行并回填结果。

### 9. 处理后验证与对比

“命令成功”只说明调用完成，不代表问题已经解决。AIOps 会在处理前冻结基线，等待
系统稳定，再用相同来源、窗口、单位和聚合口径采集处理后信号，同时观察主指标与
护栏指标。

最终结论包括：已解决、已改善、无变化、恶化或无法判断。只有时间上的先后关系而
没有足够证据时，系统不会宣称变更与恢复存在确定因果关系。

### 10. 报告与审计

系统提供五类报告：

| 报告类型 | 主要用途 |
| --- | --- |
| 故障报告 | 记录故障时间线、影响、根因、证据、处置和当前状态 |
| 性能报告 | 呈现性能症状、瓶颈、关键指标和优化建议 |
| 日巡检报告 | 汇总当日健康状态、异常、风险和待办建议 |
| 周巡检报告 | 汇总趋势、重复告警、未解决事项和周期对比 |
| 处理前后对比报告 | 展示主指标、护栏、副作用和最终验证等级 |

报告正文为不可变内容；更正时创建新版本，不覆盖历史。Run、任务、证据、策略、人工
输入、审批、执行和验证全过程均可审计。前端可通过实时事件展示分析进度、补证请求、
审批状态、执行状态和报告就绪状态。

## 业务使用方法

### 首次配置

1. 管理员为成员分配运维操作员、审批人或管理员角色；
2. 运维操作员配置 Prometheus、Zabbix 或 OEM 监控源并执行健康检查；
3. 创建 Oracle/MySQL Target，配置只读诊断凭据；如确需受控执行，再单独配置执行
   凭据；
4. 将 Target 与一个或多个监控源绑定，并确定主来源和补充来源；
5. 创建并启用诊断策略，明确自动触发条件和允许的动作边界；
6. 管理员创建私有 AIOps Agent，绑定监控源、策略、可选 Target、模型和巡检计划；
7. 将 Agent 授权给指定用户或角色；
8. 如需周期巡检，创建计划、绑定 Target 后再启用。

### 日常使用

1. 用户通过对话、告警或巡检进入一个运维 Run；
2. 系统采集监控、数据库和知识证据，展示实时进度；
3. 用户查看根因等级、支持证据、反证和数据缺口；
4. 如系统请求补证，用户提交文本、SQL 结果或文件，也可以选择跳过；
5. 如无需变更，系统输出结论、建议和相应报告；
6. 如需要变更，审批人逐条审核提案；不满足执行条件时由人工处理并回填结果；
7. 系统执行处理后验证，形成对比结论和完整审计记录。

## 典型业务场景

### 场景一：数据库连接数持续升高

值班人员向 AIOps Agent 询问某生产库连接数升高的原因。系统关联连接利用率、活动
会话、长事务和错误率，识别异常会话来源并判断是否存在连接泄漏或长事务占用。如果
数据库暂不可连接，系统请求用户执行最小只读 SQL 并回贴。最终输出根因等级、影响、
应急缓解、长期修复和验证方式。

### 场景二：阻塞告警触发受控处置

监控系统推送严重阻塞告警。AIOps 自动创建 Run，检查活动会话和阻塞链，并通过
监控时间线验证影响。根因达到提案门槛且策略允许时，系统生成终止阻塞会话的高风险
提案。审批人核对会话、风险和回滚说明后单条批准，执行器再次验证目标和前置条件，
完成操作后对比阻塞链、响应延迟和错误率，最后生成故障与对比报告。

### 场景三：每周数据库健康巡检

运维负责人建立周巡检计划并绑定多个 Target。调度时间到达后，系统按 Target 分别
采集可用性、容量、连接、事务和复制状态，对异常项形成证据与建议，再聚合为周报。
负责人可以看到重复告警、容量风险、未解决事项和周期变化，而不必人工汇总多个监控
页面。

### 场景四：通过截图和导出文件补充现场信息

用户上传监控截图、CSV 导出或 SQL*Plus 文本。AIOps 将文件作为会话证据保存，按
Agent 配置提取信息并标明来源，再与系统直采数据交叉验证。适用于网络隔离、跨团队
协作或只能从第三方控制台导出信息的现场。

## 产品价值表达

PPT 中建议将价值表述为可验证的能力，不使用未经实测的百分比：

- 从“看见告警”提升为“得到有证据等级的根因判断”；
- 从依赖个人经验转为可复用、可追溯的标准诊断过程；
- 从工具间人工搬运数据转为监控、数据库、知识和人工证据统一汇聚；
- 从聊天建议转为带策略、审批和执行器复核的受控处置；
- 从“命令执行成功”转为处理前后同口径验证；
- 从人工编写复盘和巡检报告转为全过程自动沉淀、版本化保存；
- 通过角色权限和私有 Agent 授权，使能力能够按团队和场景安全开放。

## 当前能力边界

生成 PPT 时必须保留以下边界，避免把规划能力描述成已交付能力：

- 当前公开产品 Target 类型为 Oracle 和 MySQL；PostgreSQL 已有内部只读诊断驱动
  与目录，但尚未开放为当前 AIOps 托管 Target；
- 当前系统可自动执行的数据库变更仅为审批后的会话终止或断开，其他动作只能形成
  建议或由人工执行并回填结果；
- Email 和即时通信通知仅预留扩展接口，尚未提供实际发送适配器；
- Shell、OEM Job、Zabbix Remote Command 不由系统自动执行；
- 告警和巡检流程不会等待人工补证，证据不足时输出部分或无法判断的结果；
- 不能把知识库内容或模型推断当作现场事实，不能把时间相关性直接表述为因果关系。

## 推荐 PPT 结构

建议生成 14 页，适合 15 至 20 分钟介绍。

| 页码 | 标题 | 核心信息 | 建议画面 |
| --- | --- | --- | --- |
| 1 | KBot AIOps：可信、可控的数据库智能运维 | 产品名称和一句话定位 | 数据库、监控、AI 与运维人员组成的闭环主视觉 |
| 2 | 为什么需要 AIOps | 数据分散、告警无根因、经验难复用、处置难审计 | 四项业务痛点，不使用虚构数字 |
| 3 | 从告警到验证的完整闭环 | 发现、诊断、建议、审批、执行、验证、报告 | 横向闭环流程图 |
| 4 | 谁在使用 | 运维操作员、审批人、管理员的职责分工 | 三角色泳道或职责卡片 |
| 5 | 功能全景 | 资源配置、三类入口、诊断、协作、处置、报告 | 分层能力地图 |
| 6 | 统一连接运维数据 | Target、监控源、凭据、策略、Agent 和巡检计划 | 资源关系图 |
| 7 | 三种业务入口 | 对话排障、告警自动诊断、定时巡检 | 三入口汇入统一 Run |
| 8 | 证据驱动的根因分析 | 四类证据、支持与反证、四级根因 | 证据漏斗或假设—证据矩阵 |
| 9 | 数据不足时，人和 AI 继续协作 | 人工 SQL、文本和文件补证，可跳过并受限结论 | 用户—Agent—数据库时序图 |
| 10 | 每次变更都在护栏内 | 策略门、逐条审批、一次性授权、执行器复核 | 多道闸门流程图 |
| 11 | 执行成功不等于问题解决 | Before/After、主指标、护栏指标和五级验证 | 前后对比示意图，避免伪造实测曲线 |
| 12 | 巡检与五类报告 | 日报、周报、故障、性能和对比报告 | 报告组合与周期时间轴 |
| 13 | 安全与审计贯穿全程 | 托管凭据、最小权限、不可变证据、版本化报告 | 纵深防护图 |
| 14 | 场景演示与业务价值 | 严重阻塞告警到审批、验证和报告的完整故事 | 一条端到端故事线和六项价值总结 |

如演示对象更偏管理层，可减少诊断工具细节，强化第 2、3、4、13、14 页；如演示
对象是 DBA 或运维团队，可在第 8 至 11 页增加诊断、补证和审批细节。

## 视觉与文案要求

- 风格：企业级、克制、可信，避免赛博霓虹、机器人头像和夸张“全自动”视觉；
- 配色：深蓝或石墨灰为主色，青绿色表示正常闭环，橙色表示待处理，红色仅表示
  风险与高危动作；
- 图形：优先使用闭环图、泳道图、证据矩阵、闸门流程和 Before/After 对比；
- 文案：每页只讲一个结论，标题使用业务语言，正文控制在三至五个要点；
- 术语：首次出现 Target 时写作“运维目标（Target）”，Run 写作“运维任务
  （Run）”，后续可使用英文简称；
- 数据：没有真实演示数据时使用“示意”标签，不生成看似真实的客户名称、IP、指标
  数值或收益比例；
- 边界：使用“受控执行”“人机协同”“证据等级”，避免使用“无人值守自动修复”
  “百分百定位根因”等表述。
