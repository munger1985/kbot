## 1. 评估结论

客户当前痛点不明显：性能问题在 XD 上线后已经不突出。因此后续不能继续把
“AI 能分析性能”当作主卖点，而要把 AIOps 做成 **DBA 日常工作的受控助手**。

三个入口保持不变，并且继续共用同一套 Agent 诊断逻辑：

```text
智能诊断 / 告警诊断 / 日常巡检
        ↓
同一套 Agent 诊断
        ↓
Finding Card → 指标与趋势分析 → 根因分析 → 解决方案
        ↓
仅当 Agent 允许动手：一条 SQL → 审批 → 执行 → 验证 → 下一条，循环到结束
```

近期竞争力不来自新入口，而来自把这套逻辑讲完整、做完整：

1. 先列出可行动的 Finding Card，不把关键事实埋进分析过程；
2. 再做指标、趋势和根因分析；AWR 原生 HTML 继续保留，分析阶段按需求做对比和趋势；
3. 最后给解决方案；允许动手时，解决方案之后逐条审批执行，绝不整批批准。

ADG 切换演练不进入诊断主链，作为后续独立功能。

官方诊断脚本按实际跑在哪一层接入，三种方式不能混用：SQL Monitor / AWR / XPLAN
由产品内 Report Tool 生成，用户不跑也不上传；SQLHC 做成 Playbook 组合已有 SQL Tool，
默认也不上传；只有 ExaCheck / ORAchk / TFA 近端消费客户已有报告。

## 2. 当前能力基线

以下只记代码和产品文档已经落地的能力，不把目标态写成已交付。

### 已具备

- 三个业务入口：智能诊断、告警诊断、日常巡检；入口不同，诊断内核同一套。
- Target 管理：Oracle / MySQL / PostgreSQL；诊断凭据和执行凭据分离。
- 诊断源：Prometheus、Alertmanager、Zabbix、OEM、Loki。
- 诊断第一屏是 Finding Card，随后是分析、解决方案；允许动手时在方案后逐条审批执行。
  Cube 告警/巡检/运行详情以只读方式渲染同一套四段 blocks，诊断页保留交互审批。
- Finding Card 已覆盖 22 类，含无效对象、FRA 余量、备份失败、长事务、高耗时 SQL；
  归档 Finding 只讲 FRA 余量，不把归档生成量写成事实。
- Oracle 只读诊断覆盖实例、会话、阻塞链、等待、存储、UNDO/TEMP、归档、复制延迟、
  无效对象、备份任务、Top SQL、执行计划、AWR/ASH HTML、AWR Diff、SQL Monitor 官方 HTML。
- 巡检 Check Catalog 24 项：19 READY 可勾选，5 PLANNED 在界面标为「规划中」且不可勾选；
  日检看当前态，周检可打开趋势项。
- Oracle 受控动作已有表空间 `AUTOEXTEND`/`RESIZE`、杀会话、索引维护、统计信息、
  用户锁定等；多命令按逐条审批、串行执行、上一条验证后再进下一条。
- `switchover` 仍为 `UNSUPPORTED`，`failover` 仅允许人工命令展示。
- SQLHC 已是 Playbook；ExaCheck / ORAchk / TFA 近端消费已有报告，不把 MOS 脚本集成进程序。
- AWR 原生 HTML 保留，分析阶段可按需求做对比和趋势。
- 库群 Fleet 总览、领导 briefing、容量约束、Target 运维记忆已有实现。
- MySQL / PostgreSQL 只读诊断已覆盖复制延迟、死元组、Autovacuum、Idle 会话、连接使用率、QPS。
- 正式报告、站内通知订阅已有后台；飞书/Email/ITSM 未交付。
- 对话诊断支持用户补证；控制面与数据库执行器已经分离。

## 4. Agent 诊断逻辑

这是三个入口共用的主链，后续改动都围绕它，不按入口再做第二套诊断。

```text
入口只负责把问题送进来
  智能诊断：用户提问、粘贴材料、选择 Target
  告警诊断：监控信号进入 Situation 后启动同一套诊断
  日常巡检：计划到期后对勾选检查项取证，再进入同一套诊断

Agent 诊断固定四段，顺序不能颠倒：

  1. Finding Card
  2. 指标分析 / 趋势对比 / 根因分析
  3. 解决方案
  4. 受控动手（仅当 Agent 允许动手）
```

告警自动诊断和巡检自动跑完时，默认停在第 3 段：给出 Finding、分析和方案，不自动动手。
用户从告警或巡检进入续聊后，才按该 Agent 的动手授权决定是否进入第 4 段。

### 4.1 Finding Card

诊断第一屏先列出关键事实，不先写分析过程。

卡片是结构化对象，不是模型自由发挥的段落。锁、长会话、主备延迟、等待事件、
表空间、长事务等各自有固定字段。锁场景至少包括：

- 系统 / Target、实例
- Holder / Waiter 的 SID、Serial、用户
- SQL_ID、锁类型、LMODE、CTIME
- 等待事件、当前值、阈值、阻塞链深度

没有阈值的巡检 Finding 也要给出对象、当前值、是否越界和影响面。
分析过程可以随后展开，不能压过卡片。

### 4.2 指标分析、趋势和根因

第二段才进入专业分析：

- 用本轮证据解释 Finding 为什么成立或为什么还不能下结论；
- 需要历史时做趋势，需要对照时做对比，不默认每次都出全量报告；
- AWR 原生 HTML / Diff / ASH 继续按快照生成，作为不可变证据保留；
- 用户要“看过去一周”或“对比两个时间点”时，在 HTML 之上输出 Load Profile、
  Top Wait、Top SQL 等变化结论，并引用已确认快照，不猜测快照号；
- 根因仍分已确认 / 很可能 / 可能 / 无法判断；数据缺口显式写出。

这一段服务 DBA 判断，不替代第一段的关键事实。

### 4.3 解决方案

第三段只给可执行的处理路径：缓解、修复、回滚、验证，以及不做的理由。
没有 Finding 时可以是“继续观察”或“按既定巡检周期执行”，不要编造故障。

自动告警和自动巡检可以在这里结束，并允许用户生成正式报告或进入续聊。

### 4.4 受控动手：一条审批、一条执行、循环到结束

仅当该 Agent 对该 Target 允许动手、执行凭据和动作目录都具备时，才进入第 4 段。
未授权时只保留方案和“仅供人工执行”的命令，不出现审批按钮。

动手接在解决方案之后，顺序固定：

```text
解决方案
  → 取出下一条已登记动作，渲染为一条 SQL / 命令
  → 用户在独立审批入口批准这一条
  → Executor 执行这一条
  → 同口径验证
      ├─ 成功 → 下一条 SQL，重复审批/执行/验证
      ├─ 失败或拒绝 → 停止后续动作，保留已执行结果和缺口
      └─ 没有下一条 → 结束，必要时给对比结论
```

约束与现有受控动作契约一致，后续产品不能改掉：

- 不支持整批批准；
- 聊天里的“同意”“执行吧”不是审批；
- 上一条未执行并验证前，不放出下一条；
- Target、参数、模板或回滚方案变化后，原审批失效；
- `DROP`、`TRUNCATE`、switchover、failover、restore 不进入自动执行器。

## 5. 官方诊断脚本如何融入

先澄清一个容易混在一起的结论：

**不是**让用户自己跑 ExaCheck / ORAchk / SQL Monitor / SQLHC，再把报告上传给产品。
**也不是**把 MOS 脚本原文放进仓库、在目标库执行，或让模型读脚本学成 Skill。
**更不是**再开第四个“跑官方脚本”入口。

正确做法是按官方能力实际跑在哪一层分成三种方式，**三种方式不能混用**：

| 能力 | 谁执行 | 用户要不要上传 | 产品怎么做 |
| --- | --- | --- | --- |
| AWR / ASH / XPLAN / **SQL Monitor** | 产品内 Report Tool，走 DB Executor | **不要。** Agent 按已确认 `sql_id` / 快照直接生成 | 方式 A：和现有 AWR 一样 |
| **SQLHC / SQLT** | 产品内 Playbook 调已有 SQL Tool | **默认不要。** 客户已有 HTML 时可作补证，不替代在线取证 | 方式 B：调查语义预编译，不进 MOS 文件 |
| **ExaCheck / ORAchk / TFA** | 主机侧脚本，不能走 DB Executor | **近端要。** 消费已有报告；Host Runner 后置为独立能力 | 方式 C：先导入 Finding，后独立执行 |

它们先被预编译成能力包，再接到同一套 Agent 诊断四段：

```text
官方脚本 / 官方包
        ↓ 预编译，禁止运行时学习
Diagnostic Pack
  ├── Report Tool   原生 HTML/TEXT，作为不可变证据（AWR 同款）
  ├── Fact Tool     结构化字典查询，给 Finding Card 提供字段
  └── Playbook      脚本对应的取证顺序、适用环境和停止条件
        ↓
同一套 Agent 诊断
  Finding Card → 分析 / 趋势 / 根因 → 方案 → 可选逐条动手
```

### 5.1 方式 A：数据库官方包报告（AWR 模式）

适用已经在数据库里、可用只读包调用的能力。

| 能力 | 现状 | 融入方式 |
| --- | --- | --- |
| AWR / AWR Diff / ASH HTML | 已有 Report Tool | 保留 HTML；分析段按需抽变化结论 |
| DBMS_XPLAN DISPLAY_CURSOR | 已有 Tool | 继续作为 SQL 诊断证据 |
| SQL Monitor 行数据 | 已有 `db.sql.plan_monitor` 读 `GV$SQL_PLAN_MONITOR` | 保留为 Fact Tool |
| SQL Monitor 官方报告 | 缺失 | 新增 Report Tool，调用 `REPORT_SQL_MONITOR` 生成 HTML/TEXT |
| AWR SQL Report | 缺失 | 后续按已确认快照 + SQL_ID 生成原生报告 |
| ADDM | 缺失 | 后续官方包报告 + Finding 映射 |

规则与现有 AWR 完全一致：

- 固定、带版本和哈希的 Tool，不允许模型把包名写进动态 SQL；
- 未确认 `sql_id` / `sql_exec_id` / 快照号时，先列出可见对象，不猜测；
- 原生 HTML/TEXT 作为附件保留，可下载；
- 回答正文只使用从报告抽出的 Finding 和分析，不把整份报告贴进对话。

SQL Monitor 是这一类里最靠近现有 AWR 模式、也最该先补的能力。
当前 `db.sql.plan_monitor` 只读 `GV$SQL_PLAN_MONITOR` 行数据，**不是**官方 SQL Monitor
报告；补齐后由 Agent 直接调用 `REPORT_SQL_MONITOR`，用户不跑脚本、不上传 HTML。

### 5.2 方式 B：把脚本调查语义做成 Playbook（SQLHC 模式）

适用 SQLHC、SQLT 这类 MOS SQL*Plus 脚本。它们本质是检查清单和取证顺序，
不是数据库里的一个包。

不能做：

- 不把 MOS 脚本原文放进仓库，也不在目标库执行该脚本；
- 不在目标库安装 SQLT 对象；
- 不让 Agent 运行时阅读脚本并生成 Skill。

要做：

- 把脚本的检查意图拆成 Fact Tool：游标、执行计划、对象统计、ASH、绑定、
  优化器参数、SQL Monitor；
- 用 Playbook DAG 固定取证顺序、依赖和停止条件，这才是“SQLHC 能力”；
- 现有目录已覆盖其中一大部分（`db.sql.cursor_details`、`db.sql.display_cursor`、
  `db.sql.object_statistics`、`db.sql.plan_monitor`），缺的是组合它们的 Playbook，
  以及绑定、直方图、基线/Profile 等少量 Tool；
- 用户给出 SQL_ID、粘贴 SQL，或从锁/长会话 Finding 进入某条 SQL 时，Agent 选用
  该 Playbook，而不是另开“脚本页面”；
- 若客户已经跑过 SQLHC 并保存 HTML，允许作为用户证据导入并抽取 Finding，
  但不替代在线取证，也不是 SQLHC 的主路径。

三个入口都复用这一包：

- 智能诊断：问题中有 SQL_ID 或 SQL 文本；
- 告警诊断：长会话、高 CPU、等待事件已经定位到 SQL_ID；
- 日常巡检：Top SQL 越界后进入同一 Playbook，不在巡检里再写一套 SQL 分析。

### 5.3 方式 C：主机侧健康脚本先导入、后独立执行（ExaCheck 模式）

适用 ExaCheck / `exachk`、ORAchk、TFA。它们跑在 Exadata 或主机上，
不能走数据库 Executor。这是三种方式里**唯一**近端以“消费已有报告”为主路径的一类，
不能把这个近端方案套到 SQL Monitor 或 SQLHC 上。

近端只做报告消费：

- 导入客户已产出的报告（对话上传或 Collector 落盘）；
- 把 FAIL / WARNING / INFO 解析成 Finding Card；
- 巡检计划可绑定“Exadata 健康包”，执行含义是消费已有报告，或只跑与库内检查
  重叠的项（参数、无效对象等字典能读到的部分）。

后端作为独立能力（与 ADG 演练同类，不进诊断主链的 P0/P1）：

- 库网内 Host Runner 按版本化检查组执行；
- 控制面和 LLM 不连主机、不持有 OS 凭据；
- 结果仍回到同一套诊断四段。

### 5.4 这些产物在诊断四段中的位置

| 产物 | 出现位置 |
| --- | --- |
| 原生 HTML/TEXT 报告 | 证据附件，默认可折叠，可下载 |
| 从报告/脚本抽出的问题 | 第一段 Finding Card |
| 计划、等待、统计、趋势解释 | 第二段分析 |
| 改计划、补统计、杀会话等建议 | 第三段方案；允许动手才进入第四段 |

DBA 需要官方原件时打开附件；默认回答不贴整份 SQLHC 或 ExaCheck。

### 5.5 落地顺序

1. SQL Monitor 官方报告 Tool，补齐 AWR 同款模式（产品内生成，不上传）；
2. SQL 诊断 Playbook，用 SQLHC 的调查语义组合已有 Tool（默认在线取证，不跑 MOS 脚本）；
3. ExaCheck / ORAchk 报告导入成 Finding（近端消费已有报告）；
4. 需要时再做 Host Runner、ADDM、AWR SQL Report。

## 6. 模块清单：改什么，加什么

### 6.1 必须改动的现有模块

#### A. 三入口共用的诊断输出

现状：三个入口已经共用 Agent，但输出更像“先讲过程，再给薄证据”。

改动：

- 智能诊断、告警诊断、日常巡检都按第 4 节四段输出，不按入口定制第二套逻辑。
- 巡检的差异只在取证范围：执行计划勾选的检查项，再把越界项变成 Finding Card。
- 告警的差异只在输入：已有 SignalEvent 作为调查起点，不跳过 Finding Card。

#### B. Finding Card 与取证字段

- 为锁等待、长会话、DG Lag、等待事件、表空间、长事务定义卡片。
- Oracle 锁诊断 SQL 至少补齐 `serial#`、`sql_id`、`prev_sql_id`、`type`、`lmode`、
  `ctime`、Holder 当前事件、阻塞链深度。
- 现有 `db.session.blocking_chain` 不够用，要改 Tool，而不是只改文案。

#### C. AWR / ASH

保留现有能力：按已确认快照生成原生 AWR HTML、AWR Diff HTML、ASH HTML。

分析阶段按需求叠加，而不是替换 HTML：

- 用户要单次报告：生成并保留 HTML，同时抽出关键结论；
- 用户要对比两个时间点：用已确认的两段不重叠快照做 Diff HTML，并分析变化；
- 用户要看一段时间趋势：在快照序列上分析 Load Profile、等待、Top SQL 的变化方向。
- 未确认快照时只列可见快照，不猜测。

#### D. 巡检计划

- 增加 Check Catalog 勾选。
- 日检默认当前态；周检自动打开趋势窗口。
- 检查结果进入同一套 Finding Card → 分析 → 方案；有问题且用户续聊、Agent 允许动手时，
  再进入逐条审批执行。
- 检查项来自版本化 Tool/Playbook，不允许页面上自由写 SQL。

#### E. 部署与网络边界

- 控制面（Portal、Main API、LLM）禁止持有或转发数据库地址/凭据。
- 只有 DB 网内 Executor / Collector 访问库。
- 不能直连时走监控、日志、用户补证，并明确数据缺口。

#### F. 动手闭环接到解决方案之后

现状：逐条审批、串行执行的契约已经有；诊断界面还没有把它固定成解决方案后的循环。

改动：

- 诊断结果里，审批卡片只出现在解决方案之后；
- 每次只展示当前这一条 SQL；
- 执行并验证完成后才展示下一条；
- 自动告警/巡检默认不进入该循环。

#### G. Oracle 容量动作决策

- 存储路径、ASM 磁盘组、余量、命名规则做成 Target 级运维事实。
- Agent 先给出容量 Finding 和方案；允许动手时，`AUTOEXTEND`/`RESIZE` 走逐条审批。
- 没有磁盘组/路径事实时，允许聊天写入并经 DBA 确认后固化。
- `ADD DATAFILE` 继续保持 `PLANNED`，直到余量契约完整。

### 6.2 需要新增的模块

#### H. 巡检检查项目录

按客户点名的 Oracle 日/周检项建设：

| 分组 | 检查项 | 日检 | 周趋势 |
| --- | --- | --- | --- |
| 备份 | RMAN 备份量、占用空间、最近成功/失败 | 当前 | 需要 |
| 存储 | 表空间余量、数据文件数、增长量、UNDO、行链接、Top Segment | 当前 | 需要 |
| 会话 | 会话数、长会话、锁等待 | 当前 | 可选 |
| 对象 | 无效对象、索引数 > 3 的表、稀疏索引、非系统对象在系统表空间 | 当前 | 需要 |
| 日志 | 归档生成量、审计记录/文件数 | 当前 | 需要 |
| 性能 | 数据文件 IO、关键等待、严重排序 SQL、核心参数 | 当前 | 需要 |

MySQL / PostgreSQL 后续对齐：复制延迟、连接使用率、慢查询、死元组、Autovacuum、
Idle 会话占比、事务回滚率。

#### I. Target 运维记忆

可审计的环境事实，不存在模型上下文里：

- ASM 磁盘组、文件系统路径、表空间放置策略；
- 核心应用名与库的对应；
- 巡检例外和已知问题。

写入可查看、可撤回、带来源（人工确认 / 自动发现）。

#### J. SQL 诊断包（SQL Monitor + SQLHC 语义）

按第 5 节方式 A + B：先补 SQL Monitor 官方报告（产品内生成），再把 SQLHC 的检查清单
做成 Playbook（组合已有 SQL Tool）。三个入口共用，不新开“跑脚本”页面，也不要求用户
先跑官方脚本再上传。输出仍是 Finding Card → 分析 → 方案 → 可选动手；
原生 SQL Monitor / AWR SQL HTML 作为附件。

#### K. Exadata 健康包（ExaCheck）

按第 5 节方式 C：近端只导入客户已产出的报告并抽出 Finding，这是目前唯一以上传/采集
报告为主路径的官方脚本。Host Runner 后置为独立能力，不进 P0/P1。
巡检计划可绑定该包，结果仍进入同一套诊断，不另做 Exadata 产品。

#### L. 库群 Dashboard 与领导简报

服务“很多库”和领导，不替代 DBA 诊断页。领导视图只保留影响、风险、建议，
不下钻 SID。

#### M. 飞书出站

后续只推诊断阶段结论，不转发监控原文。

#### N. ADG 切换演练（独立功能，后置）

不进入三个入口的诊断主链，也不在 P0/P1 交付。后续单独做：

- HA Group：一套已有主库 + 备库；
- 演练前检查、演练步骤、演练后恢复检查；
- 只生成固定命令和活检查证据，不自动执行 switchover / failover。

## 7. 分阶段 Roadmap

```text
P0  诊断主链成型           4-6 周
P1  巡检 / 容量 / AWR分析  6-10 周
P2  专项技能与多库经营     8-12 周
P3  ADG 演练与平台深化     独立功能，按环境需要
```

### P0｜三个入口都按同一套诊断逻辑输出

目标：打开任意入口，先看到 Finding Card，再看到分析、根因和方案；允许动手时，
方案后出现“一条 SQL、一次审批、一次执行”的循环。

| 模块 | 类型 | 交付 |
| --- | --- | --- |
| 诊断四段输出 | 改 | 三入口共用 Finding → 分析 → 方案 → 可选动手 |
| Finding Card | 改 | 锁/长会话/延迟/等待/表空间关键字段固定展示 |
| 阻塞链与会话 Tool | 改 | 补 Serial、SQL_ID、锁类型、LMODE、CTIME、阻塞链 |
| 动手闭环 | 改 | 解决方案之后逐条审批执行，自动入口默认不动手 |
| 网络边界 | 改 | 控制面禁库、执行器在库网、补证路径可验收 |
| 演示口径 | 非代码 | 不再解释如何造故障，直接进入 Finding Card |

验收：用锁场景走智能诊断和告警诊断，第一屏能看到 Holder、Waiter、SQL_ID、
锁类型、持有时间；方案之后若允许动手，只能一条一条批。

### P1｜巡检可配置，容量能判断，AWR 能按需分析

目标：日检/周检仍走同一套诊断；AWR HTML 保留，分析能按需求对比和看趋势。

| 模块 | 类型 | 交付 |
| --- | --- | --- |
| 巡检 Check Catalog | 加 | 客户点名的 Oracle 检查项可勾选 |
| 周趋势 | 加 | 表空间增长、归档量、备份量等进入分析段 |
| 运维记忆 | 加 | ASM/路径/放置策略可确认后固化 |
| 容量决策 | 改 | 余量 + 趋势 + 磁盘组事实 → 方案；动手则逐条审批 |
| AWR 按需分析 | 改 | 保留 HTML；按一周或两个时间点输出变化结论 |
| 本地模型 | 改 | 生产诊断默认走客户本地 DeepSeek V4 |

验收：

- DBA 能配“日检当前态 + 周检带趋势”，结果仍是 Finding Card 起头的同一套诊断；
- 对某个库告知 ASM 磁盘组后，容量方案能引用该事实；
- 用户要求对比两个时间点时，既能打开原生 AWR/Diff HTML，也能看到变化结论。

### P3｜ADG 演练与平台深化

ADG 切换演练在此作为独立功能启动，不回头改三个入口的诊断主链。

- 选择已有主从环境，生成演练前检查、步骤、恢复检查；
- 永不自动执行 switchover / failover；
- 主机/OS/网络证据、变更/拓扑、飞书静默升级按环境需要再加；
- `ADD DATAFILE` 等存储动作，等 ASM/文件系统余量契约完整后再开放。

## 8. 真实 DBA 工作流如何落到产品

```text
智能诊断 / 告警诊断 / 日常巡检
  → 同一套 Agent 诊断
  → Finding Card
  → 指标分析、趋势对比、根因分析（AWR HTML 保留，按需对比）
  → 解决方案
  → 若允许动手：一条 SQL → 审批 → 执行 → 验证 → 下一条
  → 正式报告（用户显式发起）

日检
  → 勾选当前态检查项
  → 同一套诊断（通常停在方案）

周检
  → 同一检查项加趋势
  → 同一套诊断，分析段看变化

容量
  → Finding（增长/余量）
  → 分析（趋势 + ASM/路径记忆）
  → 方案（观察 / autoextend / 加文件）
  → 允许动手时逐条审批执行

SQL 优化（P2）
  → 输入 SQL_ID / 从 Finding 进入
  → 产品内生成 SQL Monitor 报告 + SQLHC Playbook 在线取证
  → 同一套诊断四段
  → 官方 HTML 作为附件，不是先让用户跑脚本再上传

ADG 演练（P3，独立功能）
  → 选择 HA Group
  → 演练前检查 / 步骤 / 恢复检查
  → 人工执行，系统不自动切换
```

## 9. 明确不做

1. 本期不讨论、不接入 EICC。
2. 不把三个入口拆成三套诊断逻辑。
3. 不取消 AWR/ASH 原生 HTML；分析是叠加，不是替换。
4. 不让 LLM 或浏览器直连数据库。
5. 不把官方脚本原文放进仓库或目标库执行；不让模型当场学习脚本；不安装 SQLT。
6. 不新开第四个“跑官方脚本”入口；SQLHC / SQL Monitor / ExaCheck 都接到现有三入口。
7. 不把“用户跑脚本再上传”套用到 SQL Monitor / AWR / XPLAN / SQLHC；
   只有 ExaCheck / ORAchk / TFA 近端以消费已有报告为主路径。
8. 不把现有 `GV$SQL_PLAN_MONITOR` 行数据当成官方 SQL Monitor 报告。
9. 不自动执行 switchover / failover / restore；ADG 演练不进入 P0/P1。
10. 不支持整批批准多条变更 SQL。
11. 没有磁盘组或文件系统余量事实时，不自动加数据文件。
12. 不为了统一模型丢掉 Oracle 专有字段。
13. 领导视图不加 SID/SQL 细节；DBA 的 Finding Card 不删关键字段。

## 10. 建议的产品叙事

下一轮只讲四句话：

1. 三个入口还是智能诊断、告警诊断、日常巡检，背后是同一套 Agent；
2. 诊断永远先出 Finding Card，再分析趋势和根因，最后给方案；
3. AWR 报告继续生成 HTML，分析时再按需要对比和看变化；
4. 允许动手时，方案之后一次只批一条 SQL，执行完再给下一条。
