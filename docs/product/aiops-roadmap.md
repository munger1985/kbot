# KBot 4.0 AIOps 后续能力 Roadmap

版本：1.0
状态：会议后评估稿
基准日期：2026-09-18
依据：客户沟通纪要 `meeting.txt`、当前 KBot 4.0 AIOps 代码与产品契约、真实 DBA 日常工作流

本文回答三件事：现在已经能做什么、客户真正要补什么、后续按什么顺序改和加。
它不是监控平台建设方案，也不是把会议里提到的脚本全部重写成聊天技能清单。

## 1. 评估结论

客户当前痛点不明显：性能问题在 XD 上线后已经不突出。因此后续不能继续把
“AI 能分析性能”当作主卖点，而要把 AIOps 做成 **DBA 日常工作的受控助手**：

1. 接到告警后，立刻给出可行动的关键事实，而不是一段分析过程；
2. 把客户已经在跑的巡检、告警、演练、容量判断固化成可勾选、可复用的能力；
3. 在“能连 LLM、不能直连 DB”的网络边界下继续诊断，而不是要求前端或大模型碰库。

相对客户现有 EICC / 健康监控脚本，当前 AIOps 的最大短板不是入口数量，而是
**诊断结果的关键信息不完整、不突出**。锁场景是明确对照点：客户现网告警已经能
给出系统名、SID/Serial、用户、SQL_ID、Holder、锁类型、LMODE、CTIME、等待事件、
当前值和阈值；KBot 现在更像先讲调查过程，再给一个偏薄的阻塞链表。

后续竞争力应建立在三层之上，而不是再做一个监控系统：

| 层次 | 客户已有 | KBot 应做成 |
| --- | --- | --- |
| 发现 | EICC、自研巡检脚本、飞书告警 | 接入既有告警，不重复采集 |
| 诊断 | 告警文本 + DBA 经验 + AWR/脚本 | 证据驱动的结构化诊断、AWR/SQL 深度分析 |
| 处置与沉淀 | 人工扩容、ADG 演练、写文档 | 受控建议/审批执行、可勾选巡检、演练指引、领导视图 |

## 2. 当前能力基线

以下只记代码和产品文档已经落地的能力，不把目标态写成已交付。

### 已具备

- 三个业务入口：智能诊断、告警诊断、日常巡检。
- Target 管理：Oracle / MySQL / PostgreSQL；诊断凭据和执行凭据分离。
- 诊断源：Prometheus、Alertmanager、Zabbix、OEM、Loki。
- Oracle 只读诊断目录较完整，已有 51 个 Tool，覆盖实例、会话、阻塞链、等待、
  存储、UNDO/TEMP、归档、复制延迟、无效对象、备份任务、Top SQL、执行计划、
  AWR/ASH HTML、AWR Diff。
- Oracle 受控动作已有表空间 `AUTOEXTEND`/`RESIZE`、杀会话、索引维护、统计信息、
  用户锁定等；`switchover` 仍为 `UNSUPPORTED`，`failover` 仅允许人工命令展示。
- MySQL / PostgreSQL 公开只读诊断只有 6 项：身份、活动会话、阻塞链、存储、长事务、
  复制状态。
- 巡检计划可按日/周/Cron 绑定 Agent，但检查项不可勾选，趋势分析未产品化。
- 正式报告、站内通知订阅已有后台；飞书/Email/ITSM 未交付。
- 对话诊断支持用户补证；控制面与数据库执行器已经分离，但“LLM 网络不能碰库”
  还没有作为客户可验收的部署形态讲清楚。

### 明确缺口

| 缺口 | 现状 |
| --- | --- |
| 诊断关键事实卡片 | 阻塞链 SQL 只有 waiter/blocker SID、用户、事件、等待秒数，缺 Serial、SQL_ID、锁类型、LMODE、CTIME、阈值 |
| 客户告警接入 | 标准入口是 Prometheus/Zabbix/OEM，不能直接吃 EICC/飞书那种分类告警文本 |
| 巡检可定制 | 计划只绑定 Agent 和报告模板，不能按 RMAN、无效对象、归档量等勾选检查项 |
| 容量趋势与记忆 | 只有当前表空间快照；不能记住 ASM 磁盘组/存储路径，也不能据此决定是否扩容 |
| AWR 分析 | 能生成原生 HTML / Diff / ASH，但不能按“过去一周”或两个时间点做结构化对比分析 |
| HA 拓扑与演练文档 | Target 只有 `db_role`，没有主从 ADG 组，不能选择一套环境生成 switchover/failover 指引 |
| SQLHC / ExaCheck | 没有把 Oracle 成熟脚本固化成可绑定环境的 Playbook |
| 多库 Dashboard | 没有库群健康总览，领导视图不存在 |
| PG/MySQL 深度 | 无法覆盖客户告警里的死元组、Autovacuum、Idle 会话、同步延迟、QPS/线程 |
| 外部通知 | 只有站内；客户值班看飞书 |
| 主机/OS/网络 | 指标目录有 host CPU/内存模板，但不是 DBA 工作区里的一等证据 |

## 4. 模块清单：改什么，加什么

### 4.1 必须改动的现有模块

#### A. 诊断结果呈现

现状：对话先输出分析过程，关键字段散落在证据区或被模型摘要稀释。

改动：

- 为锁等待、长会话、DG Lag、等待事件、表空间、长事务定义 **Finding Card**。
- 卡片固定展示：系统/Target、实例、SID/Serial、用户、SQL_ID、对象、当前值、阈值、
  持续时间、等待事件、影响面。
- 分析过程可折叠，不能压过关键事实。
- 告警诊断首页先给出分类统计，再展开每条 Finding，对标客户现网告警格式。

Oracle 锁诊断 SQL 至少补齐：`serial#`、`sql_id`、`prev_sql_id`、`type`、`lmode`、
`ctime`、Holder 当前事件、阻塞链深度。现有 `db.session.blocking_chain` 不够用。

#### B. 告警摄入与 Situation

现状：Prometheus / Zabbix / OEM 是一等入口；客户实际值班看 EICC 和飞书文本。

改动：

- 增加通用 `SignalEvent` 适配：系统名、分类、阈值、当前值、实例、SID、SQL_ID 等
  结构化字段优先，原文只作附件。
- 用显式类别映射，不靠告警文本猜根因。
- 同一系统、同一时间窗的 Lock Wait + Long Session + Event Count 应能并入一个
  Situation，而不是各诊断一次。

#### C. AWR / ASH

现状：能按快照生成原生 HTML、AWR Diff、ASH，但用户仍要自己读报告。

改动：

- 保留原生 HTML，作为不可变证据。
- 新增结构化分析：Load Profile、Top Wait、Top SQL、实例效率、时间模型。
- 支持“最近 7 天”和“两个已确认时间点”对比，结论必须引用快照号和时间窗。
- 未确认快照时只列可见快照，不猜测。

#### D. 巡检计划

现状：选 Agent、周期、报告模板；检查内容由 Agent 临场发挥。

改动：

- 巡检计划增加 **Check Catalog** 勾选。
- 日检默认当前态；周检自动打开趋势窗口。
- 检查失败要落到标准 Finding，而不是一段巡检散文。
- 检查项来自版本化 Tool/Playbook，不允许页面上自由写 SQL。

#### E. 部署与网络边界

现状：执行器已与 API 分离，但客户强调“前端出过事”，验收口径不够硬。

改动：

- 控制面（Portal、Main API、LLM）禁止持有或转发数据库地址/凭据。
- 只有 DB 网内 Executor / Collector 访问库。
- 不能直连时走监控、日志、用户补证，并明确数据缺口。
- 演示和文档都按这套边界讲，不再暗示浏览器或模型能连库。

#### F. Oracle 容量动作决策

现状：已有 `AUTOEXTEND`/`RESIZE`；`ADD DATAFILE` 因缺少 ASM/文件系统余量契约而停在
`PLANNED`。

改动：

- 把存储路径、ASM 磁盘组、余量、命名规则做成 Target 级运维事实，而不是聊天临时记忆。
- Agent 只决定“建议扩、建议 autoextend、还是证据不足”；自动执行继续审批。
- 没有磁盘组/路径事实时，允许聊天写入并经 DBA 确认后固化。

### 4.2 需要新增的模块

#### G. 巡检检查项目录

按客户点名的 Oracle 日/周检项建设，先覆盖高频，再补冷门：

| 分组 | 检查项 | 日检 | 周趋势 |
| --- | --- | --- | --- |
| 备份 | RMAN 备份量、占用空间、最近成功/失败 | 当前 | 需要 |
| 存储 | 表空间余量、数据文件数、增长量、UNDO、行链接、Top Segment | 当前 | 需要 |
| 会话 | 会话数、长会话、锁等待 | 当前 | 可选 |
| 对象 | 无效对象、索引数 > 3 的表、稀疏索引、非系统对象在系统表空间 | 当前 | 需要 |
| 日志 | 归档生成量、审计记录/文件数 | 当前 | 需要 |
| 性能 | 数据文件 IO、关键等待、严重排序 SQL、核心参数 | 当前 | 需要 |

MySQL / PostgreSQL 第一批对齐客户告警：复制延迟、连接使用率、慢查询、死元组、
Autovacuum 停滞、Idle 会话占比、事务回滚率。

#### H. Target 运维记忆

Agent 需要记住的不是闲聊，而是可审计的环境事实：

- ASM 磁盘组、文件系统路径、表空间放置策略；
- ADG 角色、切换窗口、业务允许中断时长；
- 核心应用名与库的对应，例如 `WMSDB225`；
- 巡检例外和已知问题。

写入要可查看、可撤回、带来源（人工确认 / 自动发现），不能只存在模型上下文里。

#### I. ADG 环境与演练文档

新增 HA Group：一套主库 + 备库，而不是两个互不关联的 Target。

用户选择已有 ADG 环境后，生成三类文档：

1. 演练前检查：角色、Gap、apply/transport lag、归档、保护模式、switchover 状态；
2. 演练步骤：只生成固定、版本化命令和顺序，不自动执行 switchover/failover；
3. 演练后恢复检查：新角色、lag、应用连接、回切条件。

文档必须引用当次活检查证据；库不可连时明确缺口，不编造可演练结论。

#### J. SQL 专项诊断工作台

把 SQLHC 的能力固化成界面流程，而不是让模型去“学习脚本”：

1. 输入 SQL_ID 或粘贴 SQL；
2. 采集游标、执行计划、对象统计、ASH、历史 SQLSTAT；
3. 输出计划问题、统计信息过期、等待、绑定、优化建议；
4. 原生报告作为附件，页面主视图是结构化结论。

#### K. ExaCheck 能力包

ExaCheck 不在对话里现场解析脚本，而是预编译成环境级巡检配置：

- 硬件/OS、集群、数据库、存储、网络分组；
- 绑定到 Exadata 环境，而不是单库 Target；
- 结果进入同一套 Finding / 报告，不另做一套 Exadata 产品。

#### L. 库群 Dashboard 与领导简报

Dashboard 服务“很多库”和领导，不替代 DBA 诊断页。

DBA 视图：按库看延迟、锁、长会话、磁盘、OS、探活、未处理告警。
领导视图：风险库数量、容量预警、演练是否过期、巡检覆盖、待审批变更。
表述只保留影响、风险、建议和责任人，不下钻 SID。

#### M. 飞书出站

第一期只把 Situation 阶段结论推到飞书：已确认异常、影响库、诊断状态、下一步。
不把监控原文再转发一遍。静默、升级、值班表放到更后。

## 5. 分阶段 Roadmap

时间按能力包估算，不按人天承诺。Oracle 值班场景优先，因为会议对照样本都在 Oracle；
PG/MySQL 只在同一阶段补客户已经拿出告警样例的部分。

```text
P0  诊断能打过现网脚本     4-6 周
P1  巡检/容量/AWR/演练     6-10 周
P2  专项技能与多库经营     8-12 周
P3  平台深化               按环境需要
```

### P0｜把诊断做成比现网告警更可用

目标：客户用锁、长会话、DG Lag、表空间四类真实告警对比时，KBot 不再输给现有脚本。

| 模块 | 类型 | 交付 |
| --- | --- | --- |
| Finding Card | 改 | 锁/长会话/延迟/等待/表空间关键字段固定展示 |
| 阻塞链与会话 Tool | 改 | 补 Serial、SQL_ID、锁类型、LMODE、CTIME、阻塞链 |
| 通用告警摄入 | 改/加 | 吃 EICC 风格分类告警，映射到 Situation |
| 网络边界 | 改 | 控制面禁库、执行器在库网、补证路径可验收 |
| AWR 两点/一周分析 | 改 | 在已有 HTML 之上输出结构化对比结论 |
| 演示口径 | 非代码 | 不再解释如何造故障，直接进入关键事实 |

验收：用客户提供的锁告警样例走一遍，页面 5 秒内能看到 Holder、Waiter、SQL_ID、
锁类型、持有时间和阈值，而不是先读一段分析。

### P1｜接住 DBA 每周真正在做的事

目标：巡检可配置，容量能判断，AWR 能回顾，ADG 演练能出指引。

| 模块 | 类型 | 交付 |
| --- | --- | --- |
| 巡检 Check Catalog | 加 | 客户点名的 Oracle 检查项可勾选 |
| 周趋势 | 加 | 至少表空间增长、归档量、备份量、会话/锁次数可对比 |
| 运维记忆 | 加 | ASM/路径/放置策略可确认后固化 |
| 容量决策 | 改 | 余量 + 趋势 + 磁盘组事实 → 扩容建议；执行仍审批 |
| ADG Group + 演练文档 | 加 | 选择已有主从环境生成检查/步骤/恢复文档 |
| PG/MySQL 诊断包 | 加 | 对齐客户告警：延迟、死元组、Autovacuum、Idle、连接、QPS |
| 本地模型 | 改 | 生产诊断默认走客户本地 DeepSeek V4 |

验收：

- DBA 能配一份“日检当前态 + 周检带趋势”的计划；
- 对某个库聊天告知 ASM 磁盘组后，后续容量建议能引用该事实；
- 选一套 ADG 环境能生成带活检查证据的演练文档。

### P2｜专项技能、库群和领导视角

目标：单 SQL 和 Exadata 巡检可在界面完成；很多库时领导也能看懂。

| 模块 | 类型 | 交付 |
| --- | --- | --- |
| SQL 诊断工作台 | 加 | SQLHC 风格的单 SQL 诊断 |
| ExaCheck 能力包 | 加 | 按环境勾选检查组，生成巡检计划 |
| Fleet Dashboard | 加 | 多库健康、告警、容量、延迟总览 |
| 领导简报 | 改 | 正式报告增加业务影响摘要，不下钻技术细节 |
| 飞书出站 | 加 | 诊断阶段结论推送，不转发监控原文 |
| Top SQL 日监控 | 加 | 复用巡检/诊断，不新建监控产品 |

验收：对一条生产 SQL_ID 能在同一界面完成采集、计划和建议；领导页能在一屏看到
风险库和待处理容量/演练，而不出现 SID 列表。

### P3｜按环境加深，不抢主路径

- 主机/OS/网络证据成为诊断一等来源，优先消费 EICC 已有数据。
- 探活与可用性作为 Situation 输入，不在 KBot 内再做一套拨测平台。
- 变更/发布/拓扑数据接入后，才能把“最近变更”纳入根因。
- 飞书静默、升级、值班路由。
- `ADD DATAFILE` 等存储动作，等 ASM/文件系统余量契约完整后再开放。
- switchover/failover 永不进入自动执行器。

## 6. 真实 DBA 工作流如何落到产品

```text
值班告警（飞书/EICC）
  → 摄入 Situation
  → Finding Card（锁/延迟/长会话/表空间）
  → 需要时进入智能诊断或 SQL 工作台
  → 建议与审批
  → 同口径验证
  → 站内/飞书同步结论

日检
  → 勾选当前态检查项
  → 异常 Finding
  → 可转入诊断

周检
  → 同一检查项加趋势
  → 容量、归档、备份、对象健康回顾
  → 领导简报

容量
  → 历史增长 + 余量 + ASM/路径记忆
  → 建议 autoextend / 加文件 / 仍观察
  → 审批后执行，再验证

ADG 演练
  → 选择 HA Group
  → 演练前检查
  → 生成步骤（人工执行）
  → 演练后检查与回切指引

SQL 优化
  → 输入 SQL_ID
  → SQLHC 能力包
  → 计划/统计/等待结论
```

## 7. 明确不做

1. 不替代 EICC，不把 KBot 做成 OS/网络/三类库的新监控台。
2. 不让 LLM 或浏览器直连数据库。
3. 不把 ExaCheck/SQLHC 做成“把脚本贴给模型当场学习”；必须预编译为版本化能力包。
4. 不自动执行 switchover / failover / restore。
5. 没有磁盘组或文件系统余量事实时，不自动加数据文件。
6. 不为了统一模型丢掉 Oracle 专有字段。
7. 不以性能压降、准确率或节省工时等未验证数字作为对外承诺。
8. 领导视图不加 SID/SQL 细节；DBA 视图不删关键字段。

## 8. 建议的产品叙事

对外不再强调“我们也能出 AWR”。客户已经认可这一点。下一轮应只讲四句话：

1. 你们现有告警能发现，KBot 负责把锁、延迟、长会话、表空间讲清楚并给出下一步；
2. 巡检项可以按 DBA 习惯勾选，周检看趋势，而不是每次让 AI 自由发挥；
3. 容量、ADG 演练、单 SQL 诊断都能在界面完成，高风险动作仍由 DBA 审批或手工执行；
4. 大模型只在能连 LLM 的网络里工作，数据库访问永远停在库网执行器。
