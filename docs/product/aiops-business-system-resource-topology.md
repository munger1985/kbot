# AIOps 业务系统资源拓扑总体设计

版本：2.0

状态：已确认，作为后续详细设计与实施的产品基线

确认日期：2026-10-14

> 本文替代此前“业务系统 → 组件 → Target”的四步向导设计。旧原型仅保留视觉方向参考，不能再作为领域模型、接口或数据库实现依据。

## 1. 设计结论

业务系统是用户进入运维工作的唯一业务对象。一个业务系统直接关联一个或多个可管理资源，资源之间通过显式关系组成完整拓扑；不再额外建立“组件”“部署单元”“成员”或隐藏分组。

```text
业务系统
├─ 资源：db01、db02、db03、srv01、mq01、lb01、storage01……
├─ 业务系统中的展示属性：架构层、排序、责任组覆盖
└─ 资源关系：组成 RAC、Data Guard、运行于、依赖、连接、使用存储……
```

最终用户可见 Wizard 固定为三步：

1. 业务信息；
2. 系统构成；
3. 拓扑确认。

新增和编辑使用独立工作区页面，左上角有“返回业务系统”，步骤导航属于页面内容，不占用全局菜单栏。列表是大规模资源管理的主入口，拓扑是理解、校验和局部编辑关系的入口，两者操作同一份草稿。

## 2. 设计目标

- 贴近真实运维工作：用户登记“一套核心数据库”“一套应用集群”，而不是理解平台内部 Target、成员键和关系键。
- 面向全栈扩展：一期完整实现数据库，模型同时容纳计算、应用、中间件、网络和存储资源。
- 降低学习成本：不要求用户预先选择“单实例/高可用”，系统依据资源和关系推导架构。
- 避免重复录入：添加数据库时自动发现承载它的物理机、虚拟机、容器或 Pod，并建立关系。
- 适应大型系统：数百或上千资源仍以可搜索、筛选、分页和批量处理的列表为主，画布按需聚合与下钻。
- 保持事实可信：发现结果、用户确认结果和实时观测结果分开；RTO/RPO 已填写不等于数据保护已覆盖。
- 支持跨专业协作：业务系统、单个资源和关键关系可以由不同责任组负责。

## 3. 核心概念

### 3.1 业务系统

业务系统表示一套需要共同保障的业务能力，例如 MES、核心交易、电子展厅。它保存名称、系统编码、环境、重要级、业务责任组、说明和生命周期状态，不保存数据库版本或部署形态。

系统编码由 Tenant 控制台中的业务编码策略生成，默认格式为 `SYS-xxxxxx`。编码有业务可读性、创建后不可修改；UUID 始终作为内部主键，不向用户暴露。

### 3.2 资源

资源是实际被监控、诊断、执行或用于解释拓扑的对象，例如数据库实例、物理服务器、虚拟机、容器、Kubernetes 集群、应用服务、WebLogic、消息队列、交换机、负载均衡和存储设备。

稳定资源拥有平台生成的业务编码和技术责任组；默认编码示例为数据库 `DB-xxxxxx`、服务器 `SRV-xxxxxx`。Pod、容器、进程等短生命周期发现资源可不分配业务编码，但始终拥有内部 ID、来源和生命周期状态。

资源可被多个业务系统引用。停用业务系统不能级联删除或停用共享资源。

### 3.3 架构层

架构层是资源在“当前业务系统”中的展示与编排位置，不是资源类型，也不是新的父子层级。默认层为：

1. 接入层；
2. 应用层；
3. 中间件层；
4. 数据层；
5. 基础设施层。

无资源的层自动隐藏，“未归类”是系统临时视图而不是正式层。一个资源在同一业务系统内只有一个主要展示层；同一共享资源在不同业务系统中可以位于不同层。

默认归层规则：

- 负载均衡、反向代理、API 网关优先进入接入层；
- 应用服务及专属承载服务器进入应用层；
- 消息队列、应用服务器软件、集成平台及专属承载服务器进入中间件层；
- 数据库、数据仓库、缓存及其专属服务器和存储进入数据层；
- 被多套能力共享的虚拟化、Kubernetes、SAN、共享主机和共享存储进入基础设施层。

自动归层只是建议，用户可以调整；调整不改变资源身份、监控绑定、责任组或资源关系。

### 3.4 资源类型

资源类型回答“它是什么”，与架构层正交。应用服务器软件可以属于“中间件”类型，但在某业务系统中展示于应用层；数据库服务器仍是“服务器”类型，但可展示于数据层。

类型目录按运维语义组织并支持搜索、逐级展开和后续扩展，不在页面中平铺固定枚举：

| 资源域 | 典型类型 |
| --- | --- |
| 数据平台 | 数据库、数据仓库、缓存 |
| 计算资源 | 物理服务器、虚拟机、容器、Pod、Kubernetes 集群 |
| 应用与服务 | 应用服务、后台任务、批处理服务 |
| 中间件 | 应用服务器、消息队列、集成平台、API 网关 |
| 网络设施 | 网络设备、负载均衡、DNS、防火墙 |
| 存储设施 | 块存储、文件存储、对象存储、SAN |

### 3.5 资源关系

关系是有类型、有参与者角色的领域对象，不只是 `source → target` 二元连线。一个关系可以有两个或多个参与者：

- RAC：`db01`、`db02` 都以 `MEMBER` 参与；
- Data Guard：`db01`、`db02` 以 `PRIMARY` 参与，`db03` 以 `STANDBY` 参与；
- 运行承载：数据库以 `WORKLOAD`、服务器或容器以 `HOST` 参与；
- 使用存储：数据库或服务器以 `CONSUMER`、存储以 `PROVIDER` 参与。

RAC + DG 由一个 RAC 关系和一个 Data Guard 关系共同表达，不创建组合枚举或隐藏集群对象。部署形态、主备结构、版本分布和高可用标签均从资源及关系推导。

关系表是唯一事实源。Oracle 26ai 在关系表上建立 Property Graph；PostgreSQL 一期通过递归 CTE 查询，未来确有必要时可引入 Apache AGE。禁止关系表与 Graph 双写。

## 4. 业务系统示例

MES 业务系统可以直接包含：

```text
接入层
  lb01、lb02

应用层
  mes-app01、mes-app02、mes-app03
  srv04、srv05、srv06

中间件层
  mid-01、mq01、mq02
  srv07、srv08

数据层
  db01、db02（RAC）
  db03（Data Guard Standby）
  srv01、srv02、srv03、storage01

基础设施层
  vm-cluster01、san01
```

关系把这些资源串联为完整拓扑：`db01 + db02` 组成 RAC，`db03` 是 Data Guard 备库，数据库分别运行于对应服务器并使用存储，应用依赖中间件和数据库，负载均衡转发到应用服务。从任一节点都能在同一业务系统范围内查询邻居、上下游和路径。

## 5. Wizard 总体交互

### 5.1 Step 1：业务信息

用户填写：

- 业务系统名称；
- 环境；
- 重要级；
- 业务责任组；
- 可选说明和标签。

系统编码只展示生成规则和保存后的预览，不提供输入框。页面采用清晰的业务信息区、责任治理区和说明区，不堆叠无分组控件。

### 5.2 Step 2：系统构成

左侧按架构层显示资源数量、校验状态和未归类项；主区域提供资源列表、关系摘要和场景化“添加”入口。用户看到的是“添加数据库”“添加应用服务”“添加中间件”等，不出现“添加 Target”。

一期添加数据库的完整路径为：

```text
选择“添加数据库”
→ 选择新接入、复用已有资源或从监控源导入
→ 输入一个数据库入口和凭据引用
→ 后台发现数据库事实、RAC/DG 成员及 Host/VM/Container/Pod
→ 展示资源与关系识别结果和证据
→ 用户补充未能自动发现的入口，确认或纠正角色、责任组和架构层
→ 把资源、关系和监控绑定写入同一份 Wizard 草稿
```

用户只输入一次。自动发现出的服务器不要求再走一次“添加服务器”；发现与现有资源匹配时提示复用，身份不确定时禁止自动合并。数据库版本是资源属性，允许后续升级；部署形态是推导结果，增加 RAC 节点或 DG 关系后自动变化。

应用、中间件、网络和存储沿用相同交互模式；一期未实现的接入器显示明确的能力说明和“后续开放”，不能进入无效表单。

“一套核心数据库”等接入批次只用于帮助用户完成本次操作，不持久化为新的组件层。保存后，列表可按关系、类型、架构层、站点、责任组和状态聚合展示。

### 5.3 Step 3：拓扑确认

系统从 Step 2 草稿自动生成分层拓扑：

- 架构层使用横向或纵向泳道；亮色主题白底，暗色主题深色底；
- 默认聚合 RAC、DG、应用集群等关系，展开后显示有限数量成员；
- 点击节点显示资源详情和一跳邻居；双击或“下钻”按深度加载局部子图；
- 可拖动资源调整架构层，可通过关系编辑器新增、修改或删除关系；
- 所有画布操作同步回写同一草稿，资源列表和校验结果立即更新；
- 超大系统不一次渲染全量节点，默认加载架构摘要和当前焦点子图。

提交前检查资源身份冲突、未归类资源、责任组缺失、关系参与者和角色约束、禁止的环路、连接状态、监控绑定及待确认发现结果。警告可以带理由提交；阻塞项必须修复。

## 6. 自动发现与人工确认边界

自动发现可以生成候选资源、候选关系、建议层级和观测事实，但不能把推测直接当成用户确认的目标拓扑。每项发现记录来源、证据时间、置信度和确认状态。

- 高置信度且身份唯一：默认勾选，仍在确认页可见；
- 身份可能与已有资源重复：要求用户选择复用或新建；
- 无法访问远端成员：允许用户补充另一个入口继续发现；
- 发现角色与已确认角色不一致：标记偏差，不静默改写；
- 临时 Pod/Container：默认作为发现态资源，可按生命周期自动更新，但不能越权修改稳定资源身份。

## 7. 责任、编码与数据保护

责任分三层：业务系统责任组负责整体业务影响，资源技术责任组负责资源生命周期，业务系统—资源关联可以覆盖本系统中的协同责任；复制、专线等关键关系可单独指定责任组。普通场景使用继承值，只有需要时才展开覆盖设置。

业务编码策略位于 Tenant 控制台。用户只能看到生成结果和规则说明，不能输入主键、关系键、成员键、站点代码或其他技术标识。

备份与恢复继续作为独立业务域，不进入建档 Wizard。保护计划关联一个或多个数据库资源，并根据 RAC/DG 关系推导候选执行节点；RTO/RPO、备份计划、运行结果、恢复审批和演练证据在数据保护模块维护。只有满足已配置策略、近期成功备份和恢复验证等真实条件时，才可显示“已覆盖”。

## 8. 页面与导航

- 主导航只保留“业务系统”，不并列暴露“资源”“Target”或“成员”菜单。
- 目录页使用全局卡片样式；新增入口是同尺寸“＋ 新增业务系统”卡片。
- 卡片显示系统名称、编码、环境、重要级、责任组、资源规模、推导架构和真实健康摘要；不重复显示“组件数 + 实例数”。
- 详情页先显示业务概览和分层拓扑，再提供资源、关系、监控、数据保护和审计等标签页。
- 实时监控选择器使用“业务系统 → 架构层/类型筛选 → 资源”，界面不再要求用户理解 Target。

## 9. 大规模系统原则

- 资源列表使用服务端搜索、筛选、排序、游标分页和批量操作；
- 拓扑查询必须支持焦点节点、方向、关系类型、最大深度和节点预算；
- 默认只返回摘要、聚合节点和一跳邻居，禁止浏览器无上限加载全量图；
- 关系编辑按单个命令增量提交，不再用全量 PUT 替换整个拓扑；
- 节点和关系均使用乐观锁，冲突时展示具体变化并允许重新应用；
- 所有查询强制包含 `business_system_id` 和可信 Tenant/Domain 范围，禁止跨业务系统路径泄漏。

## 10. 一期范围与非目标

一期完整实现：

- 业务系统三步 Wizard；
- 数据库资源接入、已有数据库复用和监控源导入；
- Oracle RAC/Data Guard、MySQL 复制、PostgreSQL Streaming 等数据库关系；
- Host/VM/Container/Pod 的自动发现和承载关系；
- 分层资源列表、局部拓扑、关系编辑与节点下钻；
- 现有监控、诊断、巡检和数据保护从资源映射到内部数据库 Target。

一期不实现：

- 自动创建 RAC、Data Guard、复制、服务器或中间件；
- 完整 CMDB、IPAM、机房容量或配置合规管理；
- 浏览器一次性展示全量大图；
- 把应用、中间件、网络和存储占位误标为已具备自动发现能力；
- 把 Graph 作为第二套事实库或引入双写。

## 11. 设计验收

- 用户无需选择单实例/高可用，架构标签可由资源关系稳定推导；
- 用户新增数据库只录入一次，确认页同时看到数据库、承载环境及关系；
- 页面和公共合同不暴露 `target_key`、`component_key`、`member_key`、`relation_key`、`site_code`；
- 同一资源可安全加入多个业务系统，且在每个系统中只有一个主要架构层；
- 任一节点可在同一业务系统范围内完成邻居、上下游和路径下钻；
- 列表与拓扑修改的是同一草稿，不存在两份拓扑事实；
- 数百至上千资源时列表可正常管理，拓扑按预算加载；
- 数据保护状态不因填写 RTO/RPO 自动显示为“已覆盖”；
- Ammolite 与 KBot 的业务语义、合同和状态一致，差异只存在于 PostgreSQL/Oracle 和前端技术适配层。
