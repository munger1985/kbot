# AIOps 运维工作、报告与知识资产设计

确认日期：2026-11-03。状态：本次代码实施与本地回归已交付，真实环境测试由用户手动执行。
部署、模型／KC／通知的真实闭环及检索质量尚未验收；本地已知配置页视觉差异见修改计划第 6.23 节。
适用于 Ammolite Cube 与 KBot4；两仓产品语义一致，平台、数据库和前端实现允许必要差异。
具体代码基线、缺口、实施顺序和验收见[修改计划](../operations/aiops-output-jobs-implementation-plan.md)。
案例在通用 KC 上的业务适配见[案例入库与检索定制设计](../proposals/aiops-diagnosis-case-knowledge-design.md)。

## 1. 设计结论与适用优先级

按“工作入口 → 正式成果 → 可复用知识”组织产品，不再将报告、诊断历史、案例和上传资料混为一类。

本文件是本次菜单、业务归属和会话异步产出的已确认规范。与旧文档中“报告与知识”分组、
“历史诊断案例／运维知识”页面命名、同步等待出报告及立即跳转的目标约定冲突时，以本文为准。
既有调查证据、正式报告冻结、专业巡检、案例来源复核、脱敏、审核、撤回和权限规则累积适用，
不因整理菜单而放宽。文档确认不表示相关代码已交付。

## 2. 四类业务对象

| 对象 | 回答的问题 | 业务职责 | 不代表什么 |
| --- | --- | --- | --- |
| 巡检记录与报告 | 检查了什么，发现哪些异常和风险 | 执行检查、发现风险、评价状态和留痕 | 执行完成不等于数据库健康，也不等于问题已解决 |
| 诊断会话与报告 | 针对问题查到了什么，建议、实际处置及验证分别是什么 | 调查协作、方案、处置记录与正式复盘 | 诊断结束或报告就绪不等于已实施或已恢复 |
| 诊断案例 | 本次经历有哪些值得下次借鉴的经验 | 经提炼、脱敏和审核后复用的检查路径、措施、效果和限制 | 历史会话或报告不自动成为案例 |
| 运维资料 | 按规范或技术文档应该怎样理解和操作 | 手册、SOP、厂商文档、架构及实施资料 | 文档描述不证明当前环境事实，也不授予执行权限 |

巡检负责发现和评价，不承担问题处置闭环。报告可以记载建议和真实关联处置，但不能把建议写成已执行。
巡检发现需要继续调查时，继承其目标和证据进入 Agent 工作台；后续调查不原地改写已冻结巡检报告。
报告用于汇报和归档，案例用于未来复用；同一调查可分别产出二者，无先后依赖。
历史会话继续在 Agent 工作台查看，不再用“案例库”泛指全部诊断历史。

## 3. 导航结构

~~~text
Agent 工作台                         固定首位，保持应用默认主入口

运维工作
├─ 运维总览
├─ 实时监控
├─ 告警诊断
├─ 数据库巡检
└─ 恢复演练

报告中心                             单独直达项，不增加同名父分组

知识资产
├─ 诊断案例库
└─ 运维资料库

配置与治理                           内容、顺序、路由、权限和配置行为不变
├─ 业务系统
├─ 监控源
├─ 责任组
├─ 运维知识库
├─ Agent 管理
├─ 模板中心
└─ 运行记录
~~~

- Agent 工作台是诊断、知识问答和继续已有调查的统一入口，不新增平行聊天页。
- 合并原“态势与事件”“巡检与演练”为“运维工作”；拆开原“报告与知识”。
- “运维报告”更名“报告中心”；“历史诊断案例”更名“诊断案例库”；“运维知识”内容页更名“运维资料库”。
- 现有报告、案例和资料路由保留，不为改名增加重复路由或第二套页面。
- 配置区的“运维知识库”继续负责库及解析模型等配置；“运维资料库”负责内容、审批和发布，不复制配置页。
- 只读浏览、生成、审核及配置权限仍按现有角色边界执行，不以菜单变化自动授予权限。
- 复用现有导航样式和分区交互，不开展新的视觉风格设计；报告中心需要真正的单独直达项。
- 菜单、页面标题、面包屑和无菜单详情页归属来自同一导航定义。两个前端语义一致，其他 App 不受影响。

## 4. 页面职责

### 4.1 数据库巡检

页签采用“巡检记录／巡检计划”。巡检记录按批次展示来源计划、执行范围、进度和失败原因；
进入批次后选择数据库查看正式报告。同一份报告与报告中心共用 Report ID、版本和冻结正文，不另造简版报告。
巡检计划不新增侧栏入口，沿用当前页内管理方式。

### 4.2 报告中心

提供“全部／巡检报告／诊断报告／专项分析报告”筛选；生成任务和正式报告分区展示，失败任务不得伪装成空白报告。

- 巡检报告：日常检查以及真实闭合周期的汇总，继续遵循专业巡检规范。
- 诊断报告：会话或告警调查的正式记录。
- 专项分析报告：Workload、Activity、前后对比及外部工具分析等，按实际报告类型归类。
- 分类使用明确合同映射，不通过标题关键词判断；保留已有细分 report_type。
- 查询使用 category（INSPECTION／DIAGNOSIS／SPECIAL_ANALYSIS）；“全部”不传分类。
  六种 INSPECTION_* 属于巡检，INCIDENT／PERFORMANCE 属于诊断；
  COMPARISON、三种数据库的工作负载／活动／SQL 健康检查及 pgBadger 属于专项分析。
  分类、精确 report_type、template_ref 和 Target 是交集，必须在服务端过滤后再分页。
  游标绑定当前业务空间、调用身份和全部筛选条件，切换条件回到首页，不能复用旧游标。
- 正式报告每页最多 50 份，显示“本页”数量而非伪造总量；生成记录独立读取与计数。
  任务完成后刷新当前筛选的报告首页；结果不符合当前筛选时，仍可从任务链接打开确切报告。
- 原生 AWR／ASH 等工具附件仍可作为证据，不因存在文件就自动成为一份 Agent 诊断报告。
- 报告保留模板和来源版本、完整度、证据边界、处置与验证状态及来源会话／Run。
- 提供预览、下载、版本追溯和继续诊断入口；报告中心不是 Agent 自动检索的知识库。

### 4.3 诊断案例库

展示提炼任务、案例草稿、待审核和已发布版本，不复制所有会话和报告。
保留四类用途：排查参考、已验证处置、优化经验、失败教训；不再新增四套独立库。
案例突出问题、环境、诊断路径、措施、实际效果、适用条件、禁忌和未决问题，原调查与报告通过来源链接追溯。
同一问题多轮归并有效判断，不按每轮回答自动新增案例。未验证经验不能被手工改标签升级为已验证处置。
发布、拒绝、退役、来源更正、复用反馈及精确版本撤回继续使用既有治理规则。

案例不是报告 PDF 的副本。基于现有案例 Profile，定制问题与环境、实际排查路径、支持与反证、
措施与效果对应、适用边界和失败警告，编译成脱敏正文及结构化知识投影，再复用 KC 入库、
结构解析、词法／向量检索与精确引用。不得把业务事实判断或 VERIFIED 判定下放给 KC。
“已登记／处理中”“索引就绪草稿”“已发布可检索”分别显示；草稿有索引不表示进入 Agent 检索。
检索只使用当前授权的确切发布版本；命中措施时同时带出前提、效果和禁忌，而非只返回裸命令。
详细结构、版本、检索候选范围与验收以专项设计为准，不重建解析器或案例专属聊天系统。

案例被检索到后，还须核对当前 Target 的环境与案例前提／禁忌，明确展示“相符、冲突、未知或禁用”。
自然语言判断使用当前 Agent 已配置的规划模型，不增加配置表单；不可核验时显示未知。
即使案例整体已验证，缺少单项效果证据的措施仍不可当作当前处置推荐；失败教训只作为警告。
检索结果和引用均保留这些边界，历史经验不构成当前现场证据，也不授予执行权限。

### 4.4 运维资料库

管理上传的手册、SOP、厂商文档、架构说明和实施规范，保留现有审批、解析、版本和发布流程。
与案例在业务上分开，但共享 KC 解析、检索、精确引用及通用治理能力，不新建另一套检索引擎。
分类依据内容用途而非仅依据来源：上传的事故复盘可以经独立核验形成案例候选，诊断中总结的通用 SOP
也可以经独立整理审核形成资料；不能因上传或生成而自动改变知识性质或信任等级。
上述跨类型整理是分类原则，本批不额外承诺新增一键转换入口。

### 4.5 两类知识的共同使用方式

“案例库”和“资料库”是业务分类，不是两套独立 KC 或向量库。资料定制回答“规范怎么要求”，
案例定制回答“类似问题过去怎么排查、实际效果及限制是什么”；不能只改显示名称、沿用同一套提取规则。
Agent 通过现有知识来源开关和授权范围使用其中一类或两类，结果标明来源类型、确切版本和适用差异。
资料与案例冲突时分别呈现依据与限制，不把历史成功经验升级为规范，也不当作当前环境已验证事实。
固定案例资源、Domain 绑定与显式模型配置在现有配置／初始化体系内解决，不新增配置菜单或让用户选择技术 Collection。

案例入库不是生成后的可选“上传附件”，而是“沉淀案例”后台任务的一部分：提炼并脱敏 →
生成案例专属知识正文及关联清单 → 复用 KC 受理、解析、索引与精确引用 → 草稿就绪后通知。
人工发布是下一步独立治理操作；只有确切发布版本才能被后续诊断检索。
资料的规范／操作卡提取与案例的检查／措施／效果提取分别维护，不把资料审批流程原样套给案例。
检索结果须能说明“哪里相似、当前环境有何不同、原措施是否实际执行、效果如何、哪些情形不能用”，
不能只返回相似度、根因摘要或一条命令。配置区原七项及现有表单保持不变，
缺少案例资源或模型时明确说明前置条件，不在生成请求内自动建库或借用模型。

正文检索在授权和发布门禁后联合排序，不固定“手册优先”或“最新案例优先”。
以正文相关性为主，当前适用性、证据结构、验证关联、用途和版本年龄只作有界重排，
结果附可解释评分卡；首版工程策略及其尚未完成的真实质量验收见专项设计第 7.3 节。

## 5. 会话中的两个独立操作

选中已有会话时，在同一操作区保留“生成报告”和“沉淀案例”两个入口。
只有全部轮次均已结束且至少存在一项 COMPLETED／PARTIAL 结果时，才具备提交产出的基本来源资格；
WAITING_USER 仍在等待补充，不属于产出终态，不能因最新轮次完成就忽略较早的活动轮次。
空会话、只有失败／取消记录、仍在运行或等待补充、当前权限不足时禁用入口并显示具体原因。
按钮再分别按报告／案例来源资格与既有权限启用，案例来源核验或某类提交繁忙不阻断另一类操作；
前端条件只负责解释，服务端仍复核实际来源、权限和最终资格。

| 操作 | 用户确认内容 | 后台输出 | 页面落点 | 完成含义 |
| --- | --- | --- | --- | --- |
| 生成报告 | 来源范围、报告模板及确切版本 | 正式诊断报告 | 报告中心／报告详情 | 报告已保存，可以查看；内容可能有明确缺口 |
| 沉淀案例 | 有效轮次、归纳、实际处置、效果来源和适用限制 | 脱敏并处理就绪的案例草稿 | 诊断案例库／指定案例版本 | 草稿可完善和送审，不是已发布知识 |

两者独立提交、独立任务、独立结果和独立重试。既不强制先出报告，也不因沉淀案例而关闭或禁止继续会话。
现有“诊断收口”里的处置登记与人工反馈字段可以保留在案例确认流程中，但不得暗示问题已经解决。
报告仅冻结既有授权材料，不暗中发起新的目标库调查；需要补充取证时另行明确发起。
报告与案例共用不可变调查来源，不能通过彼此循环引用提升证据强度。

## 6. 异步任务与通知闭环

~~~text
确认操作
  → 同一业务事务保存任务、冻结输入和待执行领域事件
  → 返回任务回执，会话及对应页面立即可查
  → 后台认领、重验来源与权限、分阶段处理、保存结果
  → 原子登记终态和结果通知事件
  → 通知中心投影并提醒发起人
  → 直达确切报告、案例版本或失败任务
~~~

1. 提交接口返回 202 与持久化任务 ID；只做必要授权、资格、输入冻结和排队，不等待模型、KC 或文档装配。
2. 页面提示“已提交，可离开页面”。切换菜单、关闭浏览器或 API 进程结束都不应丢失任务。
3. 输入冻结到提交时的来源及版本；后续新轮次不静默纳入。来源被撤回、更正或撤权时必须重验，
   不能用冻结快照绕过现时授权。需要新范围或新输入时创建新任务。
4. 一次输出任务有独立身份，不能把来源 Run ID 当作所有报告和案例的统一任务 ID。
5. 报告中心与案例库提供生成记录，包括排队、阶段、时间、失败原因、重试及结果链接。
   尚无正式产物时只显示任务，不创建假的空白报告或已完成案例。
   会话可用可折叠任务摘要保留问答空间；摘要与列表均从持久化任务恢复，不依赖本地计时或内存。
   案例结果必须定位指定 asset/version；同页跳转也重读该版本，不因新修订出现而改看最新版本。
6. 案例需等待来源核验、脱敏及必要 KC 处理完成并进入可完善草稿状态后，才能发送“案例草稿已生成”。
   KC 仅受理不等于草稿已就绪；人工发布审核不属于这次生成任务的完成条件。
7. 完成和失败均通知发起人；案例送审后才按既有权限创建审核待办。进度更新不反复产生提醒。
8. 成功通知直达确切报告或案例版本；失败通知直达任务记录。进入目标页重新鉴权并恢复正确业务空间。
9. 业务状态和通知 Outbox 事务一致；通知消费失败可重试，不能重跑已完成生成或删除产物。
10. 通知中心是投影和提醒，不是业务任务真相；页面可独立读取任务状态。无需新增 AIOps 任务中心侧栏入口。
11. 输出事件以业务来源版本排序，不以到达时间或系统时钟推断重试；低版本不得覆盖新状态。
    对账使用真实 SERVICE 身份读取最小任务快照，再按发起人的当前授权核验；
    写回校验观察到的投影版本，慢响应不能覆盖并发新事件。同版本终态通知仍可投递，避免对账先行造成漏报。

## 7. 状态、幂等与可靠性

| 维度 | 表达规则 |
| --- | --- |
| 输出任务 | 排队中、处理中、已完成、失败；阶段单独记录 |
| 报告内容 | 沿用 READY／PARTIAL 等内容合同，不用任务成功掩盖证据缺口 |
| 案例治理 | 草稿、待审核、已发布、拒绝、退役等，与生成状态分开 |
| 处置与验证 | 未实施、实际执行、效果未知／已验证等，不能从报告或审核状态推定 |

任务处理成功而报告为 PARTIAL 时，保留“已完成＋报告有缺口”，通知明确提醒，不混淆任务失败。
“审核通过”仅表示允许发布，“用户反馈恢复”仍是人工来源，不自动授予 VERIFIED。

任务请求带幂等键，按 Domain、发起人、任务类型和来源划定作用域；同一作用域内相同键不同输入拒绝，
相同授权范围和冻结输入的重复提交复用任务或可用结果。受理时间及预分配产物 ID 不作为业务输入变化。
报告和案例具有不同幂等空间，不得互相合并。重放、重试、租约回收和过期 Worker 回传都须防重复产物、
防旧状态覆盖新状态；外部 KC 已受理结果要保存确切版本后恢复处理，不重复上传。
重试区分临时故障与不可重试的权限／来源／输入问题，保留尝试和失败记录。
后台执行使用当前可信授权，不持久化浏览器令牌、API Key 或过期内部 JWT，不借系统身份扩大权限。

## 8. 范围与验收边界

本次包含菜单、页面归属、两个会话操作的真实异步化、持久化任务查询、通知直达和对应页面输出。
同时包含案例在现有 KC 之上的知识投影、入库对账、发布资格、检索与引用定制；
不是仅将案例列表改名，也不是把生成结果上传成功就视为知识复用闭环。
报告详情现有“提炼案例”等同类入口应复用同一后台机制；其他独立 Workload、Activity、pgBadger
生成或导入流程不因本批自动扩大为全量异步改造。
报告详情的“沉淀案例”同样只返回任务回执，保留报告阅读位置，结果在案例库生成记录中查看。
纯标题／版式修订或报告引用了已有会话收口案例时，可复用已验证来源的确切案例版本；
复用不改写原案例的请求身份、来源指纹、治理状态或 KC 索引，不将“任务已受理”提示成“草稿已生成”。
配置区、Agent 配置流程、Target 权限、诊断执行、巡检调度和专业报告内容规则保持原边界。
不重写历史报告，不自动将历史会话或旧自由文本回填成案例，不新增平行聊天或解析系统。

验收需覆盖：两操作互不依赖；离页及进程恢复；重复提交和事件重放；冻结来源后继续会话；
来源更正及撤权；失败记录与重试；PARTIAL 报告；案例处理完成但未发布；输出保存后通知；
通知积压与深链鉴权；两个前端同语义；配置菜单及权限零变更。
案例须真实验证生成、KC 处理、草稿通知、人工发布、新会话检索、精确引用及撤回后阻断的闭环。
代码与本地替身测试、真实持久化、模型／KC 和浏览器端到端验收必须分别记录。
