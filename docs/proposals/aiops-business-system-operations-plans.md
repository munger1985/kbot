# 业务系统驱动的运维计划设计

状态：已确认；2026-11-02。Ammolite 与 KBot4 同步采用本设计。本文覆盖巡检计划实施，备份执行只定义边界，不在本次实现。

## 归属与入口

业务系统是运维对象，计划属于一个业务系统；Agent 是可替换执行者，其授权不是计划范围来源。一个系统可以有多份巡检/备份计划，一份计划只属于一个系统。创建顺序为：业务系统 → 全部纳管数据库预览 → 检查模板、调度周期 → 授权且具备能力的 Agent。

业务系统详情提供运维计划/执行记录入口；日常巡检保留跨系统总览，允许先选系统创建计划。报告读取仍遵循 aiops:use，不要求资源配置权限；计划变更要求 aiops:plan_manage。资源配置与计划操作分区，Agent 管理页不承担计划主入口。

## 范围与授权

计划持久化必填 business_system_id；创建、编辑、启用均校验租户/域、系统状态、Agent 启用与主动诊断能力、对该系统的授权以及模板对系统数据库的覆盖。系统归属创建后不可变，需要调整时新建计划，不把历史批次转移到另一系统。

每次启动批次，从该系统登记的纳管数据库解析执行范围，按逻辑 Target 去重；RAC 不按节点重复执行。不借 Agent 的其他系统扩大范围，也不取权限交集后静默漏库。已停用的系统资源不执行；仍在纳管范围但缺少 Target、Target 被停用或资源配置不完整时明确阻止批次，并列明资源，不静默丢弃。连接不可用或凭据失效由各目标实际执行失败呈现，其他目标可继续。零数据库不算成功。

只读巡检默认动态纳入新增数据库。批次进入执行时冻结业务系统身份/名称、资源与 Target 清单、Agent 版本、模板版本和执行窗口；排队期间尚未启动的批次在真正启动时冻结。批次执行期间资源变更不增减已冻结清单；重试不重新展开范围。执行时重验授权，撤权不能扩大权限或静默缩小目标清单。

## 批次与报告

一个系统批次形成多个数据库目标运行，记录预期目标清单以及完成/失败数。未形成运行的目标计入失败，报告缺口不能改变已成功执行的运行状态。页面分别显示执行完成度、报告完整度、数据库健康，不能互相代替。

批次详情是执行事实聚合，不另做报告渲染；每个数据库通过 report_id 打开与运维报告相同的正式报告/PDF。展示当前动态范围预览及本批次冻结范围，新增/排除资源可通过相邻批次目标清单追溯，历史报告不回写重算。

## 批次结果页阅读流程（2026-11-02）

日常巡检“查看批次”打开独立结果页。页面分为批次总览、数据库执行清单、当前数据库结果三个层次；宽屏为清单与结果双列，窄屏上下排列，内容使用页面自然滚动，不把结果塞入抽屉或独立滚动窗。

总览分别展示数据库目标数、执行完成数、失败数、已关联正式报告数及批次时间，不把执行成功表述为数据库健康。数据库清单以本批次冻结范围为基础，按 Target 去重，优先使用冻结名称与类型，补充真实运行；冻结目标缺少 Run 时保留入口并明确标记“未生成运行”，不静默遗漏。历史批次未冻结范围时只展示已有运行，不用当前资源补造历史。

选择数据库后展示该库执行状态、报告状态、失败原因及取证质量；零覆盖率与未记录分别展示，未知状态不使用成功样式。主操作“查看报告”仍打开运维报告的同一正式报告页面；无报告则说明未形成报告，不展示空白报告。深入诊断是当前库的后续操作，保留来源 Run，不能篡改正式报告。URL 保留当前目标/运行，刷新及从报告返回时恢复选择；批次编号、计划编号和冻结/排除清单收入可展开的审计信息。

验收覆盖：完成、部分完成、运行中、失败、全部或部分缺少运行、零/缺失覆盖率、未知状态、长名称与长错误、历史无冻结范围，以及数据库切换、键盘操作、刷新选择保留、正式报告跳转、深入诊断来源与 320px 窄屏。两端使用同一隔离数据浏览器对照，不创建线上计划或触发真实执行。

## 备份计划边界

未来备份计划复用系统归属、授权、调度、批次和审计概念，不复用巡检执行器。备份检查是只读取证；备份执行需要数据库适配、写操作授权、目的地、保留/加密策略、审批、恢复验证与并发隔离。新数据库未经备份策略确认不自动执行备份。本次不添加占位备份计划接口或推测性通用调度框架。

## 实施与验收

同步公共/内部合同、Entity、规范 Schema、初始化工件、仓储、应用服务、调度、前端和测试。只使用新规范，不保留按 Agent 展开所有系统的兼容路径，不从旧 Agent 权限猜测计划系统归属；旧计划的归属必须由用户确认，历史批次/报告保持原事实。本次不执行线上 Schema 变更、数据回填、服务拉取/重启或真实巡检。

必须覆盖：Agent 同时有 ERP/WMS 授权时 ERP 计划只执行 ERP；换 Agent 不换范围；跨租户/域与撤权拒绝；新增库下一批纳入、重试范围不变；停用/未建 Target 不静默遗漏；混合数据库模板覆盖、逻辑 Target 去重；目标失败和缺少 Run 正确汇总；系统入口与日常巡检入口复用计划表单、标准报告入口。两边独立验证，不用一边通过替代另一边。


## 本次落地与上线前置

已同步实现：系统归属合同与持久化字段、系统数据库范围解析、Agent 授权与能力门禁、调度投递、批次冻结清单与缺失运行汇总、系统详情入口、系统优先计划表单和标准报告链接。备份执行不在已实现范围。

这是必填字段的规范变更，不是可直接覆盖旧数据库的纯代码更新。Ammolite 的 ORM 初始化器只为新表创建规范结构，不会替已有表新增列；KBot4 的 Oracle 规范版本为 54，并已同步全量/保留来源目标的重建工件及部署校验工件。重建工件不等于无损升级脚本，不能为了补列在承载历史计划和报告的数据库上直接执行。

上线前必须先备份并由用户逐项确认旧计划归属，再批准明确的数据库切换方案；不得推断系统归属，不重写历史批次、报告或伪造历史冻结范围。上线验收需在批准的目标环境核实实际数据库结构、启用计划与授权，再执行受控巡检验证三库结果。本轮只更新代码及规范工件，未执行线上 DDL、回填、重建、服务拉取或重启。
