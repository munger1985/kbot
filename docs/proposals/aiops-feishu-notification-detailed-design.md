# AIOps 飞书通知接入详细设计

## 2026-11-06 配置边界修订与实施计划（当前规范）

本节替换下文历史实施记录中的 TOML 外发启停、public_origin 和相关部署门禁。现阶段使用标准飞书，OpenAPI／OAuth 默认使用官方地址。支持无外网 OP 部署经企业网关转发：token_url 和 message_origin 是仅部署管理员维护的 TOML 技术配置，不放入租户页面或数据库；允许明确配置 HTTPS 网关，不自动发现、不跟随重定向，不引入专有飞书协议。企业微信和专有部署协议不在本次范围。

1. 渠道 App ID、加密 Secret、启停继续存数据库；新增独立通知公共设置保存门户 HTTPS Origin。Ammolite 按 Tenant、KBot 按全实例，不按 Domain，不在各厂商连接上重复保存门户地址。设置具备行版本和审计，首次读取未配置时版本为 0。
2. 删除 ExternalDeliveryConfig 的 enabled／public_origin 字段及运行时门禁，不保留双读、TOML 回退或启动时导入。TOML 只保留网关地址、Worker、超时、重试、限流等技术参数；加密根密钥仍由部署环境持有。
3. 新增 GET／PUT /api/v1/notification-delivery/settings，沿用渠道管理权限。页面在通知渠道页提供公共设置的独立抽屉，复用现有 AdminDrawer／KBotDrawer；遮罩与 Escape 不关闭，保存期间禁止关闭。渠道和公共设置保存不产生外部请求。
4. 检查凭据、身份登记／验证码、纯文本试发不依赖门户地址。试发仍须渠道启用、目标已验证和显式确认；身份可选，未绑定用户不接收外发通知。启用业务规则须配置有效门户地址；存在启用规则时不允许清空地址。未配置地址不生成业务投递，页面明确说明且不补发历史事件。
5. 独立 Worker 始终运行，按数据库当前渠道状态领取／复核任务；Outbox 投影从当前范围公共设置生成受控链接。设置不跨请求缓存，修改无需重启；既有任务内容、幂等 UUID 和历史入口保持冻结，不重写。初次发布新代码仍需正常更新服务，不能把“后续配置热生效”理解为“不用部署代码”。
6. 实施顺序：同步合同与 canonical／定向新增表升级工件 → 应用和投影／Worker → 两端管理交互 → 权限、版本、租户隔离、热生效、无门户试发、真库回滚回归 → 架构／Schema／OpenAPI 验收 → 精确提交推送。升级只新增公共设置表，不删除或回填已有连接、密文、任务、站内通知和业务记录。

本次不包含真实飞书发送、服务器拉代码／重启、责任组或群绑定改动。数据库升级必须先做只读预检；不得以全库初始化替代。

## 当前范围修订（2026-11-06）

- 渠道配置、身份绑定和外发策略不属于 Domain：Ammolite 按当前 Tenant 配置；KBot 全实例配置。每个 owner 只允许一个飞书连接，跨业务空间复用；不能以任意默认 Domain 代替全局范围。
- 渠道类型明确选择飞书／企业微信。企业微信仅占位，前后端均禁止创建、启用及发送。
- 个人飞书 open_id 是新建用户的可选项，编辑成员可补绑、更换及清空解绑；不把此身份写入跨租户共享的用户资料。留空不依赖飞书配置，站内通知正常，不生成个人外发任务。
- 登记身份不自动试发；本人显式发送验证码并确认，成功后才启用个人业务消息。更换身份创建新候选，旧绑定及其历史保留，旧任务不得重定向。
- 管理接口不接受 Domain 参数。业务任务和独立入口必须保留真实资源 Domain；验证／试发可无 Domain。投影按合法受众取交集，发送及点击继续检查当前权限；绑定不是授权。
- KBot 个人通知按当前账号可访问的业务空间聚合，登录时选中的空间不作为个人收件箱分仓条件。Ammolite 沿用 Tenant + 当前用户及有效权限收件规则。
- Oracle canonical 为 Main API v10（含通知公共设置表）；PostgreSQL 同步唯一规范。已有旧范围表必须先执行部署预检；定向范围工件仅接受空旧外发表，有记录或旧通知凭据时停止，不删除、猜测合并或自动回填。完成范围验收后再单独新增公共设置表，设置升级不要求既有渠道为空。线上升级证据按目标环境分别记录，见部署文档第 6 节。

## 1. 设计基线与阶段边界

本方案落实“第一阶段站内通知基础修复 → 第二阶段飞书接入 → 后续企业微信扩展”的实施顺序。第一阶段范围和验证证据见 [AIOps 通知第一阶段基础修复](../operations/aiops-notification-foundation-phase-1.md)；已有资源定位规则见 [AIOps 通知定位与会话边界](../architecture/aiops-notification-navigation.md)。

“第二阶段”是本轮通知改进计划的第二阶段，不重排 Ammolite 原通知中心建设计划中的阶段编号；原计划中外部渠道对应的阶段 5，仍应以本专题作为本轮详细设计。

实施授权：用户已批准按本方案开始第二阶段代码实现。第一阶段真实手工验收证据仍需单独记录，不能据此推断已验收；单元测试、浏览器 fixture 或 API 模拟器不替代业务链路验收。本轮实现不包含线上部署授权。

### 1.1 本阶段交付范围

- 企业自建应用机器人连接配置、托管凭据引用、连接检查及受控试发。
- 平台用户与飞书用户身份绑定、验证、修改和解绑。
- 告警确认／升级／恢复、审批提醒、人工交互、审批结果、执行结果、人工结果登记及报告完成通知。
- 持久化投递任务、限流、重试、不确定结果处理、失败查询和受控重发。
- 飞书卡片中的“查看详情／进入处理”，定位并处理原任务。
- KBot4 与 Ammolite 的领域语义、合同、数据库工件、管理功能和测试同步维护。
- 为企业微信保留统一适配接口，但不在本阶段交付企业微信连接器。

### 1.2 明确不做

- 不在飞书卡片内直接批准、拒绝、取消或执行数据库动作。
- 不接入飞书原生审批流程或任务中心，不重建工作流引擎。
- 不以飞书登录替代现有系统身份和入口会话。
- 不引入收消息、交互回调、已读回执或飞书事件订阅作为本阶段依赖。
- 不自动补发历史事件，不因新增渠道重新投递已经处理的历史通知。
- 不转发监控原文、SQL、执行原始输出、报告正文或完整业务过程。
- 不用本次设计变更授权数据库清理、Schema 写入、服务器发布或重启。

审批仍在原任务页面完成，沿用独立审批人、当前权限、资源父子关系及版本校验。

## 2. 已有能力与实际缺口

### 2.1 复用第一阶段

复用事务 Outbox、受控事件目录、收件人解析、原始告警等级、具体 HITL／Proposal 身份、工作流关闭事件及权威状态对账，不绕开原有业务服务。

业务状态仍以所属服务为准；通知“已读”、飞书“接口接受”均不能改变业务状态。

### 2.2 Ammolite 实施前基线与本轮扩展

已有 `packages/platform_core/src/platform_core/notifications/delivery.py` 中的 `IMNotificationSender` 协议，以及 `platform_notification_delivery_job` 任务表。现有任务以 `notification_id + user_id + channel` 区分，仍缺少连接、明确目标、消息版本、租约、发送结果及故障恢复。

站内事件目录仍按原渠道控制站内投影；本轮以独立外部受控事件目录和策略生成外发任务，不放开旧策略中的占位 IM，也不依赖 Inbox 存在。总开关默认关闭，出现 IM 类型不代表已启用真实渠道。

本轮已扩展现有投递任务，未另建平行队列；发送协议已演进为两项目共用的语义合同，不保留兼容旧协议的双路径。

### 2.3 KBot 本轮新增

KBot 已新增对应的平台级连接、绑定、外部投递任务、尝试记录和外部详情入口代码及 canonical DDL／增量工件。已有站内通知 Worker 继续负责投影，外部网络调用不加入站内消费事务。工件已离线校验但未写入线上库。

## 3. 接入方式与服务边界

### 3.1 企业自建应用机器人

主方案采用企业自建应用机器人，不采用群自定义 Webhook 机器人作为主链。原因是需要明确用户身份、个人消息、受控群消息及厂商返回的 `message_id`。

本阶段不发展为多企业商店应用。自建应用自身对应一个飞书企业；系统 Tenant／Domain 与飞书企业标识不是同一种身份，不能相互替代。

### 3.2 链路

~~~text
业务状态变化 → 同事务 Outbox → 事件消费与安全校验
                                ├─ 站内通知、待办和后台任务投影
                                └─ 按外部策略生成持久化投递任务
                                     ↓
                                独立投递 Worker
                                     ↓
                                飞书适配器 → 飞书用户／受控群
                                     ↓
                                详情入口 → 登录与重新鉴权 → 原任务
~~~

消费端在同一次本地事务内保存站内投影和应有的外部任务；失败时由 Outbox 重试恢复。外部网络调用只在任务领取事务提交后执行，结果通过新事务及租约／版本条件写回。

飞书不可用不能阻塞业务提交、站内通知和待办关闭。领取、发送和结果写回不能持有业务表的长事务。

### 3.3 部署架构（已确认）

本阶段采用平台通知模块与独立外部投递 Worker，不新增飞书 HTTP 微服务。Worker 与 Main API 复用代码及应用镜像，以不同入口命令运行，独立启停、配置资源与扩容；外部发送不得注册为 API lifespan 后台协程。

KBot 已有站内投影 Worker 保持独立；Ammolite 已有站内投影任务保持现状，本阶段不扩大为全部后台任务重构。两项目新增的外部投递均由独立进程承担。

持久化数据库任务是可靠队列，不引入 Redis、Kafka 或 RabbitMQ。适配器负责厂商协议，应用层负责权限、受众及工作流状态，仓储负责短事务领取和条件写回。后续企业微信沿用相同任务和 Worker 合同；只有出现独立团队、容量或多系统服务化需求时，再设计完整的数据所有权和服务合同并拆为微服务。

真实验收使用用户准备的飞书测试企业与自建应用；HTTP 模拟仅用于自动化故障测试，不部署完整飞书模拟服务，也不自动启用真实渠道。

### 3.4 所有权

- 业务服务：权威业务状态、事实事件、合法参与人和已有处理命令。
- Platform Core：跨项目通知合同、受控外发内容、渠道协议及凭据基础设施。
- Main API 应用层：策略决策、当前权限检查、连接管理、身份验证、发送编排及审计。
- Repository／Unit of Work：任务领取、幂等登记、CAS 写回和尝试记录；仓储不自行提交。
- 飞书适配器：令牌、消息编码、厂商错误分类及接受回执，不决定业务审批或收件人权限。
- 前端：管理、可见性展示、登录恢复及原任务落地，不持有 IM Secret，不调用厂商 API。

业务服务只声明 `IM` 渠道语义，不保存 Webhook／Token，不依赖飞书 SDK。企业微信后续替换或新增发送适配器，不修改业务事件生产流程。

## 4. 消息与收件人

### 4.1 默认消息矩阵

| 业务消息 | 默认合法收件人 | 主要入口 |
| --- | --- | --- |
| 告警确认、升级、恢复 | 当前有效订阅人／责任人 | 原告警 |
| 等待审批 | 当前有权审批且不是申请人的用户 | 原 Proposal／审批 HITL |
| 等待查询授权、人工补证 | 原人工交互的合法处理人 | 原 HITL |
| 审批通过、拒绝、过期、失效 | 申请人及当前合法参与人 | 原方案及处理结果 |
| 执行成功、失败、取消、未知、开始前超时 | 申请人及当前合法参与人 | 原 Execution |
| 人工执行结果登记、报告完成 | 原任务相关用户／订阅人 | 原结果／报告 |

普通进度默认不外发；已有开始事件不能自动变成高频提醒。告警保留 INFO／WARNING／HIGH／CRITICAL 原始等级，不把通知紧急度当作原始等级。

执行成功只表示执行回执成功，卡片明确“执行成功，效果待验证”；UNKNOWN 不伪装成功，开始前超时与执行失败分开表达。

### 4.2 不以站内通知存在作为外发条件

外部任务从校验后的事实事件和渠道策略生成，不依赖个人站内通知是否存在、是否聚合或是否已被清除。`notification_id` 可以是关联定位，但不能作为外部任务唯一事实来源。

必须避免以下漏发：

- 没有 IN_APP 订阅人时，连同明确配置的 IM 投递一并跳过。
- 多次执行结果被站内聚合后，只剩同一个外发任务。
- 清除个人收件箱后，外发任务和详情入口丢失。
- 关闭事件的通知收件人不同，导致原审批待办无法关闭。

“允许外发”也不能扩大业务受众。仍以当前用户、角色、订阅、模块启用及资源访问权限解析合法目标。

### 4.3 审批与人工交互

审批提醒绑定确切 Proposal／HITL，不仅绑定 Run。收件人必须同时满足当前业务使用、审批与空间范围要求，排除申请人；策略不得重新加入申请人或无权用户。

发送前读取第一阶段权威状态投影，确认审批／人工输入仍待处理；已经关闭、过期或失效的可操作提醒取消投递。结果事件按独立身份投递，不能用旧的打开事件覆盖。

权限不可确认、业务服务不可达时，不推断任务已关闭，不向未经确认的目标发送业务内容。

## 5. 飞书身份绑定与群消息

### 5.1 个人身份

首版以 `open_id` 为个人目标。绑定至少表达：

- 连接 ID。
- 本地用户身份及配置所属范围：Ammolite Tenant 成员；KBot 全局用户。
- 飞书 `open_id`、绑定状态、验证时间和版本。
- 维护与验证的真实操作人审计。

`open_id` 只在特定飞书应用下有效，不能跨应用复用。不同系统或不同连接使用不同应用时，必须分别绑定，不按姓名、邮箱相似度或旧应用 ID 猜测目标。

建议流程：

1. 管理员在新建用户时可选填写候选飞书身份，或在用户详情中补绑；不填表示不接收个人飞书通知。
2. 向候选飞书身份发送一次性验证消息；这也是受控、有频率限制且可审计的真实发送。
3. 对应用户登录系统后输入验证码，确认双方身份关系。
4. 修改、解绑、停用及绑定版本变化均审计；验证码限时、限次，不保存明文验证码。
5. 缺失或已解绑时不生成个人外发任务；已登记但未验证的候选不会发送业务消息。

发送前重新检查账号、成员身份、资源权限、连接及绑定是否有效。冻结目标后若绑定被修改，不得把同一个任务偷偷重定向到另一个人；应取消原目标任务，并通过明确的新决策生成任务。

### 5.2 群消息

首版以个人消息为主，群消息仅开放受控、低敏的告警提醒：

- 管理员明确绑定群、连接和业务范围；机器人必须在群内且允许发言。
- 默认只发“有事项待查看”等低敏提示及受控入口，不广播审批方案、SQL、执行输出或报告正文。
- 不认为机器人在群内就意味着群成员拥有业务资源权限；转发或点击都必须重新鉴权。
- 不自动 `@所有人`，不从个人身份绑定推断群受众。
- 默认不向群发送具有敏感内容的个人审批提醒。
- 群的可见内容必须经过独立外发白名单；不能直接复用个人卡片全部字段。

## 6. 卡片、内容白名单与详情入口

### 6.1 内容

卡片模板版本随代码发布，首版不开放任意 HTML／JSON 模板编辑。个人卡片可包含：

- 系统及环境标识；测试环境醒目标注“测试”。
- 消息类型、原始告警等级、业务发生时间。
- 明确允许外发的资源名称和简短脱敏摘要。
- “查看详情”或“进入处理”URL 按钮。
- 来源状态说明，例如执行成功但效果待验证。

即使现有字段名为 `summary` 或 `safe_payload`，也不能原样转发。采用外部渠道专用的字段白名单及长度限制；日志和尝试记录不保存完整请求／响应正文。

禁止外发或记录到投递日志：密码、Secret、Token、连接串、SQL／DDL、查询结果、执行原始输出、完整报告、文档正文、Prompt 和异常堆栈。

### 6.2 独立入口

拟新增用户可访问的前端入口：

~~~text
https://系统域名/notifications/open/{entry_id}
~~~

该路径已实现；真实飞书客户端与外网访问仍待联调。`entry_id` 是不可猜测的定位标识，不是登录、审批或资源访问凭证。

处理顺序：

1. 未登录先走既有登录／入口会话流程，仅保存本系统内部的原入口。
2. 服务端基于可信身份校验用户及确切 Tenant／Domain，不信任 URL 提供的授权上下文。
3. 读取该入口保存的受控 `route_key` 和类型化参数。
4. 检查 Run、Proposal、HITL、Execution、报告等资源的作用域及父子关系。
5. 进入原任务，重读当前状态，再使用已有业务命令处理。

Ammolite 复用统一工作台与 BUSINESS 会话恢复；KBot 补齐外部首次打开时的登录恢复及明确空间定位，不依赖 sessionStorage 中恰好选中的空间。

不允许任意 `redirect_url`、Token 或审批令牌进入 URL。不因缺失定位、撤权或资源不存在而跳到默认空间、其他租户或管理控制台。

### 6.3 与收件箱清理分离

详情入口具有独立记录和明确有效期，不依赖个人通知是否存在。入口与仍有效投递任务的保留关系须一起验证；禁止通知归档／删除级联破坏仍需使用的外部入口或投递审计。

入口过期或资源不可用时返回明确、安全提示。个人专属入口仍检查合法收件人；受控群入口仍按当前点击者的实际资源权限裁剪。

## 7. 数据对象及数据库边界

本节冻结逻辑职责，精确物理字段、索引、API DTO 和表名在实施时同步维护于 canonical 工件，不在两项目复制独立且不一致的业务模型。

| 逻辑对象 | 必要信息 |
| --- | --- |
| 渠道连接 | Provider、所属范围、App ID、托管凭据引用、启停、健康状态、配置版本 |
| 身份／群绑定 | 连接、内部主体或业务范围、外部身份、验证状态、版本 |
| 策略渠道关联 | 受控事件、当前合法目标规则、连接、外发限制与时间策略 |
| 投递任务 | 来源事件、确切范围、连接、冻结目标、消息用途／版本、冻结内容及 Hash、幂等身份、期限、租约、状态 |
| 投递尝试 | 尝试编号、时间、耗时、安全错误码、厂商请求标识、message_id |
| 详情入口 | 隔离范围、受控资源定位、受众模式、有效期和审计 |

任务同时记录消息模板版本及观察到的连接／绑定版本。`message_id` 只在确定取得厂商回执后保存。

### 7.1 共同原则

- App Secret 复用各项目现有托管凭据设施，按用途／范围校验读取；不建立明文业务列。
- API 不返回已有 Secret、密文、凭据内部引用或 Token。密钥根由运行环境提供，不能提交到仓库。
- 不跨服务建立资源物理外键；内部通知对象的引用与删除策略必须明确，不默认级联清理任务。
- Schema 验证仅在规范工件、部署流程及 acceptance 中执行，不加入启动、readiness、UoW 或请求流程。
- 不靠历史回填猜测缺失资源、租户、用户或飞书身份。
- 运行时配置使用项目现有 typed settings，不从网页输入任意接口 URL。

### 7.2 KBot Oracle

同步 Entity、规范 DDL、manifest、必要生成工件与验收。业务结构只使用主键、外键和列级 NOT NULL；不新增 CHECK／UNIQUE 或用唯一索引绕过政策。

幂等登记使用受主键定位、可锁定的稳定身份行以及业务事务校验；多 Worker 创建与重试必须有真实并发回归。不能用“先查询不存在再插入”宣称并发安全。

线上结构调整另行明确目标并经用户授权，以受控增量工件执行；不调用重建脚本清空通知或业务数据。

### 7.3 Ammolite PostgreSQL

扩展现有 `platform_notification_delivery_job`，使其表达来源事件、连接、目标、版本、租约和回执；旧 `notification_id` 引用不能限制为必须存在个人站内通知。

同步 canonical Schema／Entity、初始化、代码、合同、测试与文档；不新增本地兼容迁移、双读写或历史回填。已有线上环境的部署操作必须另行审阅和授权，不以全库初始化替代。

## 8. 发送状态、幂等与故障恢复

### 8.1 状态语义

| 状态 | 含义 |
| --- | --- |
| PENDING | 已持久化，等待发送 |
| SENDING | Worker 已领取，具有可校验租约 |
| ACCEPTED | 厂商接口确定接受，已取得有效回执 |
| RETRY_WAIT | 已确认可重试的失败，等待下一次尝试 |
| UNKNOWN | 请求可能被接受，但未取得确定结果 |
| BLOCKED | 凭据、权限、身份或配置问题，需要处理 |
| DEAD | 达到重试上限，保留原因与审计 |
| CANCELLED | 已失去发送意义，例如原人工任务已关闭 |
| EXPIRED | 超过任务或消息的发送期限 |

ACCEPTED 不等于已读、用户已处理、数据库执行成功或效果验证成功。本阶段不提供已读回执。

### 8.2 任务身份与冻结消息

投递任务以“来源事件 + 连接 + 具体目标 + 消息用途／版本”确定身份。关联具体执行／人工交互，不按 Run 单独去重。

同一任务的重试保持相同消息内容、目标和厂商 `uuid`；重新渲染产生不同内容时不能继续使用同一个 `uuid`。任务重发不能重新扩大收件人集合。

本地幂等负责长期不重复创建任务，厂商去重只是额外保护，不承诺端到端 exactly-once。

### 8.3 一小时去重窗口与 UNKNOWN

官方消息接口 `uuid` 最长 50 字符，相同值在 1 小时内至多成功发送一条消息。本地生成满足长度限制的稳定请求标识，内部幂等键与厂商请求标识可分开表达。

- 明确的限流／服务拒绝：按分类进入 RETRY_WAIT 或 BLOCKED。
- 请求可能已发出但响应超时、连接中断、发送后进程崩溃：按 UNKNOWN 处理，不能简单当作未发送。
- 去重窗口内可按同一 `uuid`、同一冻结内容重试；窗口基于第一次可能发送时间，并考虑时钟与安全余量。
- 窗口外仍无确定结果：保持 UNKNOWN，不无限盲发。
- 人工确认重新发送时提示可能重复，创建新发送代次并记录真实操作人；不覆盖旧尝试证据。

租约到期不等于厂商没有接受请求，恢复流程必须识别是否可能已进入网络发送阶段。

### 8.4 领取与结果写回

使用有界批次、短事务及防竞争领取；持久化租约令牌／期限和尝试身份。发送结果仅允许匹配当前租约及版本的 Worker 写回，旧 Worker 不能覆盖新尝试。

配置停用、绑定变化、用户撤权、消息过期时在发送前阻断。外部调用前后存在不可彻底消除的并发窗口，点击和业务动作始终再次鉴权，不能承诺撤权可撤回已到达飞书的内容。

### 8.5 限流、降噪与告警

同时处理 HTTP 状态和业务 `code`。HTTP 200 但业务码非 0 不计成功；即使 `code=0`，缺少合法消息回执也不能伪造 ACCEPTED。

遵循 `x-ogw-ratelimit-reset` 等厂商等待提示，并采用有界、带随机抖动的退避；连接、目标和平台总量限流分开控制，不硬编码一个 QPS 代替所有限制。

重试上限、等待、静默、合并及消息期限使用受控配置，不延长原审批有效期。强制／需处理事件按既有规则保留站内及时可见性，不用共享通知记录延迟站内投影。

本轮降噪采用部署侧有界配置，默认关闭，仅允许原始等级 INFO／WARNING 的新告警与恢复；等级缺失、HIGH／CRITICAL、升级、审批、人工处理和执行／报告结果均绕过降噪。静默使用半开 UTC 小时时段、支持跨日，发送前及重试前重新检查；等待超过原期限时明确 EXPIRED，不延长期限。合并窗口为固定的 0～300 秒，限定同空间、连接与凭据版本、绑定与版本、目标、事件类型、确切资源及等级，仅保留窗口内最后一个从未发送的提醒；旧任务标记 CANCELLED／NOTIFICATION_COALESCED 并保存新任务关联审计，不删除来源、入口或投递证据。已尝试发送、SENDING、UNKNOWN 任务不能合并，事件重放不能取消较新的任务。

外部异常通过站内管理状态、审计及指标呈现；渠道自身的失败告警不能递归投递到同一故障渠道。

## 9. 飞书 API、凭据与环境配置

本次设计依据 2026-11-05 查阅的官方文档。实施前应复核文档和应用实际开通能力，不从旧教程复制历史字段。

### 9.1 新版应用令牌

~~~text
POST https://accounts.feishu.cn/oauth/v3/token
grant_type=client_credentials
~~~

按当前应用支持的认证方式，在 `client_secret_basic` 和 `client_secret_post` 中选择一种，不同时使用。响应读取 `access_token`、`expires_in` 和 `token_type`。

按 `expires_in` 缓存并提前刷新，不硬编码两小时，不每次发消息都取 Token。缓存按连接、App ID、凭据版本及权限范围隔离，刷新做并发合并，替换密钥后失效。

新版 Token 为较长 JWT，传输／缓存链路至少预留官方建议的 4 KB；不按旧 Token 长度截断，不把解码 JWT 的内容当作未经验证的本地授权依据。

旧 `/open-apis/auth/v3/tenant_access_token/internal` 已在本次查阅文档中标为历史版本，本方案不增加旧／新自动兼容分支。

### 9.2 消息

~~~text
POST https://open.feishu.cn/open-apis/im/v1/messages?receive_id_type=open_id
~~~

个人目标优先 `open_id`；受控群使用 `chat_id`。卡片使用 `interactive` 消息，`content` 按厂商协议序列化。成功回执保存 `message_id` 和安全请求标识，不记录完整响应正文。

应用开启机器人能力并发布；个人目标在应用可用范围内；群目标要求机器人在群内并可发言。最小发送权限使用 `im:message:send_as_bot`，不为方便预先申请通讯录、收消息或高风险能力。

### 9.3 配置隔离

令牌服务与消息 API 是两个不同官方 Origin，不得假定共享同一个 API Base URL。

生产端点限定为部署侧允许的官方 HTTPS 地址；UI 只选择连接，不填写任意 URL／Webhook。开发／测试已支持分别覆盖令牌地址和消息 API Origin，但必须显式启用 fixture 门禁及允许目标范围，不通过自动失败回退进入真实渠道。

对 Mock 使用假 Secret、假身份和测试标识；禁止把真实凭据发给 Mock。模拟器地址、生产域名、门户公开地址均通过 typed settings 接入。精确配置项名称在实现时进入配置模型和示例，不把本文示意名称当作当前可用配置。

## 10. 管理界面与运维

### 10.1 2026-11-06 页面职责修订

本轮只调整通知页面与查询交互，不改责任组模型，不新增租户用户组，不实施群绑定归属或群路由。现有责任组、群绑定、业务数据和投递记录保留，不做数据库升级或历史补发。

- 通知渠道与通知投递拆为独立菜单和页面。Ammolite 在租户控制台配置，KBot 全局配置一次；不要求选择 Domain。
- 渠道页每种类型使用一张摘要卡片，飞书单例不分页。企业微信仅不可操作占位。配置抽屉只负责名称、App ID、Secret 与启用状态；Secret 不回显，关闭即清除本次输入。
- 保存、检查连接、真实试发分离。令牌检查通过不等于送达；真实试发仅选择当前连接的已验证个人目标，并经共享确认组件明确确认。投递结果在记录页查看。
- 个人身份仍在创建／编辑成员时可选维护，本人验证码确认放到“我的通知设置”。群登记入口暂不展示，新规则和试发不选择群；既有绑定与策略不被自动修改。
- 消息规则作为渠道页的次级管理区，按中文事件名称与已有个人绑定选择，不要求填写用户 UUID。策略只筛选业务合法收件人，不授予权限。
- 投递页按时间、状态、事件类型和接收用户精确筛选，默认每页 20 条；后端多取一条返回 has_more，不用当前页条数猜测还有下一页。时间采用带时区的半开区间。
- 详情抽屉显示安全摘要、回执、错误码与尝试时间线；不以原始 JSON 代替界面。ACCEPTED 显示“平台已接受”，UNKNOWN 显示“结果待核实”；受控重试保留重复风险确认。
- 队列概览明确为全量队列与近 24 小时尝试指标，不冒充当前筛选结果。近期渠道操作记录在投递页次级折叠区展示，不与配置表单混排；统一审计中心整合不在本轮扩展。
- 前端复用现有主题变量、语义按钮与共享确认组件，验收覆盖桌面／窄屏、权限、空状态、加载失败、分页边界与详情切换。
- 所有通知抽屉复用共享 `admin-drawer` 样式及行为，不维护页面私有的原生 dialog 抽屉。遮罩点击与 Escape 均不关闭；显式取消／关闭清空 Secret，写请求期间锁定关闭按钮，上层共享确认取消不关闭底层抽屉。
- 权限、配置维护与外发启用相互独立：capabilities 同时提供 `runtime.enabled/code/message`。总开关关闭时，渠道管理员仍可新建／编辑连接、加密保存 Secret、轮换凭据及暂停渠道，保留单例检查、版本控制、范围鉴权与审计；不依赖 public_origin，不调用飞书，不生成任务，也不自动启用部署总开关。页面明确提示外发未启用，但不能因此禁用“配置飞书”或“保存配置”。
- 检查连接、发码、真实试发、规则写操作及实际投递仍保留既有外发门禁；总开关关闭时外部操作返回 503／`NOTIFICATION_EXTERNAL_DISABLED`，Worker 不领取任务。配置按钮可用不代表消息发送可用，不能由此绕过部署、凭据、身份或业务授权条件。

以下为能力边界说明，其中群配置入口按上述修订暂缓：

1. 通知渠道：新增／编辑连接、替换密钥、连接检查、暂停与健康摘要。
2. 身份绑定：创建／编辑成员时可选维护个人身份，本人到“我的通知设置”验证；群绑定入口暂缓。
3. 投递记录：状态、事件与目标的安全摘要、尝试历史、安全错误码、受控重发。

权限区分渠道管理、绑定管理／本人验证、投递查看与重发；复用已有治理授权入口并明确新增 capability。前端按服务端 capability 渲染，后端不依赖页面隐藏进行授权。

保存配置不自动向真实人或群试发；连接检查不等于消息已送达。试发必须明确选择当前已授权测试目标，真实发送及失败都审计。

最少观测：队列数量／最老等待时间、接受率、重试／UNKNOWN／BLOCKED／DEAD、外部耗时、令牌刷新失败、限流、缺少绑定和过期取消。避免按每个用户／资源 ID 制造高基数指标。

## 11. 真实飞书测试环境

### 11.1 不自行部署完整飞书服务端

本阶段推荐使用官方 SaaS 的独立测试企业或企业批准的隔离测试范围。官方当前自建应用教程建议创建新企业体验开发；是否免审及可用权限以实际企业设置为准，不保证所有账号都存在专用“测试企业”控制台按钮。

kbotdev 只需部署我们的应用。用户已选择真实飞书测试企业；本轮不部署 API 模拟器或完整飞书服务端。自动化 HTTP 桩不是飞书客户端／租户的替代品。

### 11.2 准备步骤

1. 创建独立测试企业，至少准备三个实际可登录的账号：A 申请人、B 审批人、C 无业务权限用户。
2. 在飞书开发者后台建立两个企业自建应用：`KBot-AIOps-Test`、`Ammolite-AIOps-Test`。
3. 开启机器人能力，申请最小权限 `im:message:send_as_bot`。
4. 创建并发布版本，将测试用户纳入应用可用范围；只保存机器人配置不代表能力已生效。
5. 通过官方 API 调试台获取各应用下的用户 `open_id`；不能跨应用复制使用。
6. 需要群测试时，建立专用测试群，将对应机器人加入并确认可发言。
7. 第二阶段代码交付后，在两系统分别配置测试连接、验证身份绑定和启用有限测试策略。

不要把假身份当作可登录飞书账号；至少以真实可操作的测试账号完成申请人与审批人分离验证。

### 11.3 网络

本阶段只有出站推送及 URL 跳转，不需要飞书接收消息／卡片交互回调，不为此公开内部 API 端口。

飞书客户端所在的手机／电脑必须能访问卡片中的系统地址。推荐 HTTPS 域名及有效证书。服务器私网地址 `10.0.0.190` 只适用于可访问该私网的设备；不应把内部服务端口直接暴露为详情入口。

仅绑定回环地址，禁止公开 `/__admin` 管理接口。远程管理使用现有安全 SSH 通道；Worker 在容器中时通过专用 Docker 网络访问，容器内的 `127.0.0.1` 不是宿主机。

### 12.2 基础连通性桩

注册假令牌响应：

~~~bash
curl -sS -X POST http://127.0.0.1:18081/__admin/mappings \
  -H 'Content-Type: application/json' \
  --data '{
    "request": {
      "method": "POST",
      "urlPath": "/oauth/v3/token"
    },
    "response": {
      "status": 200,
      "headers": {"Content-Type": "application/json"},
      "jsonBody": {
        "code": 0,
        "access_token": "mock-feishu-token",
        "expires_in": 3600,
        "token_type": "Bearer"
      }
    }
  }'
~~~

注册假消息接受响应：

~~~bash
curl -sS -X POST http://127.0.0.1:18081/__admin/mappings \
  -H 'Content-Type: application/json' \
  --data '{
    "request": {
      "method": "POST",
      "urlPath": "/open-apis/im/v1/messages",
      "headers": {
        "Authorization": {"equalTo": "Bearer mock-feishu-token"}
      }
    },
    "response": {
      "status": 200,
      "headers": {"Content-Type": "application/json"},
      "jsonBody": {
        "code": 0,
        "msg": "success",
        "data": {"message_id": "om_mock_example"}
      }
    }
  }'
~~~

以上仅为两个静态 HTTP 桩：不实现实际身份校验、完整卡片合同、真实 message_id、`uuid` 去重或故障恢复，不能作为正式验收模拟器。

动态注册的映射不保证容器重建后恢复。实施时交付版本化 fixtures 及持久化／只读挂载的部署配置；模拟器协议与故障状态属于测试工件，部署资产按各仓库部署目录规则归档，不把模拟业务逻辑塞进部署脚本。

启动容器不会自动修改现有系统。本轮已实现分别覆盖令牌 URL 和消息 API Origin 的显式 fixture 配置，但用户选择真实测试企业，因此上述 WireMock 仅保留为可选参考，不是本轮部署动作，也不能认为已经接通。

### 12.3 正式模拟器合同与故障集

| 场景 | 验证点 |
| --- | --- |
| 正常接受 | 校验鉴权、目标、卡片与回执结构 |
| 无效凭据／Token 过期 | 正确刷新或阻断，不打印 Secret |
| HTTP 200、业务错误 | 不误记 ACCEPTED |
| HTTP 限流及厂商限流业务码 | 遵循等待提示并有界退避 |
| 无权限、用户不可达、机器人不在群 | 安全错误分类，不扩大目标 |
| 超时、断链、5xx、无效 JSON | 区分确定失败与 UNKNOWN |
| 相同 uuid 重试 | 在受控时钟和去重窗口内模拟重复接受保护 |
| 对方接受后响应丢失 | 不确定结果恢复与窗口外重发门禁 |
| Worker 崩溃／租约过期／并发 | 任务不丢失，旧租约不能覆盖新结果 |
| 撤权、解绑、任务已关闭／过期 | 发送前阻断并保留原因 |

WireMock 请求日志可能保存请求内容，仅允许假密钥和脱敏样本。正式故障模拟需有可重置状态、明确匹配规则及断言，不能仅依靠一直返回成功的静态桩。

### 12.4 模拟能力边界

模拟器不能验证飞书客户端卡片渲染、真实 open_id、应用发布与可用范围、群成员权限和手机登录跳转。上述内容必须在真实测试企业验收。

不能以模拟器计数代替真实送达证据，也不使用真实群组进行故障压测。

## 13. 分步实施计划

| 顺序 | 交付 | 门禁 |
| --- | --- | --- |
| 2.1 共同合同与基础设施 | 连接、绑定、凭据引用、投递对象、权限、canonical Schema／初始化工件 | 双仓库架构、Schema、隔离、并发幂等合同测试 |
| 2.2 可靠发送 | Worker、飞书适配器、令牌缓存、限流重试、UNKNOWN、模拟器 | HTTP 协议、故障注入、租约恢复及多 Worker 回归 |
| 2.3 事件与入口 | 外发白名单、收件人检查、卡片、登录恢复、原任务定位 | 两前端精确定位、撤权、父子错配、无收件箱记录回归 |
| 2.4 治理与联调 | 渠道／绑定／投递管理、审计、指标、真实飞书验收 | A／B／C 账号完整业务链、手机访问及真实厂商接受证据 |

以上是同一第二阶段内部实施顺序，不是另外新建阶段、平行审批服务或独立通知中心。每步同步两仓库，不能只完成一个后以数据库差异解释产品缺口。本轮已落地 2.1～2.4 的代码、管理入口、离线数据库工件和本地测试；2.4 的真实企业联调及真库并发验收仍待进行。自动化故障注入使用假 HTTP，不新增 WireMock 部署。

## 14. 验收标准

- [ ] 第一阶段已由用户完成真实环境手工验收并确认。
- [ ] A 发起审批，只有合法审批人 B 收到处理提醒，C 不收到业务内容。
- [ ] B 在原任务处理后，相关站内待办关闭，A 收到真实结果。
- [ ] 同一 Run 下不同 HITL、不同执行和版本不会被错误去重。
- [ ] 过期、失效、迟到和乱序提醒不重新打开任务，不发送过时可操作提醒。
- [ ] 告警等级保持原始语义，执行成功与效果验证不混淆。
- [ ] 发送前撤权／解绑能阻断待发送任务；转发入口不能获得额外权限。
- [ ] 两项目的 Tenant／Domain、外部连接和身份不串用，App open_id 不混用。
- [ ] 飞书故障不阻塞站内通知、业务提交和待办关闭。
- [ ] 多 Worker、重启及进程崩溃时任务不丢失，租约恢复和 UNKNOWN 处理正确。
- [ ] 一小时去重窗口内外均有测试，不宣称永久 exactly-once。
- [ ] 清除个人收件箱不破坏独立详情入口和投递证据。
- [ ] 手机未登录点击卡片，登录后仍进入确切空间的原任务。
- [ ] 卡片、数据库任务内容、日志与审计没有 Secret、Token、SQL、原始执行输出或业务正文。
- [ ] 生产不能启用任意 Mock 地址，不自动回退向真实用户试发。
- [ ] 两套系统均有真实飞书 API 接受回执及客户端展示验证，不能只出示模拟器成功记录。
