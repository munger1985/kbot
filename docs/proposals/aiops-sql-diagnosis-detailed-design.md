## 1. 目标、问题与非目标

产品目标：从窗口 Top SQL 或用户指定的 SQL 进入同一诊断流程，对确定的数据库语句、
时间范围和证据，回答“谁在消耗、为何慢/影响谁、如何处理、如何验证”。
诊断必须能联合已授权的数据库直连、监控、日志、计划、对象、应用与变更等可用信息，
形成可追溯的性能画像、原因判断、可执行或条件化的解决方案及验证方法。
系统必须可以诚实地输出部分结果，而不是承诺所有场景都能自动定位根因。

本次重构针对的原始问题（当前实现范围以实施记录为准）：

1. 两端深入分析只提交含标识的自然语言；SQL 所在实例、库、用户、子游标及原始证据行
   没有作为结构化对象传递，后续需要模型重新推断。
2. 单 SQL 可采集累计统计、活动及全库对象数据，但证据没有统一按 SQL、实例和时间关联；
   PostgreSQL 累计统计本身没有历史实际计划。
3. 固定摘要能避免部分错误推断，却主要罗列指标和固定建议；有用的计划、窗口或对象证据
   未必进入结论。
4. 周期快照当前截取有限的累计候选；窗口内新出现、淘汰或统计重置的语句可能遗漏。
   当前窗口取样只选请求区间内快照，精确起止时间通常不与采样时刻重合。
5. 单 SQL 可能再次显示 Top SQL 主表；未知字段被笼统翻译，证据缺口和内部 Finding
   在正文中重复出现。重规划限制不是全流程硬时限。
6. 取证顺序和摘要过于固定，监控、数据库、日志等没有按问题协作；缺计划就只能补计划，
   无法有效诊断阻塞、应用重试、外部资源竞争等并不总以执行计划为中心的问题。

本次设计决策：固定身份、安全、统计语义、证据引用和执行预算，不固定指标清单、
调查顺序或根因候选。复用现有 investigation，而非另建一套与其并行的 SQL Agent；
诊断质量由真实场景中的原因区分、方案针对性和验证闭环衡量，不以填满报表或 Finding
数量衡量。常见路径是经验起点，不是能力上限，也不是每次必须跑完的检查表。

非目标：自动安装扩展、变更目标库配置、执行用户提供的 SQL、自动创建索引或承诺任何一次
都可识别根因；不引入假数据、不按数据库名称或特定 SQL 写特例。

## 2. 产品交互与范围

| 用户任务 | 默认结果 | 口径与动作 |
| --- | --- | --- |
| Top SQL | SQL 文本、统计排名、主要工作量特征与诊断入口 | 默认最近 15 分钟、总耗时降序、10 条；支持调整窗口、数量、排序指标；显示实际区间与候选完整性 |
| 当前活跃 SQL | 指定采样时刻的活动会话 | 明确是时点快照；0 行不代表历史无负载 |
| 单 SQL 深入诊断 | 身份、SQL、证据质量、指标、诊断、建议 | 默认继承原选择的 Target、统计身份与时间范围；不重复展示 Top SQL 主表 |
| 直接输入标识或 SQL 文本 | 先确认 Target 和唯一对象，再诊断 | 不唯一时返回候选供选择；SQL 文本只作为不可信材料，不自动执行 |

当单点不足以区分当前假设时，可按统一 DBA 设计追加一组低成本目录采样，
显示真实次数、间隔、实际时点及中止原因；其当前/累计口径不变，不替代所请求的历史窗口。

用户未明确时间范围时使用最近 15 分钟；保留 5 分钟、1 小时、24 小时及自定义区间。
只在冻结本轮计划时将相对时间转换成带时区的绝对 UTC 范围；展示用户时区和实际覆盖。
查询指定排序字段不可得时提示能力缺口，不默默换排序方式。默认排除事务控制语句的
Top SQL 产品筛选应由可见筛选条件表达，可切换查看，不能修改原始证据或妨碍单 SQL 诊断。
默认不启用周期采集；启用前显示权限、频率、成本、留存、采集模式与生效方式。

任务范围冻结为“排行”“指定 SQL 诊断”或“负载/慢 SQL 调查”，并记录用户待回答的问题、
症状、时间、基线/SLO（如有）和完成标准。仅询问 Top N 时先完成排名和简短负载解读，
不能因历史会话分析过某条 SQL 就自动转为它的完整调查；窗口不可得时明确告知，可分开
展示累计参考，但不能把累计表当作窗口任务完成。用户要求解释原因或解决问题时才进入
相应深入调查；同一引擎与证据链可复用，不让每次列表查询承担完整诊断的时延。

## 3. 结构化对象、跨轮与授权

### 3.1 选择与 Turn 合同

对现有 Conversation Turn 创建合同增加可选的类型化 SQL 选择输入，不能借任意
`client_metadata` 绕过验证。Top SQL / 当前活跃 SQL 每行由服务端生成不透明的
`selection_ref`，绑定不可变的 source artifact、结果集、行序号或稳定行键、内容校验值、
原采集时间、所需 SQL 身份及有效期。展示名称和 SQL 文本不作为可执行输入。

目标 Turn 请求示意（字段名和最终版本在实现时纳入双方共享合同与 OpenAPI）：

```json
{
  "content": [{"content_type": "TEXT", "text": "继续深入分析这条 SQL"}],
  "idempotency_key": "<request-id>",
  "sql_diagnosis": {"selection_ref": "<opaque-row-reference>"}
}
```

沿用现有会话 Turn 路由、认证、幂等及 SSE；原有自然语言或 Starter 不受影响。
服务端对选择引用重新验证调用者、Agent 版本、会话、Target/资源授权、证据归属、
证据完整性、是否过期或已撤权，再从不可变证据提取身份；不能信任浏览器传来的 Target、
用户、SQL 文本或行内容。引用过期/删除/越权/Target 不兼容时返回明确可恢复错误或
澄清，不退化为任意 SQL 或换用其他 Target。重新提交同一幂等键必须语义一致。

自然语言标识输入先解析已授权 Target 的数据库类型，再进行相应身份校验；模型提议
仅是待核验候选。存在多条相同标识或缺必要维度时，展示候选供用户选择；不能把缺失
维度默认为其他用户、Schema、实例或 Oracle 子游标。上下文信息以原来源、时间和证据
可信等级为准，不把上一轮模型结论当作事实；可引用同一授权会话内被明确选择的历史行，
不限于紧邻上一轮，但每次都重验访问权限及目标兼容性。逻辑 Target 相同不等于实例未切换。

### 3.2 SQL 身份与序列化

建立统一的 `SqlSubject` 和引擎维度，区分“已确定”“缺失”“不适用”：

| 数据库 | 必要身份 | 需要保留、不得隐式合并的维度 |
| --- | --- | --- |
| PostgreSQL | 实际实例/集群身份、database OID、query_id | user OID、top_level；多行时分别展示 |
| MySQL | 实例身份、Digest、Schema（含明确的 NULL） | 版本、摘要来源与统计周期 |
| Oracle | DBID、实例/启动代次、容器、SQL ID | child number、plan hash、解析 Schema；聚合前保留各行 |

实例身份使用驱动与目标实际可验证的信息；取不到稳定身份则标 `UNKNOWN`，
不得假定可跨时比较。Oracle RAC、多容器按实际实例和容器归属处理，不能用本地
DISPLAY_CURSOR 冒充另一实例/子游标的计划。哈希、Digest、query_id 并非全球唯一，
SQL 文本差异或碰撞无法排除时返回歧义。

身份格式校验属于引擎与来源适配：PG query_id 的有符号十进制值不能套 Oracle SQL ID
正则，MySQL Digest 按已发现来源格式校验；缺失维度走消歧而不是格式错误或隐式聚合。

当前实现按 PostgreSQL 库/用户/顶层、MySQL Schema、Oracle DBID/实例/容器/游标/计划
保留独立统计主体。PG 只有 query_id 时，可使用版本化 statement.subjects 在凭据可见范围
定向发现完整维度，不猜当前连接数据库就是该 query_id 的库；Oracle 游标读取 DBID/CON_ID，
MySQL 显式 NULL Schema 不降为未知。最多检查 256 行、展示 20 个主体，截断明确保留。
多个完整且未截断的主体可分别诊断并做描述性比较；结论声明 subject_ids，单主体判断只能
引用自己的直接观察，COMPARISON 判断须引用每个参与主体。不能把一条游标的计划或用户的负载
套给其他主体，不生成混合对象图。维度缺失、文本冲突或截断仍保留歧义，不能隐式合并。
表格保留选行继续诊断能力，引用原始充分性 Artifact、原行号及行哈希，续问重验权限和 Target 版本。
历史统计和重复活动会话不扩大当前候选集合；零号子游标及计划值不得在规划时丢弃。
此切片不声称消除标识碰撞或支持任意多个不同 SQL 标识的完整比较。

无选行的续问按明确 SQL 主体搜索同会话最近 16 轮，跨过中间失败/无关轮，最多保留 8 份
观察、512 行和 256 KiB；达到预算须声明不完整。逐来源重新验证用户、Agent 版本、域/租户、
Target 配置和当前授权，以及原始充分性 Artifact 哈希。只投影匹配行并保存原行号、来源链和
原采集时间，不继承模型结论或历史副本。显式选择在取证前也重新读取源并校验原 TTL，
不直接复用接收请求时缓存的可信标签。历史值不是当前值，逻辑 Target 相同不是物理身份互证。

标识、OID、计数器及可能超出 JavaScript 安全整数范围的值经 wire 使用十进制字符串；
内部使用精确整数/Decimal 计算并记录单位，不得先经 float。数据库原生计数及单位保留，
转换规则与舍入由服务端确定；金额式格式化不能改变原始值。

## 4. 采集与窗口计算

### 4.1 采集策略和成本

窗口事实不限定来自自采快照：按已授权资源选择语句原生历史统计、可用报告、
逐次执行日志/事件或自采差分，并核对它们实际回答的排名问题。只有来源确实保留窗口
执行时长与次数、可说明完整性时才能给相应窗口排名；采样日志只能给已采样执行的排名，
活动采样只能给采样活动/等待负载，不能替代完整语句总耗时。Oracle AWR 区间必须按
真实快照与许可处理，不能将一小时分摊成精确 15 分钟。“至少两个可比快照”是差分
路径的要求，不是所有历史来源的统一门槛。

复用 Workload Snapshot 调度、Target 设置、只读凭据与保留策略，扩展为两种显式模式：

- `VISIBLE_SET`：尝试采集配置范围内统计源当前可见集合；记录源权限、可见范围、采集
  起止、行数、字节数、分页/查询方式、上限、截断、错误与来源版本。超限即部分采集，
  不把剩余行伪装成零。动态统计视图未必是原子快照；即使读取结束也不能证明采集间
  未出现或淘汰其他语句。
- `BOUNDED_CANDIDATES`：按配置的有限候选采集，记录筛选、上限和排序；
  只能称“已采集候选的窗口排名”，不能宣称全库 Top N。

记录每批采集的 Target 版本、实例身份和启动代次、数据库/容器、来源、版本、权限、
原生重置/淘汰信息、采集起止与质量。统一行数、字节、超时、并发、单目标和全局配额；
达到预算时停止并产出部分状态，不进行无界全量扫描。周期快照适用于后续窗口，不能
重建此前未采集的历史。采样模式、默认值、存储成本与留存可由管理员调整，任何新增或
变更数据库侧扩展、授权或采样参数须经现有管理流程。

### 4.2 边界、连续性与数值

窗口输入冻结为 `(requested_start, requested_end]`。按目标和采样序列查找
`requested_start` 及 `requested_end` 各自不晚于该边界的最近可用快照；必须
落在配置的最大边界偏差之内，否则报告缺口。显示真实的采样起止、各自偏差、采样间隔、
有效区间和缺口；边界未精确重合时标记为采样对齐区间，不称为精确请求窗口，不做插值。
不得把对齐区间多出的开头或缺少的结尾声称成请求区间。无足够有效快照时可按产品策略
另列累计参考，始终不能关闭窗口缺口。

同一语句同一身份，只对连续、质量合格、源口径一致且实际实例代次一致的相邻快照
计算差值。实例切换、版本/来源变化、缺采超限、字段不可得、计数器回退或已识别的
重置/淘汰都截断相应区间；新出现或消失的记录不能默认从零开始。多段有效区间只对
明确标记的区间求和，显示不连续性和各语句覆盖，不能包装成整个窗口的完整贡献。
全局重置时间、全局淘汰计数或计数器单调只能辅助判断；重置后增长超过旧值、个别语句
重置或淘汰重建可能无法检测，“未检测到”绝不等于“确定未发生”。

对有效样本：

- 执行次数增量 = 结束次数 − 起始次数；总耗时增量同理，执行频率 = 次数增量 / 实际有效秒数。
- 平均耗时 = 总耗时增量 / 次数增量；次数增量为零时显示不可计算，不输出 0 或无穷。
- 可加性计数、I/O、行数与单位必须逐字段声明；已有累计平均值、累计最大值、百分位数、
  规划数及不同计划/实例的值不得未经定义相减或合并。
- 窗口最大值/P95 只来自具备相同统计口径、完整性可说明的逐次记录或可合并分布，
  否则明确不可得。短 SQL 不在活动采样中出现不代表没有执行。

排名按用户选择的同口径指标降序，平值按完整稳定身份排序；不能把不同实例、用户、
Schema 或 SQL 计划无依据合并。结果分开表达：采集模式与可见范围、实际时间覆盖、
连续性、每条语句质量、排序完整性及原因；即使 `VISIBLE_SET` 也仅说明已观测统计源
的可见集合，不保证整个数据库的所有执行或源内部未淘汰条目都被捕获。
零行只能表示合格观测没有可排名记录，不证明窗口内没有 SQL。

窗口合同固定返回 `requested_start/end`、`observed_start/end`、边界偏差、
`valid_intervals`、`gaps`、`candidate_scope`、`source_visibility`、
`continuity_confidence`、`rank_metric` 和逐语句质量。显示层不得仅从单一状态值
推断完整性。完整可见集只表示成功读取所声明视图、权限和采样范围内的当前可见行；
不能证明视图保存了所有 SQL，也不能抹去重置或淘汰不确定性。

窗口质量与任务完成度分开表达，不用一个 `PARTIAL` 混合两种语义：

- `availability`：`UNAVAILABLE / PARTIAL / OBSERVED`，分别表示无可比区间、
  存在断点或不合格区间、在声明的范围内满足观测标准；不等价于数据库全量事实。
- `alignment`：`EXACT / SAMPLE_ALIGNED / OUT_OF_TOLERANCE`；容许偏差内的
  采样对齐可满足用户接受的采样口径，必须展示实际起止与偏差，不称“精确 15 分钟”。
  用户要求精确边界而来源不能提供时，明确该要求尚未满足。
- 候选范围、连续性、可见性及重置/淘汰不确定性保留独立字段和原因；候选截断必须在
  排名标题中说明“已采集候选”，不能用边界合格掩盖候选缺口。

采样持续时间、非原子读取及边界误差不能隐藏；累计参考可用不提升窗口质量。
任务是否完成取决于声明的用户目标及接受口径，不因微小采样偏差永久无法完成，
也不因另一类证据可用就谎称精确窗口已取得。任务状态与诊断置信等级见第 8 节。

同名指标需引擎级定义：PostgreSQL `rows` 是统计视图记录的处理行数，不等同扫描行数；
MySQL `rows_examined`、`rows_sent` 不可直接映射为 PostgreSQL 物理读；Oracle
并行执行、游标生命周期和累计值也应保留原生单位及口径。快照间的统计增量反映该
数据源的计数归属，不必然等于窗口内开始、完成或运行的所有语句。

累计起点按来源提供的可验证语义描述；全局 reset/实例启动不能直接充当单条语句
的确定起点，单条重置、淘汰重建及统计容量边界须单列。不能把“累计参考”统一写成
“自实例启动以来”，也不能用统计起点未知否定已观测计数本身。

### 4.3 存储和交付边界

扩展现有 Workload snapshot/statement 实体及版本化 artifact，保存完整身份、原生计数、
连续性和质量；缺值用 NULL 加来源状态，不能用 0 填充。需要容量测试、目标/时间/身份
查询索引和按保留期清理，避免原始 SQL 和绑定值进入日志或通知。

Ammolite 更新 canonical PostgreSQL ORM/初始化及 acceptance；KBot4 更新 canonical
Oracle DDL、manifest、初始化/受控升级和 acceptance，应用层实现数据隔离与业务唯一性。
业务状态、枚举和组合关系由合同与领域逻辑校验；KBot 不新增 CHECK/UNIQUE 业务约束。
不添加运行时自身 Schema 探测、历史双读双写或未经授权的重建/回填。发布须评估现有数据、
保留与兼容影响；实际数据操作、迁移、重建及回滚分别走审批。

## 5. 三种数据库的适配与计划证据

| 数据库 | 已有可复用的证据 | 目标补齐及不可推断边界 |
| --- | --- | --- |
| PostgreSQL | 语句累计视图、活动、表/索引元数据及自采快照 | pg_stat_statements 不保存历史实际计划；只在可用来源取匹配计划；规范化语句的占位符并非真实绑定参数 |
| MySQL | Performance Schema Digest、活动历史和对象统计 | 历史环形缓冲会覆盖；按 Digest/Schema 匹配，保留查询版本；估算计划不等于生产实际执行 |
| Oracle | GV$SQL、游标、V$SQL_PLAN、DBMS_XPLAN、自采快照 | 按 DBID、实例、容器、子游标和计划绑定；ALLSTATS LAST 只有存在运行时统计时可解释真实行源 |

Oracle AWR/ASH 及 SQL Monitor 按目标配置与合同声明执行现有授权检查；不由数据库
参数或查询成功推断许可证。AWR 快照频率读取实际配置和可用快照，常见默认值不是
固定一小时保证。无授权时使用非 AWR 的可用只读证据并明确缺口；不能越权回退。

计划 evidence 至少保存：引擎、实例/容器、SQL/子游标/计划身份、来源、采集时间、
计划产生环境和参数可用性、计划类型（估算/历史实际/当前实际/人工提供）、行源统计
可用性、截断、脱敏和引用。解析 SQL 对象或目录元数据只表示候选关联，历史上实际访问
路径必须依靠匹配计划或其他直接证据。被采集的计划、SQL 文本和运行时参数按敏感级别
控制查看、脱敏、保留及审计，不将原始绑定值发送给模型或日志。

默认只读查询不重放用户 SQL，不自动启用 PostgreSQL auto_explain、不自动对生产执行
EXPLAIN ANALYZE 或写入配置。普通 EXPLAIN 也可能取得锁或触发规划期函数，必须检查
版本、权限、函数、参数、超时、锁等待和负载。需要实际执行或改变采集配置时，另有
明确用户授权与审批、最小权限、只读保护、预算、审计和回滚；只读事务本身不能保证无副作用。
受限时允许用户提供计划或接入已有采集，来源标注为人工/外部，不升级为已验证执行。

三库共同覆盖的不只是计划：应能按版本与实际权限读取语句工作量、当前会话/事务、
阻塞关系、等待、对象/索引及统计环境，并结合可用历史来源。不同引擎没有某字段时
标记不支持，不用同名字段凑等价。SQL 已结束且历史来源未保存时，不承诺还原过去等待。
匹配计划是判断访问路径的重要依据，不是诊断一切 SQL 问题的前置条件；例如当前锁链、
事务及会话证据可以确认当前阻塞关系，不需要先拿到执行计划。

### 5.1 计划与参数的实际获取路径

不能把“计划缺失”永远留给用户手工补齐；Adapter 应返回能执行的来源、所需前提及
不可得原因，由调查按价值选择：

| 引擎 | 优先复用的已存在证据 | 需要单独策略/授权的后续路径 |
| --- | --- | --- |
| PostgreSQL | 已采集的 auto_explain/慢日志附件、人工或既有报告中的计划，逐项验证匹配；pg_stat_statements 仅提供统计与规范化文本 | 用已核实语句与代表性参数做受控估算 EXPLAIN；确需实际行源时在批准的安全环境/窗口实验。无已存计划时不能假定从累计视图恢复 |
| MySQL | 可见的语句事件/慢日志及已有计划材料；当前执行可评估该版本支持的 EXPLAIN FOR CONNECTION，核验连接和权限 | 对经确认的真实语句/参数做受控 EXPLAIN；实际执行取证另行审批。Digest 不能还原绑定值，历史事件未必包含计划 |
| Oracle | 正确实例/容器的游标计划、DISPLAY_CURSOR 与可用行源；有许可时匹配 AWR/SQL Monitor | 缺游标计划时按批准策略取得估算或受控实际证据；RAC 不可用本地计划冒充远端实例 |

EXPLAIN 等专用动作使用独立的版本化工具合同与风险策略，不能偷塞进只允许 SELECT
的动态查询通道。捕获不到参数时，可询问有权限的用户提供代表性参数/范围，或引用
已经授权保存的样本；不猜占位符值、不自动执行规范化 SQL。使用假设参数得到的计划
必须标为实验，不能解释过去真实执行。参数原值仅在受保护执行边界内按必要性使用，
传给模型的是类型、范围/分布摘要和不可逆脱敏信息；敏感分布本身也须访问控制。
受控估算有锁/函数/负载风险，实际执行另有风险；两者都不能仅因“诊断需要”跳过审批。

## 6. 可发现的信息资源与受控查询

### 6.1 当前基础与待补齐边界

以下是本次修订核对的实现基础，不是对全部环境已接入的承诺：

| 信息资源 | 可复用基础 | 本设计要求补齐 |
| --- | --- | --- |
| 数据库直连 | 三库 Tool Catalog、Target 只读执行、版本能力；Oracle/PG 受控动态 SELECT | 查询实际权限/视图/字段与成本边界；补齐 MySQL 同等安全的长尾只读查询能力 |
| 时序与事件 | Prometheus、Zabbix、OEM Adapter；标准 Metric/Profile；受控 PromQL | 按实际绑定与能力发现可用序列、标签、语义和覆盖；不将 Profile 清单作为诊断上限 |
| 日志 | Loki Adapter、绑定范围内的受控日志查询 | 识别已采集的慢日志、错误/死锁日志、应用日志及其身份/时间关联能力；有 Loki 不代表这些日志都已采集 |
| 计划与材料 | 各引擎目录工具、报告、artifact、受限上传检索 | 匹配 SQL/游标/参数/时间，区分估算、实际、人工来源及可信等级 |
| 主机、拓扑、应用链路、发布与配置变更 | Diagnostic Source 端口已有 host.inspect、topology.resolve、change.query 等抽象，但当前 Adapter registry 未注册相应实现 | 先定义并接入受控 Adapter、授权和审计再启用；APM/发布平台接入不能仅凭端口存在宣称完成；已采集主机指标仍可经监控读取 |

复用 `ports/diagnostic_source.py`、`adapters/diagnostic_sources/registry.py`、
`application/investigation/discovery.py` 和现有 Tool Catalog。不复制第二套源配置、
凭据或查询执行器。两仓库逐项验证实际支持；外部能力只有在相应工具/Adapter 已注册、
绑定、授权、连通和语义验证均成立后才作为可执行动作。缺少某类可选资源不阻止其他有效路径。
基础交付必须打通三库直连、已接入监控与日志、计划/元数据和既有材料；未接入的
APM/变更/主机操作分别列明后续接入范围，不能作为基础功能验收的虚构前提。

### 6.2 能力快照与发现

建立版本化 `SourceCapabilitySnapshot`，由服务端从受信配置与受控探测构建：

- 来源/Adapter/版本、绑定 Target 与实际实例、可关联 host/service、许可与实际可用权限；
- 可查询内容与维度（语句、会话、事务、对象、主机、应用、事件等）、查询接口和策略引用；
- 当前/历史时间能力、留存、采样周期、覆盖、延迟、已知时钟偏差与时间不确定性；
- 可见范围、数据质量、源血缘、支持的身份键及关系解析能力；
- 限行/字节/序列/点数/超时/并发预算、访问风险及需要额外授权的操作。

发现首先读取已有绑定、目录和缓存元数据；仅在具体证据需求出现时做受控探测，不能
每轮遍历所有源、全量枚举系统目录或扫描指标标签。缓存有 TTL，并包含权限、Target、
版本和绑定版本；每个动作执行前重验授权、许可、范围及当前可用性。冻结能力快照
用于审计，不等于许可不会撤销。模型只能选择服务端提供的 source_ref/策略，不传凭据、
地址或任意端点。业务系统多 Target 或数据库到主机/应用关系不明确时先核验映射，
不因 IP 相同或名称相似就跨库、跨服务或跨租户关联。

`AVAILABLE / NOT_CONFIGURED / UNSUPPORTED / FORBIDDEN / UNREACHABLE / STALE`
等能力状态与一次查询的 `SUCCESS_EMPTY / TRUNCATED / ERROR` 等结果状态分开；
0 行只说明相应范围的有效查询未返回对象，不能自动视为无问题或源不可用。

### 6.3 标准目录与长尾查询的协作

Metric Catalog/Profile 继续是标准指标语义与页面定义的唯一来源，Tool Catalog 继续
提供版本化、安全的常见动作；二者是复用和效率机制，不是 Agent 能观察世界的固定边界。
复用 [原生监控设计](aiops-monitoring-dashboard-integration-detailed-design.md) 的
标准定义，同时允许针对具体证据需求发现真实源并查询目录外信息：

1. 常见证据优先复用已验证目录，避免同义重复查询；目录无法表达需求时选择可发现、
   有授权且风险可控的查询能力，不要求先发布一个 Metric Code 才能调查。
2. 监控和直连数据库并列互补。历史趋势通常选时序/历史源；当前锁链、配置和对象细节
   通常选直连；同一问题可组合使用，不存在“监控不足才允许查数据库”的硬性先后。
3. 时序长尾查询先核实真实指标/标签、单位、类型、采集方与重置语义；不得猜测名字后
   把空值填 0 或用未经证实的 rate/聚合公式。PromQL 继续走现有 AST、精确 Target
   绑定和配额；Zabbix/OEM 只使用各自已实现能力，不伪装支持任意 PromQL。
4. 直连长尾查询复用服务端冻结的引擎/版本策略：AST、实际授权目录/视图/字段、允许
   函数、参数绑定、只读保护、成本上限及脱敏。禁止 DML/DDL、锁定/任意过程、任意文件/
   网络访问和未批准函数；不能以“SELECT”或只读事务为无副作用保证。MySQL 须补同等
   守卫及回归后启用，不能直接复制 Oracle/PG 策略。业务表数据抽样、真实 SQL 重放、
   主机命令及采集配置变化不在默认诊断授权内。
5. 日志只查受信绑定、时间和受控过滤范围；记录采样/丢弃/轮转/截断，不把日志中的
   SQL、命令或指令当成 Agent 指令。主机/API 等新源亦必须有能力策略和执行器，
   不能让模型借“需要补证”发起任意 SSH、HTTP 或 Shell。
6. 新观察保留原生语义与血缘；稳定、复用价值高的查询经评审与测试后再沉淀为目录或
   Playbook，不自动修改配置，不在页面生成第二套指标定义。

## 7. 问题与假设驱动的调查、诊断与解决方案

### 7.1 自适应调查闭环

目标工作流是“确定任务/对象 → 发现所需资源 → 提出问题与假设 → 选择取证动作 →
关联证据并检验 → 收敛诊断、方案和验证”，不是固定的“统计 → 计划 → 对象”流水线。

负载/Top SQL 原因调查可在预算内选择多条有区分力的语句、阻塞者或相关工作负载，
联合分析调用、资源与竞争关系；不只盯累计排名第一，也不逐条机械运行全部工具。
选取依据和未覆盖范围可见，采样之外没有排名的阻塞事务同样可能是主因。排行、单 SQL
和负载调查共用证据模型，但保留各自完成标准，不能中途偷偷扩大或替换用户任务。

复用现有 InvestigationPlan/Action，增加下列结构化语义；不另建平行任务系统：

| 对象 | 必填语义 |
| --- | --- |
| DiagnosticQuestion | 用户目标、症状、SQL/负载范围、时间、已知事实与来源、完成标准、已接受的证据口径 |
| HypothesisCase | 可验证的原因、适用时间/范围、支持与反证预测、替代解释、现有引用、状态及尚缺的关键证据 |
| EvidenceNeed | 要回答的具体问题、对哪个判断有影响、必要/可替代性、所需精度与时间、可用源及成本限制 |
| InvestigationAction | 对应需求、受控工具/源/参数、预期产出、依赖、风险、超时、可能改变的判断与停止条件 |

一次循环：

1. 从已核验身份、可用历史证据与当前症状提出少量最有区分力的问题；既有 Playbook
   提供经验路径，模型可提出目录未预列的原因，不局限于预设“CPU/IO/索引”分类。
2. 按需求选择能区分原因的证据，权衡相关性、时效、可靠性、预期信息增益和成本。
   不要求虚构精确收益分数；选择理由可解释、可审计即可。独立低成本动作可并行，
   SQL/对象等未确定时不提前运行依赖动作。
3. 执行器检查安全、授权及剩余预算；结果先登记为 Evidence，再参与计算和关联。
   新信息可能支持、反驳、缩小、拆分或替换原假设；不为维持原结论选择性引用。
4. 若新问题来自证据且能影响用户目标，补做高价值动作；没有可执行的新需求时收敛，
   不因缺口数量未归零、Finding 为空或未拿到计划就重复规划。

停止条件：完成用户目标；关键判断已充分且继续查询不会改变建议；剩余关键证据在
当前权限/历史/预算内不可得；达到 deadline/动作与重试预算；或确需用户消歧/额外授权。
不可追补的历史与未配置采集不能通过重复采样补齐。可短时重采的活动问题必须有新的
观测价值和受控时间，不以新时间戳包装同一查询无限循环。

模型负责提问题、提假设、选择候选动作、跨证据推理及解释方案；服务端负责权限、
范围、查询安全、精确计算、质量与引用校验和收敛。不能把模型限制成只解释固定摘要，
也不能允许模型把新假设直接登记为已验证事实。

### 7.2 可扩展证据模型与关联

版本化 `SqlEvidenceBundle` 是按需求组织的受控投影，不是“几个字段填满才可诊断”
的门槛；可记录任意已支持来源的类型化 observation：

| 部分 | 内容及必填质量信息 |
| --- | --- |
| subject/task/window | 已核验 SQL 与关联资源、任务、请求/实际时间、接受口径和质量 |
| observations | 原生/标准指标、时序、日志事件、会话/事务/锁链、计划、对象、配置、应用或变更材料等；kind/schema_version、值或 artifact_ref、单位/测量语义、时间、范围、来源血缘、权限与质量 |
| relationships | SQL↔session↔transaction↔object↔instance↔host↔application 的有类型关系；身份键、有效时间、direct/verified/inferred/unresolved、证据及关联置信度 |
| derived_facts | 服务端确定性计算值、输入字段引用、公式/版本、适用范围与误差 |
| hypotheses/assessments | 待验证原因、已支持/已排除范围、替代解释和反证，不污染原始事实 |
| gaps/actions | 缺失或冲突对哪个判断的影响、可重试性、替代源、下一步及责任方 |

新增证据种类需注册 schema 与语义验证，不接收无来源的任意 JSON 为事实；
新原生指标可以使用通用数值/时序类型及元数据，不要求每个指标重新硬编码分析规则。
按问题分批检索和压缩投影，保留原始 artifact，不一次把全库表、所有日志塞入模型。
跨轮继承原观察及适用时间，不继承上一轮推理为事实；“沿用”不等于不需检查新鲜度。

关联与解释必须遵守：

- 精确 SQL/实例/用户/Schema/游标、session/transaction、对象与 host/service 映射优先；
  仅文本、对象名或相邻时间相似只能生成候选。SQL 解析处理搜索路径、同名对象、
  视图、CTE、函数和分区；无法唯一解析时按需查目录，不扫描全库。
- 区分采集时间和事件/测量时间；窗口、采样粒度、重置与时钟偏差不匹配时不可精确
  关联。当前配置、索引和计划不能自动代表历史状态；当前无活动不能否定历史慢 SQL。
- 同源 Exporter 与直连读取同一计数器不算独立互证；累计总耗时也不是独占 CPU 时间，
  并发执行时不能简单除以墙钟时间声称 CPU 占用或系统贡献率。
- 数据库/主机指标单独不能归因某 SQL；结合语句身份、等待、时间、资源映射及其他证据
  可支持资源竞争或受害关系。区分“SQL 导致压力”“SQL 被其他工作负载影响”及共同原因。
  时间重合只支持相关性，不自动证明因果。
- 对象级顺序扫描不直接归因目标 SQL；共享块命中是访问次数，不是独立页数或物理读。
  无业务 SLO 不能仅凭平均 23ms 断言正常/异常；但明确死锁、报错或锁链等事实不依赖
  延迟 SLO 才能判断，事实确认和影响严重度分开。
- 分区父表的大小/存活行估计为 0 可能与数据位于子分区有关；不可直接解释为全表为空、
  统计陈旧或“证据无法解析”。零分母比率标为不可计算并按语义处理，不能作为失败卡片；
  修改量低也不能单独证明统计分布准确或所有分区不需维护。
- 负证据要求来源覆盖、身份/过滤和时间足够；采样未捕获、权限不可见或保留期过期不是
  原因不存在。矛盾证据登记冲突，先核对身份、单位、时间和血缘，不以多数投票消除。
- 所有结论可还原到 observation/行/字段及公式；证据权限失效时重新授权投影或拒绝查看，
  不借跨轮引用绕过访问控制。SQL/参数与日志内容不可信，按敏感级别脱敏后才进入模型。

### 7.3 诊断判断：证据强度而不是固定指标阈值

输出 `SqlDiagnosticAssessment`：每条判断记录问题、事实或原因、影响/受影响对象、
适用时间、支持证据、反证/替代解释、剩余不确定性及建议引用。区分：

- 已观测事实：能直接引用的数据或关系，例如当前阻塞链、计划节点、错误事件。
- 有证据支持的解释：存在机制与匹配证据，说明为何更支持该解释、仍有哪些替代原因。
- 待验证假设：列出能区分原因的下一步，不包装成已确认根因。
- 当前无法判断：明确阻止哪个判断，不写成整轮无价值或源中不存在问题。

判断等级按结论逐条给出，不能全篇盖一个“证据充分”章。既无匹配计划也无其他等价
直接执行证据时，不能断言扫描路径，但不妨碍确认当前锁阻塞；只有计划也不能断言业务
调用放大或过去所有参数都如此。
确定性守卫验证计算、身份/时间/范围/引用和安全，不宣称能机械证明模型所有因果判断；
上线需用专家标注和对照场景检验推理。对无法支持的强因果断言降为假设或阻止发布，
保留被拒绝理由与相关证据，不用修改措辞掩盖事实缺口。

校验优先使用已有策略与类型化证据，不为每条回答强制串行再调一轮模型“证明根因”；
必要的复核动作同样须有明确价值并计入预算，避免把质量治理重新变成耗时循环。

常见路径用于启发与测试，不是穷尽原因或每次必跑的框架：

| 问题/证据线索 | 可按需组合的信息 | 可形成的判断与处理方向 |
| --- | --- | --- |
| 总耗时高，单次延迟未同步升高 | 窗口调用量/延迟、可比基线、应用调用/重试、批任务与并发 | 区分业务增长、重复调用、重试放大；按证据选择缓存、合并请求、退避或并发治理，不预设建索引 |
| 单次退化、参数差异或计划变化 | 历史/当前匹配计划、代表性参数范围、统计/索引、变更时间与等待 | 分析访问路径、估算偏差、参数倾斜或发布回归；条件化改写/索引/统计维护/回退 |
| 活跃 SQL 等待或事务拉长 | 当前会话、阻塞链、事务年龄、锁对象、应用事务与可用历史 | 确定当前阻塞者/受害者；先处置事务边界或竞争，不先要求计划；终止会话须另行审批 |
| CPU/IO/内存/存储压力或队列增加 | 语句工作量/等待、主机与数据库时序、其他负载和映射 | 区分本 SQL 高消耗与外部竞争；评估限流、批任务错峰、容量或访问优化，不能单凭高命中调缓存 |
| 报错、超时、死锁、连接异常 | 数据库/应用日志、事件、事务/锁、连接与重试信息 | 诊断错误链路、连接/事务管理或放大效应；缺历史日志时不假造过去事件 |
| 当前没活动，用户投诉历史变慢 | 已有语句快照、慢日志/采样、监控、历史计划/报告与变更 | 调查历史窗口；若确无历史来源，给已确认边界与后续采集方案，不循环查询当前活动 |

### 7.4 解决方案是交付物，不是统一“再补证”

每条 `Recommendation` 必须关联诊断/假设、适用时间与对象，给出：

1. 为什么做：要解决的原因/影响、证据、反证和适用条件。
2. 做什么：具体动作或条件化方案；区分立即缓解、根因修复和必要的验证/补证。
3. 如何安全做：目标与版本、前置检查、权限/审批、执行责任方、风险/副作用、变更窗口。
4. 如何证明有效：可比窗口/负载/参数与基线、成功指标及接受标准；同时观察吞吐、错误、
   业务影响和写入/资源成本，避免只让单条 SQL 快却损害整体。
5. 如何退出：停止条件、回滚/恢复方式和验证；不能完全回滚的动作必须明示恢复限制。

方案可涉及索引/SQL/统计信息，也可涉及调用放大、重试策略、事务边界、并发、批任务、
资源容量或发布回退。只能解释支持该方向的证据，不能把经验清单原样当最终方案。
未确认原因时仍可提供明确条件与验证步骤的候选方案，不必全部退化为“缺计划请补充”；
但不能声称未经验证的改动必然有效，不能编造收益百分比。

可在对象、引擎版本与安全前提核实后给出具体查询或变更草案；生成建议不等于获准执行。
只读诊断可展示标为“待验证/待审批”的方案及风险，不因没有执行权限就一律隐藏措施。
实际执行仍走现有逐项审批、最小权限和审计；不自动执行草案，不自动结束事务、
建索引、改参数或开扩展。草案仅在显式执行流程重新验证后才可成为工具输入。

验证指标必须与来源相符：窗口平均耗时用总耗时增量/次数增量，累计 max 不相减，
P95/P99 仅在分布/逐次记录可支持时使用；必要时以可用的平均、吞吐、等待或错误率
定义验证。只做观测而无变更不需要虚构回滚语句；有不可逆影响时不能声称“删掉即可”。

SQL 改写建议还须列明语义保持条件及正确性验证，覆盖 NULL、重复行、聚合/排序、
时区和事务一致性等与该语句相关的风险；不能只验证耗时。索引建议基于已核实的
定义/有效性、选择性和访问证据，避免重复索引或只优化读而忽略业务写入成本。

### 7.5 输出契约与行为示例

排名回答交付排名、时间/范围、主要工作量特点及选择入口；单 SQL 回答先给核心判断与
影响，再给关键依据、最有价值的措施、验证及真正影响判断的缺口。数值表是证据摘要，
不能替代诊断；有可信原因时必须解释机制，而不是只列计数器和风险声明。

- 高频 SQL：若可比窗口显示执行次数明显增长、均耗近似稳定，且应用证据支持重试
  放大，则解释调用增长的影响并给退避/去重等针对性方案；无应用证据时只确认
  工作量变化，重试为待验证原因，不用累计排名直接判定调用放大。
- 无计划的当前阻塞：若会话、事务与锁链确认阻塞边及时间，明确阻塞者、受害者及
  当前影响，建议核查/缩短事务并给处置风险；历史缺失只限制历史归因，不阻止该诊断。
- 有匹配实际计划：解释相关节点、loops、扫描/返回差异、参数与对象，并用索引/统计/
  选择性证据评估具体优化；单计划不代表所有参数，最终措施包含同负载验证和写入成本。
- 只有累计统计：如实说明画像与计数边界，只列高价值待验证原因及安全措施；不宣称
  当前异常、不算伪窗口，也不把“Finding 为空”当开场或解决方案。

示例描述行为与所需证据，不能把示例中的故障预写入真实数据库的结论。

## 8. 执行状态、预算与展示

### 8.1 时延与执行治理

复用现有编排、工具和 worker，禁止为单 SQL 再叠加一轮固定摘要/重复完整规划。
设全流程持久化硬 deadline，覆盖排队、模型、工具、重规划、组合及终态提交；各下游
受剩余预算约束。交互默认预算目标为 90 秒，可受控调整；为汇总及可靠终态保留预算，
目标先在 15 秒内展示已确认基础进展，不将心跳当有效取证，不保证外部系统必定达标。
排队时亦由独立超时/租约机制收敛，不能等 worker 领取后才开始计时。

每轮有可配置的动作数、并发、token、查询成本和重试预算；按需求终止而不是为用完轮数
继续查询。动作去重键含实例/Subject、来源/策略版本、查询与参数、观测窗口和所需新鲜度；
只有新证据需求或允许的短时重采才能重做。不可重试的历史缺口/未授权直接停止该路径，
暂时性故障有限退避，重试也计入全流程预算。关闭与本任务无关的通用采集，PG 不应因
Oracle Alert Log 或无关复制指标缺失而延时或被判诊断失败。

支持端到端取消、驱动查询终止/资源隔离、租约释放、幂等收敛与审计。上层 timeout 不代表
底层查询已结束；必须验证连接/事务/任务回收。超时后禁止继续创建动作或追加第二份回答，
迟到结果单独审计。预留结构化事实的安全降级输出，模型超时也能交付已取得的可用结果。

确需用户消歧/审批/提供材料时进入 `WAITING_USER`，结束当前自动运行预算，显示具体
请求和期限；用户回应后按授权创建续跑预算，不能把人工作业等待显示为数据库运行。
挂起超过期限或用户跳过时按已有证据终结；deadline 机制需区分挂起与运行，不能后台
无限等待，也不能在等用户时继续取证。
客户端断线不自动等于取消，重连可取同一结果；有明确取消请求时收敛为取消终态。

### 8.2 三个独立的质量维度

| 维度 | 判定与呈现 |
| --- | --- |
| 任务执行 | `COMPLETED / PARTIAL / FAILED / CANCELLED` 为终态；`WAITING_USER` 为挂起状态。按用户完成标准判定；外部能力不支持或证据不足不是系统崩溃 |
| 证据质量 | 每个窗口/来源/结论独立给覆盖、对齐、候选范围、时效及缺口；不压成一个“充分/不充分”布尔值 |
| 诊断置信 | 事实、支持解释、假设或无法判断，逐项表达；任务完成不代表所有根因已确定 |

用户只要排行且已取得接受口径的结果，可完成；用户要精确窗口却只取得累计参考则部分
完成。用户要求确认根因而只有画像时同样部分完成；无计划但当前阻塞诊断与方案已充分，
可完成该目标。可选主机/APM 没接入不自动变部分完成。真实系统错误且无可用结果才标
失败；零行可能是成功的空查询，也可能不足以回答历史问题，按目标区分。
所有原因码保持稳定，不能用调整状态掩盖缺口。

### 8.3 结果展示与可观测性

SSE/非流式消费同一版本化 Assessment/Recommendation 与展示投影；进度说明当前回答
什么、为什么需要及取得什么，不泄露凭据/绑定参数。状态转换、幂等和租约保证只产生
一个终态及一份权威结果，重试/重连不重复渲染。

Top SQL 使用紧凑表格显示 SQL 片段、执行次数、总/平均耗时等与本次排序相关字段；
标识可复制、完整脱敏 SQL 可展开，其他技术列按需查看。单 SQL 使用详情与诊断视图；
不因来源工具名是 statement.top 就重新显示整个 Top SQL 表，也不重复“有数据累计表”
与“空活动 Top SQL 表”。其他范围的观察保留于证据区并正确命名。

按结论与用户影响排序正文，不用内部 Finding 数量组织回答；没有 Finding 不写
“本轮 Finding 为空/无卡片可解释”。Finding 是可选的诊断投影，不是回答门槛。
字段有稳定名称、单位与维度，例如数据库/用户/top_level，不能把它们展示成“观测字段”。
缺口按问题及根因合并，区分真正影响建议的关键缺口和无关/可选资源；原始证据仍可查。
模型/工具耗时、队列等待、重试、去重、token、覆盖、实际取证收益、取消回收和终态
均有脱敏记录，用于查清一次 500 秒究竟花在哪里。

## 10. 验收：能区分原因、给方案并验证

### 10.1 正确性与安全矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| PostgreSQL 同 query_id 多库/用户、超过 JS 安全整数范围 | 身份/字符串精确，不跨用户、实例或库串联 |
| Top SQL 跨多轮选行；会话中此前诊断过另一 SQL | 沿用所选行和授权，不被旧问题劫持；单 SQL 不重列主表 |
| 采样偏移、缺采、重置/淘汰、切库、候选截断 | 真区间/质量，无伪增量；正增长也不证明未重置；采样对齐不冒充精确窗口 |
| 新 SQL 不在累计前 N、事务控制语句、采集自身 SQL | 公开筛选/可见范围与遗漏；不误把有限候选说成完整历史 |
| 累计 max/P95、零执行、并发累计耗时 | 不相减极值/百分位，不除零，不从总耗时直接推 CPU 使用率 |
| 同 SQL 多计划、估算/实际、不同参数/时间 | 不错配；无计划不伪造访问路径，也不阻止其他有证据的诊断 |
| MySQL Digest/Schema、历史缓冲覆盖 | 不跨 Schema 聚合，不把环形记录当完整窗口 |
| Oracle RAC/容器/子游标、AWR 间隔/无许可 | 绑定真实范围，不假设固定一小时，不越过 Pack 授权 |
| 同源指标、映射歧义、时钟偏差与冲突证据 | 不虚构独立互证/因果；保留冲突并优先查范围、时间、单位 |
| 分区父表 0 估计、零分母、过期或低修改量统计 | 无伪解析失败/陈旧告警；按父子分区和真实统计语义判断 |
| SQL/日志/材料含恶意指令；目录外查询 | 数据不成为指令；AST/权限/成本、租户隔离、脱敏与审计有效 |
| 无源/无权限/空查询/超保留期 | 正确分型，不填 0、不伪根因、不反复重试不可补缺口 |
| 取消、挂起、队列超时、模型/工具挂死、断线重连 | 有界收敛、底层资源回收、单终态；SSE/非流式一致 |

### 10.2 真实运维诊断场景

使用真实引擎和可核验负载构造下列对照；故障注入必须另行授权，不能在生产自行制造故障。
相近指标不同原因必须导致不同调查路径和建议，不能只让模板多填几个字段。

| 对照场景 | 取证与方案验收重点 |
| --- | --- |
| 总耗时同高：高频稳定 vs 单次退化 | 分开调用增长/延迟退化；有可用应用重试证据时追重试，不都建议加索引 |
| 相似慢 SQL：锁阻塞 vs 扫描低效 | 前者依锁/事务证据，后者依匹配计划/对象；无计划仍能给正确阻塞处置方案 |
| 相似 CPU 高：本 SQL 放大 vs 其他批任务竞争 | 联合等待/负载/主机与映射，区分来源与受害者，避免归因倒置 |
| 同 SQL：参数倾斜/计划变化 vs 业务量变化 | 选择匹配参数/计划或基线/调用证据；相应改写/回退或调用治理，不混原因 |
| 延迟近似：应用重试/连接等待 vs 数据库执行 | 对齐应用与库耗时/事件；不把端到端延迟直接当数据库耗时 |
| Top N 高耗时语句 vs 排名之外的长事务阻塞者 | 允许多 SQL/事务关联，找到真实竞争关系，不把排行第一当作必然根因 |
| 监控缺指标但直连可用；数据库无当前活动但有历史日志 | 自动使用能回答问题的授权来源，不把监控或活动快照设成唯一门槛 |
| 无匹配计划但有死锁/错误；无任何历史 | 前者给事件/事务诊断及措施；后者诚实部分结果，停止不可追补查询 |
| 有匹配实际计划且有可验证低效路径 | 给针对性措施、风险、审批草案与可比验证，而不是只有“请补计划” |
| 可选 APM/变更源未接入，或只有累计统计 | 未接入不伪造；能回答的任务正常完成，不能回答窗口/根因的明确部分完成 |
| 自采快照缺失但有合格历史源，或只有采样日志 | 前者按真实时间/授权获得历史证据，后者限定为采样范围；不强制走双快照路径 |

每个用例预登记环境/版本/许可、可用源、故障真值和可接受解释、关键证据、错误归因禁项、
预期措施与验证条件；运行时隐藏故障标签，防止按测试名称猜答案。记录实际发现的资源、
动作选择、原始 Evidence、计算、判断、建议和最终 UI。由 DBA 复核机制与措施，不能仅
用“出现预期关键词”或模型自评判通过。根因未必唯一，应接受有证据的替代解释，不强行
要求与预设标签完全同文。

### 10.3 闭环、性能与交付门禁

- PostgreSQL、MySQL、Oracle 分别完成真实业务读写下的基本路径，源端事实、快照、
  推理和 UI 可追溯；历史计划、AWR、分位数及额外 Adapter 按版本/授权单列能力矩阵。
- 在预登记的可诊断用例中，必须给出有依据的原因、具体或条件化措施、成功标准与风险；
  不能全部以部分结果、补证清单或固定“缺 SLO”免责。无法诊断的用例必须如实限定。
- 在授权测试环境对至少一个代表性措施做受控变更与同负载前后比较，验证延迟/吞吐/
  等待/错误和副作用；无效果也必须正确识别，不以累计值上涨当优化成功。无执行权限
  时验证方案草案和审批边界，不能宣称已执行；实际变更证据作为相应发布验收门禁。
- 单元/契约/架构/故障注入与真实 UI 测试共同覆盖；单测或跨仓库对齐检查不是诊断有效
  的证明。回归集纳入此前 SQL_ID 误校验、重复卡片、漂移到旧 SQL、错误累计起点、
  无关 Finding 前言、对象统计误归因和无限重规划等反馈。
- 测量排队、模型、工具、重规划及汇总各段耗时、P50/P95、完整/部分/失败率、
  查询开销、保留空间、并发和取消回收；分任务/场景报告。默认 90 秒目标需真实验证，
  包括正常场景有用答案在预算内交付及异常场景按 deadline 收敛，不能用大量立即
  PARTIAL 刷时延，也不能容许静默运行 500 秒。超预算异常有告警与定位证据。
- 主设计、监控设计、产品入口和当前边界文档保持一致；仍未实现的内容继续标为目标。
  文档提交本身不启用采集、不部署、不修改数据库、不执行用户 SQL。

本设计的完成标准不是“永远有根因”，而是同一受控引擎能随可用证据选择正确调查路径，
在有证据时给真正有针对性的诊断与解决方案，在无证据时准确停在边界，并能通过同负载
验证区分“措施有效”“无效或有副作用”。
