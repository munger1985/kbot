# AIOps 诊断案例的 KC 入库与检索定制设计

日期：2026-11-03。状态：本次案例定制代码与本地回归已交付；真实环境测试由用户手动执行。
不代表真实模型／KC 索引、召回排序质量或发布／撤回闭环已经验收。
关联：[工作、报告与知识资产设计](../product/aiops-work-report-knowledge.md)；
[修改计划](../operations/aiops-output-jobs-implementation-plan.md)。
Ammolite 与 KBot4 同步采用。用户要求案例像运维手册一样在通用 KC 上做业务定制，不另建检索系统。

## 1. 核心决定

案例不是“把会话报告 PDF 上传到通用知识库”。案例是 AIOps 拥有的结构化经验资产，
从有效调查记录提炼，经来源复核与脱敏后形成可索引的案例知识投影，交给现有 KC 入库、解析、索引和引用。
案例草稿可以先完成索引，但只有经人工审核发布、且来源与权限仍有效的确切版本才能进入 Agent 检索。

采用“同一 KC 底座，两类业务适配”：手册定制提取规范与操作卡，案例定制提取真实排查路径、
措施效果和适用边界。两者共用解析、词法／向量检索、精确 Revision 和 Citation Pack，
不共用一套无差别的正文生成、分类判断和内容质量规则。

| 责任 | AIOps | 通用 KC |
| --- | --- | --- |
| 事实和资格 | 调查 Claim、证据、处置、效果、来源当前有效性 | 不判断真实故障是否解决，不升级 VERIFIED |
| 内容组织 | 案例 Profile、知识投影、脱敏、适用范围、失败教训、版本血缘 | 保存精确原文，结构解析、语义单元与引用定位 |
| 发布和权限 | 草稿／审核／发布／退役、Agent 范围、安全级、源撤权 | 执行可信精确 Revision 范围，不扩大到整个 Collection |
| 检索 | 业务候选资格、适用性、用途和安全提示、引用呈现 | 通用 Discovery／Evidence、词法和向量召回、原文定位 |
| 反馈和修订 | 复用反馈、人工修订、来源失效和精确撤回 | 确切索引版本状态、重处理和撤回接收回执 |

不得在 KC 硬编码 Oracle 故障词、案例成功条件或 AIOps 审核状态，也不新增案例专用向量库或平行 Agent。

## 2. 开工代码基线及缺口

本节保留本次开工检查的依据，不代表下列缺口仍全部存在；当前实现与验证记录以修改计划第 6 节为准。

两仓已有 contracts/knowledge.py 的 DiagnosisCaseProfile（OPS_DIAGNOSIS_CASE.v1），
operations_knowledge.py 的 _diagnosis_case_markdown、CASE_COLLECTION 和知识检索，
case_closure.py 的多轮直接收口，以及语义脱敏、精确 Revision 登记和索引对账。

当前 Profile 已保存问题特征、环境、结论、动作、验证、适用条件、禁忌和来源。
当前 Markdown 主要输出问题、环境、原因摘要、动作和结果，尚不能据此宣称已经完整表达
各步检查、支持／反证、动作与效果逐项关系及片段级引用。
不能因为内部 source 字典包含 Claim ID，就假设 KC 正文和返回 Citation 已保留这些语义。

当前 validate_closure_sources 还检查整个会话的活动轮次和总轮次数，处理时重新调用
_conversation_case_context 也读取当前会话。异步化不能原样套用这一门禁：
提交后追加无关轮次不应让任务失效，须改为核验冻结所选来源并处理后续反证／替代关系。
来源被实际推翻、撤权或原件变化仍然阻断；不是取消来源校验。

案例目前通过固定 diagnosis-cases 资源定位，与用户创建的手册知识库并非同一种配置身份。
KBot 有初始化工件；本轮未在 Ammolite 的规范初始化代码中找到同名资源登记，不能据此假定运行环境已具备。
两仓均须验收案例 Collection 的可信 Domain 绑定、明确模型配置及 Agent 来源范围，
不能从“手册已配置成功”推定案例必然可用，也不能隐式借用手册或 Agent 模型。

当前两仓 operations_knowledge.py 的 search 路径以 request.max_results 限制
list_published_candidates，之后才调用 KC discover／retrieve_evidence。
最终结果数不应同时作为入围候选数；这会在正文召回前排除其他可能相关的发布版本，
与完整知识范围检索的目标不一致。本轮仅确认该代码缺口，未执行真实召回评测。

## 3. 与手册定制的区别

| 维度 | 运维资料／手册 | 诊断案例 |
| --- | --- | --- |
| 权威原件 | 用户文件和确切文档版本 | 冻结调查、实际动作／验证、人工陈述及各自来源 |
| 结构化内容 | 主题、版本、前提、规范、操作步骤与原文定位 | 问题特征、环境、有效检查、原因强度、措施与效果关系 |
| 入库前处理 | 批准原文后按现有流程做标签、解析和操作卡提取 | 核验来源、提炼结构化经验、脱敏、编译知识正文 |
| 主要检索意图 | 怎么操作、规范是什么、命令或参数出处 | 相似问题怎么查、哪些措施有效／无效、环境是否适用 |
| 关键约束 | 命令必须源于原文，不由模型补写 | 建议不冒充执行，改善不自动证明因果，失败经验不推荐执行 |
| 发布 | 保留现有资料审核与解析后发布流程 | 案例草稿处理就绪后仍须人工发布审核 |

上传的复盘文档仍先作为资料来源；成为案例须走案例核验和审核，不能伪装为平台实测。
为案例增加业务投影和处理策略，不要求用户重新选择技术 Collection 或新增一套配置菜单。

### 3.1 定制范围与复用边界

业务上区分“资料”和“案例”，技术上共用现有 KC，但不能复用成一条没有类型区别的上传流水线：

| 定制环节 | 资料适配 | 案例适配 | 复用的公共能力 |
| --- | --- | --- | --- |
| 输入与原件 | 用户文件、确切原文版本 | 冻结调查、实际动作／效果与人工来源 | 文件受理、哈希、版本与幂等 |
| 知识结构 | OPS_MANUAL_PROFILE.v1、OPS_PROCEDURE_CARD.v1 | OPS_DIAGNOSIS_CASE.v1、检查条目、逐项措施效果、知识投影 | 受控结构解析、CONTENT／SUPPLEMENT |
| 可复用单元 | 有出处的规范与操作步骤，附前提、风险和回退 | 有出处的检查路径、措施效果和失败教训，附适用与禁忌 | 词法／向量召回、Locator、精确正文引用 |
| 可用性判断 | 原文及标签审批、解析和现有发布规则 | 来源有效、脱敏、索引就绪，再经人工发布 | 精确 Revision 状态、业务 Registry 与检索范围 |
| 使用与反馈 | 规范引用、原文纠错、版本更新 | 相似性解释、现场差异、有效／无效反馈与再审核 | 同一 Agent 入口、权限、版本追溯和撤回 |

案例定制主要放在 AIOps 应用层；KC 继续处理通用文档和索引合同。不要把案例全部字段直接作为
无结构附件上传，也不要复制一份手册提取器后仅改名。检索返回必须保留知识类型，不能把资料原文、
历史案例效果与本次现场观测合并成同一种证据。

案例使用独立固定资源 diagnosis-cases，与资料库隔离处理及版本范围；“独立”不表示第二套 KC 服务。
案例模型配置必须有自己的显式证据，手册模型已配好不代表案例可用。现有配置入口是否真正能够
管理该资源须作为实施项核验，不能只因后端存在配置方法就宣称已具备完整配置路径。

当前后端已提供独立的 /operations-knowledge/case-collection/models 读写合同，
显式要求 parser_llm、retrieval_llm、embedding，不要求案例配置 OCR／视觉模型。
模型可用性复用现有目录校验，绑定变更仍受 KC 向量模型不可变及并发规则约束；
读取的 CONFIGURED 只表示必要绑定齐全，不等于模型调用成功、索引就绪或业务发布。
资源缺失或策略不适配须明确诊断，不在会话请求里自动初始化，也不静默改写管理员策略。
固定资源规范初始化、定向补缺及现有管理 API 的维护说明已补齐，见
[案例资源初始化与模型维护](../operations/aiops-case-resource-maintenance.md)。
保持原配置表单不变，不以资源存在或静态配置读取宣称真实模型／KC 端到端可用。

### 3.2 案例字段如何成为可检索知识

定制必须贯穿“提炼、正文组织、召回、返回上下文”，而非只多存一份 Profile。
以下沿用现有 Profile、投影及 KC 合同，不另建案例数据库或第二套索引：

| 案例内容 | 入库表达 | 后续诊断使用方式 |
| --- | --- | --- |
| 问题与环境 | 问题签名、脱敏环境和可引用的问题章节 | 症状／机制语义召回，并说明版本、拓扑和负载的匹配／冲突／未知 |
| 实际检查与发现 | investigation_steps、Claim 来源、发现强度和检查章节 | 借鉴检查顺序与排除依据，不将未做过的检查补写成历史事实 |
| 原因判断 | root_cause 及其支持强度、限制、反证和未决问题 | 形成待核实假设，不从相似案例确认本次根因 |
| 措施与逐项效果 | actions、action_effects 及关联章节；明确建议、人工登记与受控执行 | 命中措施时同时读取其执行性质、效果、验证方式和归因限制 |
| 适用与禁忌 | applicability、contraindications、失败警告及必要上下文关联 | 明确不适用时阻断处置推荐；信息未知时提示待核验，不默认为适用 |
| 来源与发布版本 | AIOps asset/version、正文哈希、投影清单、KC Revision 与 CONTENT 定位 | 当前发布白名单内检索，引用回到该版本正文，原调查通过受权来源链接追溯 |

Profile 是业务事实与检索辅助结构，脱敏正文是引用原件，投影清单维护语义单元关系；
三者绑定同一业务版本。只查 Profile 字段不等于已做正文检索，只上传正文不等于已保留措施与禁忌关系。
KC 的通用解析不能把“人工反馈有效”或“观察到改善”重写为“验证成功”。

已确认的“配置不变”继续适用：不新增菜单、配置表单或让普通用户操作 Collection。
先核验既有配置能力是否能在原合同内维护固定案例资源；若不能，采用明确作用域的规范初始化及
现有管理 API／KC 管理能力完成显式绑定，并在部署说明中记录维护方式，不暗中新增 AIOps 配置表单。
额外的配置交互改版不在本批授权内。案例模型角色与手册不同，不代表需要增加一套模型服务。

## 4. 案例结构化知识合同

基于现有 DiagnosisCaseProfile 做明确字段扩展，生产者、消费者、校验、索引和两仓合同同批更新，
不把新语义塞入任意自然语言或依靠文件名识别，也不从历史自由文本自动补造字段。

最低知识结构包括：

1. 问题签名：症状、错误标识、影响对象、信号、问题类别；未知值明确保留。
2. 环境：数据库家族／版本、组件、平台、拓扑、与机制相关的配置和负载条件；敏感标识脱敏。
3. 有效排查路径：实际做过的检查、发现、排除项、支持与反证、结论的修订；每项关联精确 Claim／来源。
4. 原因判断：已观察／有支持／尚未确认等真实强度，区别人工归纳和系统观测。
5. 尝试措施：建议、实际执行及失败分别记录，动作引用、前提、风险、停止／回退条件按现有来源保留。
6. 对应效果：每项措施与效果关联，保留对象、时间窗、负载可比性、测量、护栏、归因限制和原验证方式。
7. 复用边界：适用条件、不适用条件、未决问题、需要现场核验的项目；失败／无效措施带明确警告。
8. 来源与治理：asset/version、调查／报告来源、内容哈希、冻结与复核时间、安全级、脱敏策略和发布版本。

记录的是可供用户阅读的检查路径和证据关系，不保存或展示模型隐藏思维链。
没有来源的排查步骤不补写成“曾经执行”；缺少效果测量不编造前后对比。

原始证据与完整来源清单继续受限保存在 AIOps；不为提高召回把完整日志、账号、连接串、
业务 SQL 字面量或敏感附件一并送入 KC。脱敏保留技术机制，且不改变原信任等级。

## 5. 案例知识投影与 KC 接入

在 AIOps 新增 CaseKnowledgeProjection 编译／适配层，复用现有案例生成和脱敏逻辑，生成：

- 脱敏案例正文：CONTENT 原文，使用稳定章节标识和可读检查／动作／效果条目，作为精确引用来源。
- 结构化检索 Profile：用于环境、用途、问题特征、禁忌、发布版本和安全过滤，不作为另一份现场证据。
- 语义单元与关联清单：标识检查、措施、效果、前提和警告之间的关系及原文位置，
  支持 KC 切片和命中后取回必要上下文。清单必须与正文哈希和确切版本一致。

复用现有 KC CONTENT／SUPPLEMENT、结构 IR、通用 Locator 和精确 Revision 资源。
确需扩展的部分做成通用结构元数据／关联单元合同，KC 只消费受控标识、位置和关系，
不直接理解 AIOps 私有业务字段。不能只把一个 JSON 附件上传成功就宣称具备语义检索。

案例输入本身是受控结构化文本，采用适配的 TEXT 解析策略，不为 Markdown 强行重复 OCR/VLM，
也不让通用文档摘要模型重新改写原因等级、执行事实或效果。模型及解析策略沿用当前库配置，
缺配置明确失败，不借用其他库／Agent 模型，不在程序里写死技术输出上限。

具体在现有策略合同内表达案例文本处理档并冻结决策，不修改手册处理行为。
当前 KC build_parse_plan 中 Collection 规范策略会覆盖临时 overrides，不能只传 TEXT 就假定生效；
实施时应核对实际 ParsePlan，必要时扩展通用内容类型策略合同，明确管理员显式策略的优先级。
资源和模型通过现有配置／规范初始化管理，不增加新菜单，不在业务请求或启动时检查应用 Schema。

### 5.1 分片与上下文规则

优先按“问题与环境／检查路径／措施与效果／适用与禁忌”组织可引用语义单元，
通过 KC 通用结构与 Locator 保持稳定定位，不以固定字数把一段措施和对应“不适用／失败”结论割裂。

每个检索单元至少关联：确切案例版本、章节／条目标识、用途、有效范围和必要上下文单元。
命中措施时，必须一起取回对应前提、效果、限制和失败警告；过长可受预算限制截断，
但必须明确不完整，不能仅返回裸命令或无条件成功摘要。
结构化 Profile 只辅助召回与筛选，回答中的引用必须落到脱敏正文的确切片段。

### 5.2 版本与索引契约

一个案例业务版本绑定一组确定的索引原件、策略／模型快照、内容哈希和 KC 精确 Revision。
继续采用平台现有 Bundle／Revision 合同；确保新版本处理或审核期间，
旧发布版本的精确索引仍可读取，不能被“Bundle 当前版本”切换隐式夺走。
若现有复用 Bundle 不能满足此条件，使用各业务版本独立的现有 Bundle 身份，
不重建 KC 模型，也不添加双读写兼容。

案例语义修订创建新业务版本和新索引版本；重复提交／重试恢复已有受理结果。
同一正文、同一来源或同一事件的副本不能通过重复索引变成多个独立支持证据。
索引失败、源失效和退役均保留治理记录；精确撤回须等 KC 确认，不把已发请求说成已撤回。

### 5.3 外部受理与断点恢复

案例 Worker 在 KC 受理前持久化确切入库来源身份、脱敏标题／Profile、知识正文哈希、
来源指纹和选定 Collection；这些是服务端恢复材料，不进入公开任务回执。
重试必须复用同一正文及入库幂等键，不因 Prompt、模型或时间变化再次生成另一份正文。
KC 已受理但返回未保存时，以同一正文和同一键取回原 Revision；保存后只使用该确切定位。

外部受理回执登记与继续执行权限分开：刚发生撤权也应保留已发生的受理事实，
但登记回执只允许当前任务租约持有者写入，不批准索引，不产生任务成功。
继续调用模型／KC、批准索引及完成任务仍须当前授权；临时授权服务故障仅等待重试，
实质撤权或来源失效则保留治理记录并按确切版本撤回。终态接收方还须覆盖
“已登记受理回执但尚未登记 Registry”的清理，不让异步失败丢失外部对象。

Registry 标记 READY 不能单独证明草稿可用：完成前复核当前有效来源及实际 Agent 清单、
投影正文哈希、KC 精确 Revision 已批准／READY、未撤回和 CONTENT 文档版本。
这些技术完成条件不改变人工发布门禁，也不把历史案例变成当前现场证据。

### 5.4 异步回执与确切版本读取

会话 :close-diagnosis 使用既有来源与人工归纳合同，要求 Idempotency-Key，返回 202 输出任务回执；
HTTP 受理只核验并冻结，不等待模型或 KC。任务状态不带冻结正文、租约或 KC 内部定位。
完成后回执定位 asset_id＋asset_version_id；案例读取接口的可选 asset_version_id 必须属于所请求案例，
跨案例定位明确拒绝，不退回“最新版本”。读取正文、管理预览及发布各自保留当前权限门禁。

两端会话和案例库通过任务查询／受控重试恢复进度；任务成功显示“草稿已就绪”，
不是“已发布可检索”。报告提炼案例已接入同一机制，替身验证见修改计划第 6.11 节。
页面结果定位已经接线不代表通知深链、真实 KC 或完整资源配置已经验收。

会话与报告分别冻结来源，复用 case_intake.py 的同一脱敏、投影、上传、回执登记和审批管线。
报告入口冻结确切报告版本／正文哈希、原件及安全级、目标版本、运行身份和 Profile，
不在后台改读最新报告或重选调查。重试不重脱敏；报告案例 Registry 的 source_hash 继续绑定原报告正文，
不因更换异步任务协议而改写来源约定。

纯展示修订可复用来源仍有效的祖先案例；报告所引用的会话收口已成案例时，可复用该确切版本。
终态必须证明结果属于本次冻结报告允许的来源复用范围，不能简单放宽任意结果的指纹校验，
也不能为通过任务校验而修改旧 Profile。已受理的多余 Revision 先登记为退役重复项，再可靠申请撤回，
不遮蔽有效案例；申请撤回不等于 KC 已确认撤回。

## 6. 入库与发布闭环

~~~text
冻结调查来源与用户确认
  → 输出任务受理
  → 来源／权限核验与案例结构化提炼
  → 脱敏、知识投影及完整性校验
  → KC 文件受理、登记精确外部版本、批准进入解析
  → KC 解析／索引完成，引用与版本复核
  → 案例草稿就绪，生成任务完成并通知发起人
  → 人工完善、送审、审核发布
  → 发布版本进入后续诊断的可检索范围
~~~

KC 技术受理／入索引审批不是 AIOps 业务发布审核。草稿进入索引可供有权限的管理预览，
但 Agent 正式检索必须经 Registry 当前 PUBLISHED 版本白名单，禁止直接全库检索草稿。
两个预览入口职责明确区分：

- 精确版本正文预览：管理权限下读取 Registry 登记的 /versions/{asset_version_id}/preview，
  从已就绪 KC CONTENT 原件和精确文档版本取回解析片段。允许草稿和待审核版本，
  但核验正文哈希、Revision 已批准／就绪且未撤回，返回前再次核对业务版本；不伪造 Agent。
- 正式检索范围预览：保留 search-preview 入口，必须显式选择 agent_id，可指定其授权 target_id；
  仍遵守 Agent 当前知识开关、来源类型、知识库绑定、安全上限和发布白名单。
  管理用户 ID 不能代替 Agent ID，也不设置一个可由请求打开的草稿检索旁路。

业务发布时再次核验原件、脱敏正文、KC 可用性、精确引用和效果资格。
因此至少区分“已登记／处理中”“索引就绪草稿”“已发布可检索”，不显示含混的单一“已入库”。

当前异步任务在“草稿就绪”结束，不等待人工审核；审核发布成功是后续独立治理事件。
索引失败使任务可诊断、可恢复，不能提前发“案例已生成可用”通知。
资料库的现有入库流程不因案例链扩展而改变，配置页面不新增步骤或隐式模型绑定。

### 6.1 “入库”必须拆成三个可观察的里程碑

| 里程碑 | 必须成立的条件 | 用户能做什么 | Agent 正式检索 |
| --- | --- | --- | --- |
| 已受理／处理中 | 已保存任务，随后登记 KC 确切受理版本；受理不代表解析成功 | 查看任务阶段、失败及恢复信息 | 不可用 |
| 草稿索引就绪 | 脱敏正文、来源和哈希复核通过，确切 KC Revision 可读且索引就绪 | 收到草稿通知，预览、完善和送审 | 不可用 |
| 已发布可检索 | 人工发布复核通过，Registry 指向该确切发布版本且当前仍有效 | 在新诊断中引用经验、查看来源与限制 | 按当前权限和 Agent 来源范围可用 |

这三个里程碑不是替换现有业务枚举的新状态机，任务、案例治理和 KC 技术状态仍分别保存。
用户修改已就绪草稿的可检索正文时，创建新业务版本并重新投影、入库和对账，不能只更新页面文字，
继续用旧正文哈希／索引显示“就绪”。普通修订期间旧发布版本继续可用；实际来源失效或撤权时除外。
编辑、生成任务完成及“复用有效”反馈都不自动发布，不自动升级为已验证处置。

## 7. 后续诊断如何检索

继续使用 ops.knowledge.search 和平台共享 Knowledge Answering 能力，
由当前 Agent 的知识来源范围与服务端业务上下文产生可信范围，不新建案例专属聊天入口。
沿用 Agent 的知识能力开关、source_kinds 与 knowledge_base_ids 绑定语义：
用户选择的知识库限定资料范围，启用 DIAGNOSIS_CASE 才加入同 Domain 授权案例；
不把案例强塞进某个手册库，也不绕过现有“未绑定知识库”的限制。配置 UI 不因此改版。

1. 解析当前问题与目标环境：用户意图、症状、数据库版本、组件、拓扑等由结构化任务上下文提供，
   不用故障词／错误码硬编码表代替语义判断。
2. 硬过滤：当前权限、Domain、安全级、Agent 已启用的知识来源、PUBLISHED 和精确索引可用性，
   以及明确禁忌；案例原件及效果引用仍须复核。
3. 适用性：数据库／版本、拓扑、负载、症状、机制和原验证条件分别记录相符、冲突、未知。
   非安全性的相似程度用于排序和解释，不把未知环境默认为匹配，也不把所有线索当硬门槛。
4. 候选范围与最终结果数分离：Registry 分页取得已授权发布版本，以稳定分片调用现有 KC Discovery／Evidence；
   候选和调用预算有界，不能先按最终 Top-K 截断，或只按最新案例取 N 条后再做相关性检索。
5. 召回与排序：复用 KC 词法／向量能力，综合问题相关性、证据质量、环境适配、验证方式、
   新鲜度和用途，去重后按用户要求的数量／顺序返回；不机械让所有手册压过案例。
6. 结果闭包：命中正文后按语义关联取回前提、措施、效果和禁忌，验证 Citation 属于当前精确发布版本；
   Registry 摘要或相同来源的其他报告不能伪装为新引用。
7. 读取前再校验：检索期间来源撤权、版本退役或被反证时阻断新输出，申请精确撤回并进入复核。

案例命中上下文通过稳定章节标识和正文 Unicode 位置闭合到确切 CONTENT 原文，
由正文哈希和 KC 文档版本共同验证；不为关联上下文捏造 KC Evidence ID。
必要关联单元缺失或超过闭包预算时拒绝该条案例并提示，不能仅保留措施而丢弃失败警告。
候选扫描超过预算时明确报告范围不完整，不能把有界扫描包装为全库已经无匹配。

诊断返回至少包含：案例用途、原问题与环境、可借鉴检查／措施、原效果与验证方式、
当前环境差异、禁忌和未决事项、确切案例版本和正文 Citation。
Agent 将其当作待核实假设或经验，仍须采集当前证据，不能用相似案例确认本次根因。
失败教训作为警告和排除线索，不能把其中的失败动作自动推荐给 Executor。
历史命令不能携带原环境参数直接执行，知识引用不扩大任何工具或变更授权。

### 7.1 两类知识联合检索与使用边界

同一问题可同时命中资料与案例，但结果保留各自身份：资料提供适用版本的规范依据，
案例提供原场景、实际路径和效果；不把两者拼成一条看似来自同一原件的结论。
同一调查产生的报告、案例和副本按来源血缘处理，不能重复计作独立证据。
没有正文证据时不得用 Registry 摘要代替 Citation，也不得为凑齐用户结果数放宽发布或授权范围。

明确区分检索和处置推荐：失败教训仍可作为“不要这样做”的警告命中；环境明确不适用的措施
不能作为当前处置推荐。自然语言禁忌不能仅靠字段存在或关键词匹配就宣称已实现硬过滤。
需要通过版本化的业务适用性判断表达相符、冲突、未知，并验证其与当前可信 Target 上下文的关系；
缺少必要前提或无法安全闭合措施／效果／禁忌时，不输出可直接执行的处置建议。

当前工作区已具备投影、发布范围分页、精确版本、上下文闭包及下述结构化适用性链的离线测试；
真实模型的语义判断准确性、排序质量及真实 KC 检索仍待评测，不因合同或替身测试通过而视为已验收。

### 7.2 当前环境适用性与逐项措施资格

案例正文仍由 KC 提供，AIOps 业务层另附 OPS_CASE_REUSE_DECISION.v1；
不把模型判断伪装成 KC 原文，不用查询中的自述替代当前可信 Target。

- 冻结当前 Agent 版本、显式 planner_llm 和 Target 行版本，仅读取数据库类型／版本、拓扑、
  数据库角色和部署类型等安全技术事实，生成上下文指纹；不读取连接端点、主机、账号或凭据。
- 数据库类型、主版本与拓扑分别标记 MATCHED／CONFLICT／UNKNOWN；缺少、字面 UNKNOWN，
  或版本无法规范解析时均为未知，不能因两段自由文本版本相同就认定主版本匹配。
  这只是环境兼容判断，不证明当前症状、负载、根因、备份、维护窗口或恢复情况。
- 自然语言前提、禁忌和原验证限制保留稳定条件 ID，使用当前 Agent 已配置的 planner_llm
  单批判断，不新增模型角色或配置表单，不借用案例解析模型。输出必须绑定当前指纹、
  完整覆盖所选案例及原条件、逐字引用条件，已知判断必须引用实际当前事实。
- 默认最多判断 20 份案例，单份 96 条条件、总计 512 条和 100,000 字符输入预算；
  调用限时 30 秒，技术输出上限仍取模型服务配置。模型／目录／Prompt 不可用、输出非法、
  缺少当前目标或超过预算时显式降为未知，说明语义核验范围不完整。
- 整体状态优先级为 PROHIBITED → CONFLICT → UNKNOWN → MATCHED。缺少前提或禁忌、
  未决事项或历史验证限制均不能自动解释为安全；模型不得宣布原验证限制消失。
- MATCHED 仍不等于可以推荐任意措施。只有已验证处置／优化经验中的单项措施，具有与
  原 controlled_verification_ref 对应的正向效果（RESOLVED／IMPROVED）且无单项限制，
  才具备“参考并需当前验证”的推荐资格。案例整体成功不能复制给每项动作。
  排查参考不升级为处置；失败教训固定 WARNING_ONLY，失败动作不获得推荐或执行资格。
- PLAN／CHANGE／VERIFY 排除未满足处置推荐条件的正向案例，失败教训仍可作为警告；
  DIAGNOSE／EXPLAIN 可呈现差异或未知，但不能据此给出当前可执行结论。
- 决策同时保留在结果、reuse_context 及每份 Citation 的 locator.case_applicability；
  只消费 Citation 的 Agent 也不得丢失边界。所有结果始终 execution_authorized=false、
  historical_knowledge_is_current_evidence=false、requires_current_verification=true。
- KC 和模型调用均在数据库事务之外；全部外部调用结束后，重新核对确切发布版本、
  来源授权和当前 Agent／模型／Target 指纹。期间发生变化则丢弃旧结果，不补取另一批 Top-K。

上述是实现边界，不是语义正确性的充分证明：引用一个真实字段并不证明模型正确理解了该条件。
新增 20 场景质量集与[评测说明](../operations/aiops-case-retrieval-evaluation.md)，
覆盖四类案例、五种检索用途、跨数据库／版本／拓扑、禁忌与未知、同源去重和单项效果。
实际排序以 KC 正文相关性为主，业务重排策略见第 7.3 节；尚未证明综合排序的真实目标效果，
不得把评分器离线通过或数据集结构有效写成真实模型召回／排序质量通过。

### 7.3 有界业务重排与可解释评分

两类知识在精确发布、授权、来源、正文引用及案例用途门禁之后统一排序，再做同源去重及最终 Top-K。
新增独立 application/knowledge_ranking.py，不在 KC 中加入 AIOps 判定，不从查询关键词推断案例用途。
CATALOG 仍是无正文引用的授权目录，不冒充正文相关性排序。

首版 OPS_KNOWLEDGE_RANKING.v1 使用 KC Discovery 分数与最佳正文 local_rank 组成的相关性，
乘以“1＋业务加分”。各因子处于 0–1，总加分最多 20%，因此正文相关性比另一项高超过 20%
的旧知识不会被新鲜度或质量元数据反超；零相关性不因元数据变成命中。
首版权重是离线工程策略，不是训练结果或真实质量评测结论，也不增加用户配置表单：

| 因子 | 最大加分 | 只认可的信号 |
| --- | --- | --- |
| 当前适用性 | 6% | 案例真实当前上下文判断为 MATCHED；请求提示和空筛选不算，资料未作同类判断则不加分 |
| 证据结构 | 4% | 案例有原引用的 OBSERVED／SUPPORTED 检查覆盖率；资料步骤引用与其 source_evidence_ids 的交集覆盖率 |
| 验证关联 | 4% | 案例逐项效果链接受控引用、可比较、有方法且无单项限制的覆盖率；资料带来源步骤的操作卡中登记验证项的比例 |
| 用途适配 | 4% | 现有 purpose 与可追溯检查、实际措施推荐资格／失败警告或验证关联相符，不按标题或查询词判别 |
| 版本年龄 | 2% | 服务端版本 created_at，以 365 天半衰比例衰减；缺失、无时区、无效或未来时间不加分 |

版本年龄不是事件发生时间，不证明知识仍然有效；重新发布不刷新此因子。资料登记验证项
也不等于执行过验证。失败测量与正向测量使用同一关联质量要求，不因结果不利降权；
案例整体成功、任意方法名称、引用数量或重复步骤不能直接变成高质量信号。
安全门禁先于加分，失败教训即使排序靠前仍为 WARNING_ONLY，历史知识始终不授权执行。

结果附 ranking 评分卡，含策略版本、原相关性、各因子／权重、版本年龄和评估时间；
coverage 标识策略。相同业务分按原相关性、稳定 asset_version_id 决胜，
不优先某类资产或更多引用。适用性语义预算仍只覆盖正文最相关的至多 20 份案例，
预算外保持未知并明示覆盖不完整，不能称为全库已完整重排或语义核验。
实际效果仍须使用第 8 节固定质量集及真实模型／KC 分别验证；离线测试只证明公式、门禁和合同。

## 8. 实施与验收

修改落点为两仓 AIOps contracts/knowledge.py、case_closure.py、case_report.py、
operations_knowledge.py、repositories/knowledge.py、case_semantic_redaction.py 和既有 KC 客户端／共享检索链。
新增可独立测试的 case_knowledge_projection 应用模块，避免继续把所有逻辑堆入 operations_knowledge.py。
若通用语义单元／关联元数据不足，再同步扩展 platform_core 的 KC 合同、platform_clients、
KC 结构解析／Evidence 输出和两仓 OpenAPI；不将 AIOps 特定领域判断放进 KC。
AIOps Profile、索引元数据与业务实体有变化时同批更新规范 Schema、初始化／部署及 acceptance，
不自动给历史案例补造检查、措施或效果。

新增案例检索评测至少覆盖：

- Oracle、MySQL、PostgreSQL 各自环境，版本／拓扑冲突及未知；
- 同症状不同原因、同机制不同表述、错误码缺失、较旧相关案例不能被新无关案例挤掉；
- 诊断参考、已验证处置、优化经验、失败教训的正确呈现；
- 措施命中时必须带出效果和禁忌，引用准确，不把根因未知改成已确认；
- 草稿／拒绝／退役不被正式检索，当前 Agent 未启用案例时不回流；
- 同源去重、跨空间拒绝、查询期间撤权／反证、精确新旧版本与撤回 ACK；
- 生成成功但未发布不可检索，发布后可引用，再修订或撤回后不再推荐旧版本；
- 模型或 KC 故障、幂等受理和索引恢复不重复入库；手册检索不回归。

最终验收必须真实执行“会话沉淀 → KC 处理 → 草稿通知 → 人工发布 → 新会话检索命中 →
引用预览 → 来源更正／撤回后阻断”，分别记录离线单测、检索评测及真实模型／KC 结果。
