# AIOps 数据库备份与空库恢复演练设计

状态：新版设计已进入开发。适用 Ammolite 与 KBot4。本文取代旧版设计及 D0/D1 执行记录。现有人工恢复证据、巡检备份检查和 DBA 恢复文档能力保留，均不代表自动备份或恢复演练已上线。代码进度与启用条件以[实施计划](../operations/aiops-data-protection-implementation-plan.md)为准。

## 1. 做什么、不做什么

- 对业务系统已经登记的 Oracle、PostgreSQL、MySQL 数据库，由用户在「数据保护」中显式纳入。程序提供版本化备份脚本模板；用户配置已有的备份身份、执行位置、存储和计划参数，不编写、不上传脚本。到点由现有 Worker 调用数据库原生或现有成熟工具。
- 用户提供专用、隔离的空恢复环境。到约定时间，AIOps Agent 调用批准的恢复脚本，校验结果，出具正式演练报告，分析与期望 RTO/RPO 的差距并给出整改方案。
- **Agent 永远不能恢复、覆盖、重建或打开现有生产库数据文件，包括生产备库；没有强制继续或管理员豁免。真实生产恢复只沿用现有恢复文档能力，由 DBA 人工执行。** 源端计划只执行备份，不能借用备份凭据执行恢复。
- 以「现有 AIOps 调度/Worker → 已有执行通道 → 固定模板/受控脚本 → 数据库工具 → 证据 → 报告」为主线。首版复用现有 Agent、任务、托管凭据、授权、Artifact 和报告能力。**不新增 C helper、pidfd/seccomp/cgroup 机制、密封 FD 握手、独立守护进程、自建传输/凭据协议或通用执行框架。** 现有通道不具备某场景所需权限或边界时，停止该场景并提交差异给用户确认。

## 2. 页面、配置与状态

「数据保护」是独立、可选的页面及配置归属。业务系统页只列出本系统数据库的保护摘要和「查看数据保护」链接；单库链接直接定位该资源，多库入口带系统筛选，不默认选第一库。两处进入同一个页面，同一套资源权限；业务系统不保存保护字段、凭据或计划。未纳入不是告警，不阻塞建档、发布、诊断或巡检，也不等于没有外部备份。

独立入口采用与实时监控一致的选择顺序：左侧按业务系统展开，在系统内搜索并选择数据库；右侧显示所选数据库的保护配置及记录。数据库归属来自业务系统资源清单，不以接入监控为前提；选中数据库前不读取或启用任何保护计划。

| 配置／记录 | 在「数据保护」中管理的内容 |
| --- | --- |
| 保护对象与目标 | 显式引用稳定的数据库资源 ID；期望 RTO/RPO、口径和重要程度。多个业务系统共享同一库时使用同一保护对象，不重复调度。 |
| 身份与执行环境 | 源库备份身份、执行主机/Agent、存储访问引用、演练实例身份、必要时单独的验证身份和密钥引用。仅填写或选择已存在的身份，不创建账号、申请账号或自动授权。 |
| 存储 | 选用用户已准备的目录或工具已支持的仓库；记录可达位置、读写主体、保留期限、容量与加密前提。 |
| 备份计划与记录 | 从业务系统的数据库资源读取已登记的引擎和版本，选择内置模板及工具要求；不在数据保护中重复维护数据库版本。用户填保存目录或仓库、受支持的并行度、时区、执行时间/周期和超时。启用时冻结源库版本、模板标识及模板修订，生成持久化备份 Job；展示下次执行、结果、产物引用、日志覆盖和最近成功时间。 |
| 演练目标、计划与报告 | 独立登记用户提供的空环境、用途和身份；选择备份来源、一次性/周期时间、场景和验证项，查看执行结果、指标与报告。 |

发布或修改业务系统不自动启用保护。源库身份、目标端点、实例/目录、工具模板、存储或凭据发生变化后，停用受影响计划直至重新校验、由有权用户确认。停用不删除产物和报告。保留既有人工恢复证据及原引用，人工登记和审核不会变为自动实测；如未来要切换既有表单归属，应在新入口可用后做定点切换，不静默迁改历史数据。

## 3. 工具选择与实际执行位置

| 数据库 | 源端备份 | 演练端恢复 |
| --- | --- | --- |
| Oracle | 在已有配置的执行节点调用 RMAN，按模板备份数据库、所需归档、控制文件和 SPFILE；服务器通道写入批准介质。 | DBA 提供清洁辅助实例（符合批准模板的启动状态，例如 NOMOUNT）和专用目录，使用既有备份及归档做备份式恢复/复制，不从运行中的生产库抓数据。恢复、打开及验证只对辅助实例。 |
| PostgreSQL | 沿用支持版本的物理备份工具（原方案推荐 pgBackRest），通过程序内置模板调用基础备份；核对现场 WAL 归档及覆盖。 | 在独立 PostgreSQL 实例的数据目录及表空间恢复，读取仓库内的基础备份、WAL 与时间线历史，按配置回放并验证。物理恢复不是往正在运行的空业务数据库执行导入。 |
| MySQL | 沿用与服务器版本匹配的现有工具（原方案推荐 XtraBackup），使用既有备份入口；时间点恢复另依赖独立保存的连续 Binlog。 | 在独立 MySQL 实例上由工具 prepare 并恢复至空数据目录，再用 Binlog 在完整事务边界回放；只能启动/管理演练实例。 |

### 可配置的全量与增量周期

每个源库仍只有一份备份计划，时区使用 IANA 名称。支持三种方式：

- 仅全量：沿用原 Cron。
- 全量与增量分别配置 Cron：两条规则可自定，使用同一时区。两条规则同时命中时只执行全量。例如，全量 `0 2 * * 0`、增量 `0 2 * * 1-6` 表示周日全量、周一至周六增量。
- 按天轮转：以时区内的起始日期为第一轮首日，填轮转周期、全量和增量两个时刻。每轮首日全量，其余天增量；例如周期为 3 天表示全量、增量、增量，跨周、跨月、跨年都连续计算，不会在月初重置。

系统以任务的**计划触发时间**和该时区判定备份类型及基线，而非 Worker 的当前日期。规则与备份链证据存放于现有配置和任务 JSON，不改数据库表。

| 数据库 | 计划全量 | 计划增量 | 空库演练读取 |
| --- | --- | --- | --- |
| Oracle | RMAN Level 0（原普通全备不能作为 Level 1 的基线） | RMAN 累计 Level 1；核对相同数据文件和 incarnation 下的 Level 0 检查点 | 仅在演练工作目录集齐已选 Level 0 与 Level 1 的备份片，供辅助 RMAN 读取 |
| PostgreSQL | pgBackRest `full` | pgBackRest `incr`；逐段验证 repo1 中的前驱和实际引用 | 使用精确备份标签，从只读仓库恢复相应链及达到一致点所需的 WAL |
| MySQL | XtraBackup `--backup` | XtraBackup `--incremental-basedir` 指向本次增量对应的全备；增量起始 LSN 必须等于全量结束 LSN | 在演练工作副本上先 prepare 全备，再应用所选增量，最后写入专用空 datadir |

按 Cron，增量只认最近一次计划全量；按天轮转，只认本轮首日的计划全量。所需全量须属于同一库、同一批准配置和仓库，并在增量的计划时刻之前完成校验。若其缺失、失败或原生链条不完整，不会沿用更早的全量，也不会自动改跑全量。初次启用或保存为新版本后，须等一个新的计划全量成功。手工操作不得切断由产品使用的仓库链；保留基线、必要归档及全部被引用的增量，不按单个增量目录独立删除。记录和演练报告区分全量与增量，报告列出所选备份及依赖；RTO/RPO 仍按演练证据衡量，不以备份频次代替实测，也不因此承诺任意恢复点。Agent 仍只允许恢复已登记的隔离空库。

上述是工具方向，不是已通过验收的版本矩阵。各引擎首批覆盖取决于程序内置模板支持的工具版本和现场条件，不以用户提供备份脚本为前提。未确认的 RAC/ASM、备库源端、跨版本、托管云、MariaDB、特殊存储引擎、TDE/Keyring 或 CDB/PDB 粒度不能自动放行。用户若只提供一个在线空数据库、没有物理恢复所需的实例和目录，页面应解释差异并阻止物理计划；pg_dump/pg_restore、mysqldump/mysql 等逻辑方案可另行确认，其对象范围与 RPO 不等价于物理整库/PITR，不能静默替换。

按业务系统登记的版本选择预设，允许明确确认兼容的版本共用实现；命令、工具代际或产物格式不兼容时分别登记。未登记、无预设或实际版本与登记不符时禁止使用其他版本替代。启用和执行前由适配预检验证实库和工具兼容性；登记版本或已批准模板变化后，旧 Job 不执行，重新确认后才使用新预设。演练模板按备份来源版本与独立目标版本核验兼容性，预设尚未确认时不启用；恢复不能跨版本兜底，也不改变空库与生产禁令。

备份模板由程序预先实现并纳入代码版本管理；保存 Job 时固定模板版本与参数，到点从固定模板生成 RMAN 命令文件或对应工具的参数。保存路径或仓库按工具实际写入的位置校验（例如 RMAN 服务端通道），并行度按引擎支持范围校验。DBA 负责确认执行身份、目录和权限，不负责为每个 Job 编写备份脚本。不执行聊天生成的 Shell/SQL、任意脚本路径或自由命令。恢复模板仍走独立的批准流程，分开绑定执行位置、凭据与命令入口。主机权限由现场 DBA 预先授予，仅给所需目录和服务，不要求通用 root/sudo 或为此另装平台常驻组件。

优先在现有 Worker 可运行工具、访问资源的部署形态下直接调用。必须到远端执行时，只有现场已有获准调用固定脚本的通道、且能分开源端和演练端身份才启用。普通诊断 SQL/只读通道不能直接升级为远程写入通道，也不能把“用户已有脚本”当作自动具备调用权限。

首版已确认：三库恢复由独立演练主机上的现有 AIOps Worker 本机执行，不采用远程执行通道。演练主机由 DBA 准备，与生产主/备隔离，备份只读、写入只限专用空环境。PG 恢复到选定全备的一致点；MySQL 不追加 Binlog 回放。启用条件和待实测范围见[实施计划](../operations/aiops-data-protection-implementation-plan.md#5-已确认的原生演练部署方式与验收交接2026-11-18)。

## 4. 权限设计：只有数据库账号通常不够

「保护配置」标题旁的 `?` 图标打开只读抽屉，不在主页面展开权限清单。抽屉随当前数据库展示备份、恢复演练各自的配置要求和检查状态，区分「数据库权限」「执行主机权限」「备份存储权限」「网络与工具」「恢复后验证权限」。保存前可查看所需项；连接成功不是备份或恢复授权已验证。权限示例是 DBA 准备清单，不由 Agent 执行 GRANT，不能仅凭页面复选框证明能力。

| 权限面 | 源端备份 | 演练端恢复 |
| --- | --- | --- |
| 数据库身份 | 专用备份账户，按下表和工具版本开最小权限；不复用普通诊断账户。 | 独立目标的恢复/实例管理身份，验证用只读身份；不接收生产恢复凭据。 |
| 主机执行身份 | 能启动批准程序、读取模板、写任务日志；文件型工具需读源数据/表空间文件。Oracle 要识别 RMAN 客户端与服务端通道实际访问的不同位置。 | 能管理专用实例、写独立数据/日志/表空间目录，读取模板及解密材料；无操作生产服务或写生产目录的权限。整库物理恢复可能覆盖空实例中原有数据库账号，须预先确认恢复后的认证方式。 |
| 存储与密钥 | 允许写批准的备份空间、列举/读取自身产物做校验；保留和删除限于此计划产物、按明确策略执行，不给通用删除权限。 | 备份仓库只读；写入只发生在专用演练目录。需要解密时使用演练侧授权引用，不临时依赖失效假设下的源库。 |
| 网络与工具 | Worker/既有执行位置能访问批准的源端、仓库和工具，使用已有安全通道。 | 访问仅限演练实例和批准仓库；恢复写入路径不可达生产实例，实例不能接入生产复制或访问生产业务依赖。 |

各引擎要点：

- **Oracle**：源端优先用支持版本的专用 `SYSBACKUP`，远程认证核对监听、密码文件、认证模式与 CDB/PDB 作用域；如现有脚本用 OS 认证，由 DBA 确认专用组与受控入口，不能无条件降级为 SYSDBA。普通 PDB 账号不够做整实例备份。Oracle 服务端通道需访问备份介质；同时确认 ARCHIVELOG、控制文件与 SPFILE 保护。有恢复能力的源身份只给已批准的备份模板，不给 LLM 或恢复流程。演练端的辅助实例认证、Oracle Home、独立数据/控制/联机日志路径及必要 Wallet 单独准备。
- **PostgreSQL**：pgBackRest 需 DBA 按版本核对备份控制/状态函数、归档配置、实例访问方式与文件访问，必要时包含备份起停、WAL 切换和状态读取；`pg_monitor` 不是备份授权。仅若已确认使用 `pg_basebackup`，才按其要求准备登录、`REPLICATION`、`pg_hba.conf` 与 WAL 条件，不能把该清单套给所有工具。不默认给 SUPERUSER、通用服务器文件或程序执行权限。演练端需正确的 PostgreSQL OS 服务账号、独立 PGDATA/表空间及仓库读取权，禁用生产连接和复制/订阅副作用。
- **MySQL**：XtraBackup 按兼容版本核对所需的 `BACKUP_ADMIN`、`PROCESS`、`RELOAD`、`LOCK TABLES`、`REPLICATION CLIENT` 等授权及必要的 performance_schema 读取；以实选工具和方式为准，不将示例全量套到任意版本。日志流权限独立，`REPLICATION CLIENT` 不是 Binlog 流读取授权。源端 OS 身份要能读工具要求的数据文件，说明锁和 I/O 影响；演练端要能 prepare、写专属 datadir、启停对应 mysqld、按需回放并验证。确保实例标识独立，禁用复制自动启动、事件等可能作用到生产的行为。

凭据使用既有加密托管，业务对象仅保存引用；不把明文密码、完整连接串或密钥放进命令参数、模型上下文、日志和报告。若工具必须用认证文件，采用现有受控方式及最小文件权限；撤销或缺权限时不回退到其它账号。预检不创建用户、写生产表或尝试实际恢复：检查身份、角色/权限、版本、路径、空间、依赖和目标状态；无法无破坏验证的项明确标为未验证，不能用试恢复生产库来确认。

## 5. 备份、空库门禁和演练流程

1. **备份**：和定时巡检一样，保存计划后计算下次执行时间；启用后由既有 AIOps 调度与 Worker 认领到期任务，备份 Job 与巡检计划分开存储。不创建操作系统 Cron。Worker 校验启用状态、资源权限、源身份、执行位置和仓库，按冻结的内置模板与参数执行；记录开始/结束、退出、脱敏日志、产物引用、校验和可用恢复坐标。工具退出码与完整、可读的产物都要确认；日志缺段不把备份伪装成可达任意时间点。备份保留由批准策略/工具管理，不删除正被演练引用的产物，也不默认删除生产归档。
2. **恢复前必检**：演练只从数据保护登记的独立目的地选择，不能从生产/普通 Target 列表、对话参数、源凭据或失败回退创建。保存配置时检查，真正写入前在实际执行位置再以只读方式核验。根据引擎核验非生产用途、真实主机/实例/服务身份、完整路径及其解析后位置、不与任何已知生产主/备或运行中的非演练资源重合、网络与执行身份独立、从属组件不会访问生产、落盘与空间准备、目标空闲且为空。不能只看标签、主机名字符串或连通性。
3. **空的定义**：物理恢复用已准备但无现有业务文件的辅助实例/数据目录，允许引擎规定的最小启动或初始化文件；逻辑方式若获准则是演练专用实例上的无业务对象目标库。已有数据、身份有歧义、目录指向生产或已被占用、证据缺失、目标被替换时一律拒绝。定时任务没有例外。禁止强制覆盖、自动清空、删除未知目录或为准备目标停生产库。上一轮恢复完成后由 DBA 在隔离环境重新准备，登记新一轮可用状态并通过复检；周期计划不能跳过。
4. **执行和验证**：冻结来源、计划版本、期望目标、目的地、场景、T0 和既有可用产物。取回备份，走固定恢复脚本，验证预期实例可用、恢复坐标与批准的关键对象只读检查；如配置并执行隔离业务探针，则单列应用验证结论。恢复执行通道不加载源端高权凭据，不从生产补拉数据，不使用 Oracle Active Duplicate 冒充介质恢复。失败保留现场，不能盲目重跑写步骤。
5. **调度与结果**：备份周期、演练一次性/周期均记录明确时区和下次触发；同一计划时点一条运行，同一目的地一次只允许一个演练。复用既有领取和互斥能力。错过演练窗口记录跳过，不积压补跑。重启或超时后若实际进程状态不明，报告未确认、保持目标不可再次使用、由 DBA 检查；不为此新建进程生命周期设施。报告可独立补生成，不能重触恢复。

首批覆盖「用故障时已存在的备份恢复至最近可证明可恢复点」；若现有工具和日志链支持，按确认矩阵覆盖指定点恢复。后者验证命中边界及耗时，主动回退窗口不当作日常 RPO 损失。没有日志链或证据不可用，计划应明确不支持对应场景。

## 6. RTO/RPO：建议、实测、差距

目标仅在「数据保护」填写。页面自动带入并只读展示当前业务系统已登记的重要程度，不重复选择，也不因查看页面或编辑备份、演练计划而更新保护配置。在保存保护配置时带入该等级；用户仍可设置主备形态并确认最终 RTO/RPO，经验建议须与当前等级和主备形态匹配后才能采用。以下为经验起点，不是 SLA 或当前能力承诺：极高 15 分钟/1 分钟，高 1 小时/5 分钟，中 4 小时/1 小时，较低 8 小时/4 小时，低 24 小时/24 小时（依次为 RTO/RPO）。共享库仍只有一份保护配置，不按拓扑自动放宽目标。

- 单库仅定期备份：按备份间隔和成功率解释可达性，不能建议已具备分钟级 RPO。连续归档：还看实际持久化延迟和断链。异步主备：参考传输/回放差距，不报零。同步主备：可另评失效切换能力，不能替代备份重建演练，也不能仅凭有备库宣称零 RPO。
- **演练 RTO**＝验证通过时刻 − 模拟故障声明 T0；T0 在恢复步骤之前确定。分别列计划时间、调度等待、备份取回、恢复/回放、验证及报表耗时。T0 后排队进入 RTO，报告生成不进入 RTO；预置实例、已准备存储等作为演练假设明示。未完成只报告已用时间，数据库可用不等于应用恢复。
- **实测 RPO**＝T0 − 已验证恢复到的数据时间。只用 T0 时已成功并可获取的产物；以 Oracle SCN/Incarnation、PG Timeline/LSN、MySQL GTID/Binlog 边界及可信时间映射取证。不能用备份完成时间、最新业务数据时间或库能连接代替。映射只能证明区间时显示区间；证据不足、时间错位或验证失败输出未测得，不记零。
- 分别计算实测减期望：正数是超标，非正是达标；区间跨目标或证据不足不下达标结论。目标、估算、实测分列，冻结当次目标版本。多库分别达标不证明业务系统整体达标；同步切换与空库重建也不混算。

## 7. 正式报告

复用现有报告中心、受权限控制的 Artifact 与 PDF 导出。每个已受理的演练有一份可追溯报告，包括失败、门禁拒绝、部分完成及证据不足；报告可区分执行结果、验证等级、指标达标情况和报告本身生成状态。确定性代码生成事实和指标，Agent 基于事实撰写原因/建议，不能补造证据或被报告文字改变结果。

报告包含编号、版本、计划/目标快照、业务上下文、真实演练范围与排除项、产物/日志链、时间线、实例/对象验证、期望/实测/差值、证据引用、风险和整改。例：恢复验证通过，RTO 目标 30 分、实测 47 分（超 17 分）；RPO 目标 5 分、实测 18 分（超 13 分）。整改需绑定证据：如日志归档延迟则检查落盘频率或断链；取回过慢则核查吞吐/近端仓库；回放长则由 DBA 评估基础备份周期和演练资源。为每条建议注明责任方、验证方法与建议复演口径，不自动更改生产配置或创建新的整改工作流。

## 8. 执行纪律

详见[实施计划](../operations/aiops-data-protection-implementation-plan.md)及仓库 `AGENTS.md`。设计落地按已确认的需求、方案和阶段推进。发现缺口先列证据、最小选项、影响，再取得确认；不在“继续”或“全部完成”的授权下新增架构、常驻组件、系统依赖、子项目、实际环境操作或交付门槛。进度按可见功能与代码级证据报告，不再沿用已经失效的 D0/D1 状态。
