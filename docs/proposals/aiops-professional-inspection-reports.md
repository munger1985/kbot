# 专业数据库日常与月度巡检报告设计
状态：已确认，2026-11-02；Ammolite 与 KBot4 同步实施。本设计替代旧巡检报告中以采集计数、证据覆盖率和最大基线偏离为中心的正文约定，不改变诊断报告的事实与权限边界。

## 1. 产品目标与范围

日报回答“今天数据库是否正常、有什么问题、需要做什么”；月报回答“整月是否稳定、问题是否反复、性能容量如何变化、下月做什么”。业务系统决定范围，Agent 只是执行者。日报每库一份正式报告，系统批次展示汇总；月报以业务系统为范围，逐库展开。所有入口、Web 与 PDF 消费同一冻结报告投影，不另拼正文。

日报默认观察最近 24 小时，当前检查明确注明快照时间；七日基线只辅助分析，不替代日报观察窗。月报使用报告时区的完整自然月；当前月尚未闭合只能称月度阶段报告。计划频率与报告周期独立。

日巡检监控读取范围为本次观察区间加此前七天，只使用已授权来源，仍遵守来源查询窗口上限；数据库现场检查与报告观察区间保持不变。本期覆盖率与参考历史覆盖率分别计算，旧历史缺失不能否定本期已有的完整检查。历史报告只使用已有冻结事实，不因缺少七天历史而重跑或补造样本。

## 2. 判定原则

判定链：基础检查集 → 结构化规则与适用性判断 → 问题风险 → 总体结论 → 正式出版。
Agent 可以解释和组织语言，不能临时猜测阈值、覆盖规则结果、补造证据或恢复事实。

- 正常：全部必要检查完成，未发现异常或需关注风险。
- 需关注：存在明确风险，尚未达到严重异常标准。
- 异常：存在明确故障或严重问题。
- 检查未完成：必要检查不足，不能形成完整正常结论；列明具体项目、原因和影响。

异常和风险优先展示，其他项目未完成不能将已知问题覆盖为未知。存在已知问题且检查不完整时，同时显示健康结论与未完成事项。执行状态、报告完整度和健康判断独立。可选来源缺失不否定已完成范围；必要来源缺失不能伪装正常。正文不使用笼统“整体健康未知”，不提供无依据的健康分数。

## 3. 日报结构

1. 报告头：系统、数据库、类型版本、环境、巡检时间、观察区间、编号版本。
2. 巡检结论：一句业务结论、重要问题和优先动作，不以工具执行数量充当摘要。
3. 问题与风险：有问题才展开；每项含对象、时间、实际情况、判断依据、影响、优先级、建议和复查条件。
4. 基础检查明细：正常项目也展示，列为“检查内容 / 结果 / 实测情况 / 判断标准”；状态为正常、需关注、异常、未完成、不适用。
5. 关键指标：当前值、可靠的观察期统计与趋势、判断标准及结果；不按最大相对偏离制造风险。
6. 处置事项及检查限制：建议逐项关联问题；必要检查缺失在结论附近说明。
7. 技术附录：采样质量、证据覆盖、工具、原始代码、来源 ID/Hash 和统计方法，不抢占正文。

标准日报必须覆盖引擎对应的基础检查集：实例服务、资源负载、连接会话、存储容量、锁事务、性能慢查询、可取得的数据库错误、适用的复制高可用和日志链。备份按明确启用的保障策略纳入。专项勾选不能取消基础集；仅有专项观测不足以形成标准“正常”报告。

按引擎能力适配固定只读工具；不支持、未授权或未接入分别如实说明，不静默跳过，不扩大授权。单机复制不适用须有角色依据。快照未见阻塞不等于全天无阻塞。判断规则应有版本，阈值具有指标方向、绝对水平和必要的持续性语义，七日基线仅辅助。没有适用规则的指标仅为观测，不能冒充正常检查。

## 4. 备份保障

归档/WAL/Binlog 正常不等于成功备份。启用备份保障策略后，成功记录、时效或策略违约作为独立正式检查；没有有效成功记录（包括尚未接入记录来源）属于备份保障风险，审查已完成但不合规，不因此阻止生成报告或降低检查完成数。查询失败、时间无效或样本不可追溯才列为核验限制。不将同工具的日志链正常结果清零，也不把缺记录断言为从未备份。未纳入范围的能力不作为自动全局缺口。月报汇总实际纳入的保障检查，不再展示 RESERVED 扩展占位。

## 5. 月报结构

1. 月度运行结论：本月稳定性、重要问题、已验证恢复和未解决事项、下月优先动作。
2. 系统与数据库概况：逐库月度评价、重要问题、期末状态和待办；保留期内成员及有效区间，不能用月末成员覆盖整月。
3. 稳定性与重要事件：中断、重启、严重告警、阻塞等，说明影响、持续时间和恢复情况。
4. 性能与容量：月内趋势、持续压力、主要瓶颈、月初/月末容量、增长来源、剩余空间、清理扩容建议。
5. 问题闭环台账：首次/最近发现、重复情况、严重度、当前状态和下一步，区分新增、持续、复发、已验证恢复、待验证。
6. 下月运维重点：只保留与事实相关的整改、容量性能、能力补齐及效果复核。
7. 附录：数据来源、覆盖边界、上月可比性和统计方法。

月内出现异常但期末恢复，表述为“月内发生异常，已验证恢复”，不能改写为全月正常。后续未再次采到问题不等于已解决；只有同一对象的明确复查证据才能标记恢复。重复巡检观测不直接等于多次事故。

## 6. 月度统计约束

只汇总自然月半开区间内的事实，指标身份必须包含数据库、指标、维度、单位。重叠来源去重且保持来源追溯；不同数据库不可混成一条时序。月报优先从冻结的带时区采样按报告时区重新分日；相同时间同值去重，同刻不同值排除并说明。只有日聚合时，必须与报告时区一致；未知或不同时区的日点不按日期字符串强行纳入月度统计。区分真实采样和日聚合点，日点百分位明确标为日点分布；没有实际峰谷不能伪造。没有连续观测及有效时长分母不得把快照均值标为精确月度可用率。

上月对比仅限同范围、同指标维度单位和同统计粒度；缺少上期或口径不可比明确说明，不从正文反推值。容量预测必须有足够数据及假设，不强行生成。历史不足影响哪些日期和哪些判断须在正文点明，不能只藏附录。缺失数据库/检查不能因零问题而视作正常。

## 7. 展示与冻结

日报和月报结论、检查结果、问题、建议及限制共享结构化业务字段。报告生成时冻结投影、规则版本、范围及来源，后续浏览不使用当前策略重判历史。展示编辑不能改健康状态、统计、证据或执行效果。正文短时间使用报告时区，技术附录可保留完整 UTC 时间。

页面独立展示并自然滚动，正文不堆积原始错误码、Hash 和扩展占位。无指标或无问题时提供准确简短说明，不输出空表格。PDF 与网页章节及判断一致。

日报恢复独立“七天基线对比”：展示对比值、七天均值、绝对变化、相对变化和日均趋势。冻结原始样本足够时，使用本次半开观察区间均值与此前不重叠七天均值；只有精确七天冻结汇总时，明确标“最新样本”，不声称取得本期均值。百分比指标以百分点标注绝对变化，零基线只展示绝对变化、不计算无限变化率；状态和原始累计计数不做普通均值偏离比较。缺测、冲突或覆盖不足时说明暂无可比基线，不插值补线，不影响已冻结健康结论。趋势参考与健康规则分开，吞吐量增长不自动成为风险。

附录在桌面为标题保留至少 260px，并随文字宽度展开，窄屏上下排列。统计方法、数据说明和技术来源分组展示；来源单独放入默认折叠的“技术追溯信息”，不与问题或数据说明混合编号。证据编号用于定位原始记录，内容指纹（Hash）用于核对内容，均明确标注字段名称与用途；PDF 同样使用这些名称与说明，不将内部标识当作巡检发现。

## 8. 验收

- 基础检查完整且无异常，明确数据库运行正常，并可核查正常明细。
- 单项工具有结果不等于基础巡检完整；缺必检时不误报正常。
- 已知异常不被其他缺口抹成未知；缺失明确到项目。
- 备份无法验证不污染日志链检查覆盖率，并给针对性建议。
- 监控指标按规则进入业务判定，缺规则不伪装正常；吞吐相对增长不自动成为风险。
- 月报区分期内问题与期末状态，不把未再出现判为恢复，不把同一事件重复计数。
- 跨数据库指标隔离、统计粒度真实、完整自然月、历史不足和不可比边界均有测试。
- 两仓各自验证，所有入口和 PDF 使用同一冻结结论；不改写历史报告，不自动重跑线上任务。

## 10. 展示接口合同补齐（2026-11-02）

线上报告展示请求暴露了出版投影与 HTTP 响应合同未同步的问题：日报已生成 `header.timezone` 和 `header.business_system_name`，但严格报告头模型未声明这两个字段，AIOps API 抛出 `ResponseValidationError` 返回 500，Main API 将下游失败转换为浏览器看到的 503。问题发生在展示响应校验阶段，不应因此重跑巡检或修改报告内容。

- 日报与月报合同显式声明各自的时区、系统范围、指标、明细和检查限制；移除旧的 `baseline_metrics` 入口字段和月报扩展占位，保持与已批准投影一致。
- 报告头继续使用 `extra="forbid"`，不靠放开任意字段、删除业务字段或绕过响应校验解决错误。
- 新增双仓一致的 HTTP 回归：四类日报和多库月报经过真实内部端点、窄客户端方法及公开端点序列化；同时验证未声明字段仍被拒绝、公开 Schema 含业务字段。业务数据源和身份边界使用隔离替身，不连接真实数据库。
- 本次 AIOps 单元回归 Ammolite 1227 项、KBot4 1191 项通过，均包含新增 7 项；OpenAPI 生成与验收分别通过 18/15 个快照，架构边界及双向语义一致性检查通过。
- 发布时需更新并重启加载共享合同的 Main API 与 AIOps API；不涉及数据库升级、报告数据修改或巡检重跑。本次仅提交推送，未部署或重启线上服务，不能据此声称线上已恢复。

## 9. 取数链路修复约束（2026-11-02）

- 日巡检读取本期加此前七天时，Prometheus 会按查询点数预算自动增大步长；八天、120 点的实际步长为 5760 秒。序列计算必须冻结来源的 `effective_step_seconds`，正式出版时与原始 ObservationSet 复核，本期覆盖率和逐日基线覆盖率均按该规格计算，不再把“一小时以内”作为来源完整的必要条件。未记录规格的历史稀疏样本不猜测为完整，缺测不能通过重新推断大步长被掩盖。
- MySQL 命名绑定必须支持 `:limit` 等关键字参数，且不改写字符串、注释、引号标识或百分号语义。数据库语法、权限、对象和连接错误必须分类，不能统称内部执行失败。
- 只有收到明确 SQL 拒绝错误且成功完成只读事务回滚的查询，才允许在保留原错误的同时提前归还共享额度。该确认是请求内生命周期状态，不冒充取消终止回执；超时、外部取消、围栏撤销、网络中断和回滚失败继续保留租约清理宽限，不通过扩大并发解决。
- 容器 CPU/内存 recording rule 采用两端一致的 `aiops_db_container_cpu_utilization_percent` 和 `aiops_db_container_memory_utilization_percent`，指标目录与部署生成器同步，不依赖另一产品的品牌前缀。主机指标必须绑定数据库真实宿主机的 `host_target_key`，不可用其他服务器的数据替代。
- 未完成项的建议依据结构化错误码分别提示额度调度、模板/参数修复、最小权限、连接恢复或监控采样；监控缺测应核对实际间隔、本期覆盖、来源绑定和冻结规则。第三方备份核验仍要求策略时效内的真实成功记录，不能用 Binlog、归档链或“未发现错误”替代。
- 修复只影响后续运行。旧报告、冻结事实与健康结论不重写；新增采集点和新 recording rule 不回填历史，没有足够历史时仍如实说明不足。

### MySQL 阻塞检查的最小函数依赖

MySQL 8.x 的 `sys.innodb_lock_waits` 依赖 `sys.format_statement` 与 `sys.quote_identifier`，前者还调用 `sys.sys_get_config`。在已有必要视图读取权限的前提下，由 DBA 核对实际诊断账号后仅补齐这些依赖：

```sql
GRANT EXECUTE ON FUNCTION sys.format_statement TO '<diagnostic_user>'@'<allowed_host>';
GRANT EXECUTE ON FUNCTION sys.quote_identifier TO '<diagnostic_user>'@'<allowed_host>';
GRANT EXECUTE ON FUNCTION sys.sys_get_config TO '<diagnostic_user>'@'<allowed_host>';
```

部署验收使用实际只读诊断凭据验证视图和依赖函数，不以管理账号执行成功作为通过，也不授予全库 EXECUTE 或写入权限。首次接入宿主机采集后，应分别验证 Exporter 私网监听、Prometheus Target 的 up、实际 CPU/内存/文件系统序列，以及两端新运行冻结的主机映射。配置加载成功不等于数据已经可用。

## 12. 当前健康、历史统计与备份作业核验（2026-11-02）

### 12.1 时间口径

日巡检的观察区间改为截止计划触发时刻的最近 24 小时，不再固定读取昨日自然日；周度计划仍保留原有周期规则。数据库现场检查与当前资源状态使用实际执行时快照，并分别注明检查时间，不能把当前查询结果描述为全天无故障。

当前监控与历史参考使用两个独立冻结窗口，复用同一已授权来源和目标绑定：

- 当前窗口默认最近 15 分钟、60 秒请求步长；健康判读要求最近有效样本距快照时刻不超过 5 分钟。窗口与时效来自版本化报告策略，执行前冻结。截断、留存语义不明、无效或过期样本不能判正常。
- 历史窗口为报告最近 24 小时及此前七天，遵守来源查询窗口、点数、序列和响应预算。当前与历史请求分摊原响应字节预算；保留原始 ObservationSet、窗口、来源声明步长和可重放计算。

### 12.2 统计口径

必要检查完成率等于已完成必要业务检查数除以必要业务检查总数，包含数据库基础集、必要资源角色及已启用的备份策略核验。数据库查询执行率单独统计，只说明工具执行，不代表健康。监控采样完整率按指标聚合当前窗口覆盖率，未返回样本的已请求指标计为零；无数据和不支持的指标不得从分母消失。历史趋势参考不足不混入当前采样分母。执行日志和报告页面使用同一计算结果。

### 12.3 真实备份记录接入

新增只读标准指标，当前实现由已授权 Prometheus 绑定提供；不会新增目标库表或写入目标数据库，也不会自动扩大既有绑定授权：

- `backup.last_success.timestamp`：查询 `aiops_backup_last_success_timestamp_seconds{target_key="..."}`，值为真实备份作业最近成功结束时间的 Unix 秒。
- `backup.last_run.status`：查询 `aiops_backup_last_run_success{target_key="..."}`，最近一次已结束作业成功为 1、失败为 0；进行中不重写结束结果。

核验覆盖所有必需来源：有效成功时间在策略时效内才合规；超过时效或最新作业明确失败列为问题；未提供有效成功记录列为备份保障风险，检查完成。查询失败、时间无效/来自未来、采样过期或不可追溯才列为未核验。已有失败不能被其他来源缺失掩盖。Oracle 仅对策略要求的 ORACLE_RMAN 来源保留原生成功记录核验，未来时间不再误判为时效合规。

## 14. 成功空结果的统一业务语义（2026-11-02）

本节取代旧版把“成功查询但无应有记录”计作检查缺口的规则，不仅适用于备份。报告是否完成与数据库是否正常必须分开：检查完成可以得出正常、需关注或异常结论。

| 结果语义 | 报告处理 | 是否完成该项检查 |
| --- | --- | --- |
| 应有的状态、成功作业记录不存在 | 问题与风险中列明缺失对象、影响、建议 | 是 |
| 监控查询成功但无样本 | 报告监控盲区，不推断数值为零或数据库故障 | 是 |
| 阻塞、长事务等异常清单零行 | 正常，未发现对应异常 | 是 |
| 未配置适用的复制通道等可选对象 | 不适用；不编造复制故障 | 是 |
| 查询超时、权限不足、结果截断、时间或数据无效 | 具体检查限制；保留其他已完成检查和已知问题 | 否 |
| 本期趋势没有足够历史参考 | 说明不可比较，不影响当前检查 | 不降低当前完成数 |

检查目录的 `zero_row_status` 显式使用 `FINDING / CLEAR / NOT_APPLICABLE / OBSERVED`。原来以 `GAP` 标识应有状态行的项目改为 `FINDING`；Oracle 最近备份作业零行同样报告记录缺失。仅普通观测清单保留 `OBSERVED`，不把所有零行一律报错。判定依赖执行前冻结的目录语义，不按中文标题或数据库名字硬编码。

备份按启用策略逐来源冻结 `source_results`：`COMPLIANT / FAILED / OVERDUE / NO_SUCCESS_RECORD / UNVERIFIABLE`。无成功记录为 `MEDIUM` 保障风险，失败或超期为 `HIGH` 问题；不同来源分别进入问题台账。只有逐来源审查完整时，缺记录风险才允许完成策略审查；普通结果缺证据引用、截断或无法核验仍不能通过完整性门禁，不编造一条成功或失败作业。

例如：15 项正常检查加 1 项备份成功记录缺失，必要检查为 16/16，报告就绪、运行评价需关注，问题列出缺少哪个来源的有效成功记录及备份保障风险，不再显示“15/16，检查未完成”。这并不等于确证历史上从未做过备份，处置建议分别要求核实未执行的作业或补齐已执行的成功记录。

监控成功空结果必须有原始 ObservationSet 中对应 gap 的证据引用，并关联冻结的授权绑定、指标和当前窗口。来源超时/认证失败、历史参考无数据不得转换为当前空记录风险。原始空结果保留在冻结工件中，正式报告只将其从技术缺口移至业务风险，不修改原始数据、不补零，也不降低采样完整率分母。两仓同步保留来源与绑定字段，避免 KBot4 丢失来源定位后无法判读。

## 16. Oracle 正常结论与自动扩展容量判定（2026-11-03）

正常的异常清单空结果直接表述为“未发现长事务”“未发现会话阻塞”“未发现无效对象”，其他成功的异常清单明确为“未发现异常”。移除“不是未取证”等取证流程解释和“无适用规则时仅展示观测”的含混文案，判断依据不再重复实测结论。查询失败、权限不足或无效数据仍列为检查未完成；应有记录缺失仍按第 14 节报告业务风险，不能统一写成正常。

表空间不按 SYSTEM、SYSAUX 或业务名称设例外，也不因数据库版本较新就假定文件可增长。只读查询逐文件读取 `AUTOEXTENSIBLE`：启用时计入不小于当前大小的 `MAXBYTES`，关闭时仅计当前 `BYTES`；关闭后残留的 `MAXBYTES` 不构成扩展空间。混合开关的多文件表空间逐文件相加，不能由某一个文件可增长推断全部文件可增长。

- 保留“已分配空间使用率”作为现场观测，不再单凭这个比例产生表空间容量问题。
- “配置容量上限”是各文件按开关计算的容量之和；“距配置上限剩余空间”等于该上限减已用空间，包含文件内部空闲及尚可扩展部分。
- 容量规则使用“已用空间 / 配置容量上限”，沿用达到 85% 报告容量风险的规则。未启用扩展或已接近扩展上限时仍需报告风险，不能因自动扩展开关为 YES 就判正常。
- 实测情况同时展示已分配空间使用率、自动扩展文件数、配置上限、上限使用率和剩余空间。相同阈值只展示一次，问题记录显示对应表空间的数值，比例说明统一保留两位小数。
- 配置上限不等于实际可获得的磁盘容量；文件系统、ASM 可用空间、PDB 存储配额等可能进一步限制扩展，需结合各自检查核对。本轮不新增这些来源、不用配置上限声称底层存储充足，也不按剩余空间推造增长速率。

## 18. 三类数据库的问题 SQL 清单与逐条 Agent 研判（2026-11-03）

巡检 SQL 区域不再展示累计调用量或总耗时榜单，也不固定取 Top 3/Top 5。MySQL、Oracle、PostgreSQL 均使用专门的问题候选只读查询，先按冻结规则识别单次耗时、CPU 时间、IO 等待/读取、锁相关等待或临时落盘开销，再列出所有已取得的问题 SQL，按严重性、超限倍数和稳定身份排序；调用次数和累计总耗时不能单独触发问题。查询先筛选异常，不先截取累计总耗时排名，避免正常高频 SQL 挤掉真正问题。

默认规则以版本化策略维护并在每次执行前冻结，参数与判定共用同一份规则。平均耗时达到 1000 ms/次、CPU 时间达到 200 ms/次、IO 等待达到 100 ms/次、锁相关等待达到 100 ms/次可以产生复核项；单次读取达到 1000 块、扫描达到 10000 行、临时落盘达到 1 次/块的资源开销规则同时要求平均耗时达到 10 ms/次。达到规则阈值五倍为高风险，其他为需关注。阈值表示巡检筛查策略而不是所有业务的性能 SLA，可通过策略维护调整。不同维度合并到同一 SQL，不重复计数；没有证据的维度保持未知，不补零、不据主机 CPU 高反推某 SQL CPU 高。

Oracle 使用现有动态性能视图，不引入 AWR/ASH 许可依赖；CPU 时间不称 CPU 使用率，应用等待不直接等同于行锁阻塞。MySQL 原生摘要的表锁时间、扫描和磁盘临时表与单次耗时分别解释，不伪称已取得逐 SQL CPU 或物理 IO 时间。PostgreSQL 使用适配版本的 pg_stat_statements，IO 计时不可用时明确该维度未测，不推算 CPU 或锁耗时。累计统计只约束当前保留的数据库统计，不冒称日报窗口增量或已确证根因。

逐条调用当前 Agent 配置的模型，根据该 SQL 的原始观测、命中规则与引用分析可能原因和初步优化建议。结构化输出校验 SQL 身份、证据引用与字段归属；原因保持待验证，不能凭空确认缺索引、执行计划或根因。建议说明验证方法和审批边界，不自动执行 SQL、变更索引或参数。每条分析独立保存状态、模型收据与 Prompt 引用，某条失败不能吞掉该 SQL 或伪装为已完成 Agent 分析；仍保留规则事实和复核建议。分析只在生成巡检时进行，刷新网页或导出 PDF 不调用模型、不重判历史结论。

完整执行且没有命中问题规则时显示“当前没有问题 SQL”。未执行、能力不支持、采集关闭、取数失败、部分取数或截断时明确说明范围，不使用正常空态。业务不设问题条数截断，但仍遵守受控执行器的行数、字节与时间安全上限；触及安全边界必须显示未完整读取，不能宣称已列出数据库全部问题。历史榜单没有执行新规则时提示重新巡检，不能通过刷新把旧榜单重新定性成问题或正常。

网页、运维报告与 PDF 使用同一份冻结问题与 Agent 分析。耗时沿用一位小数，按数值自适应 ms、s、min、h。不修改持久化 Schema，不回写历史报告，不自动部署、重启、触发巡检或修改目标库。

上线需同步更新 Main API、AIOps API、Worker、DB Executor 与前端，并按现有定向同步流程加载新增的 `aiops_agent.inspection_sql_review` Prompt 基线（版本 `1.0.0`，不得覆盖网页手工版本）。仅更新页面不能取得新问题清单；部署后须重新执行巡检，刷新历史榜单不能得到新判定。已有计划不用删除重建，触发时重新冻结当前检查目录、查询参数、规则及 Prompt。

## 19. Oracle 旧排序巡检入口统一（2026-11-03）

### 19.1 漏项与执行前收口

第 18 节的问题 SQL 流程没有覆盖旧 Oracle 专项：旧模板可将 `oracle.performance.heavy_sort_sql` 冻结为 `db.sql.top_current`，使巡检仍按旧“累计耗时 ≥ 10 秒”规则列出“严重排序 SQL”，并绕过逐条 Agent 研判。此前“已有计划不再重复执行累计榜单”的验证范围不足，本节补齐这一路径。

执行前以当前检查目录重新编译基础检查及模板所选专项，保留计划的检查选择；旧步骤不能覆盖当前工具映射。所有预期证据为 `TOP_SQL` 的巡检步骤只能使用 `db.sql.problem_candidates`，即使旧快照没有检查 ID，也不得恢复累计榜单路径。非 SQL 专项和其有效参数继续保留；冻结查询参数仍与判定策略一致。

原检查 ID `oracle.performance.heavy_sort_sql` 保留，显示名称统一为“问题 SQL”，映射到统一问题 SQL 工具，不再使用“SQL 排序与临时空间”这一窄化名称。筛查范围包括实际可取得的耗时、CPU、I/O、锁相关等待、扫描量、临时落盘及工作区开销，按数据库采集能力判断，不承诺每种数据库都能取得全部指标。与“问题 SQL”同时选择时，同一目标只查询一次，不产生两份问题清单。独立交互诊断的旧工具与规则不删除，但不再作为巡检 SQL 风险入口。

模板编辑器在同一业务主题的同名检查内，按工具和数据库范围识别系统保障已覆盖的等价检查，不将同一次执行再列为可追加专项；不同业务含义的检查不因共用工具而合并。只读详情也按同名主题合并展示。既有检查选择及冻结版本不回写，新建草稿只选取策略中的正式保障 ID，不新增重复执行入口。三类数据库共用“问题 SQL”主题名称、筛查范围说明以及逐条 Agent 分析与初步建议的呈现规则。

### 19.2 真实工作区证据与筛查口径

Oracle 统一查询除 `V$SQLSTATS` 的单次成本外，增加 `V$SQL_WORKAREA` 工作区统计。两个来源分别按当前容器、SQL ID 聚合后关联，避免多个计划或工作区放大执行次数；同一 SQL 的不同计划合并，同名 SQL 的不同容器隔离。范围仍是当前连接实例及可见容器，不冒称全 RAC 或日报窗口增量，不依赖 AWR/ASH。

新增两条仅适用于 Oracle 的冻结规则（策略版本 `2026-11-03.3`）：

- 工作区多遍处理比例 ≥ 10%，且平均 SQL 耗时 ≥ 10 ms/次。分母为工作区执行次数，不是 SQL 执行次数。
- 单工作区临时空间历史峰值 ≥ 64 MiB，且平均 SQL 耗时 ≥ 10 ms/次。多工作区取峰值的最大值，不求和冒充并发占用。

达到规则阈值五倍为高风险，其他为需关注。仅有一次 one-pass、累计执行次数多或累计耗时大均不能单独触发问题；平均 0.7 ms 的高频 SQL 不因累计量高而入选。临时空间历史峰值不等于当前压力，工作区也可能用于哈希连接或聚合，不能未经执行计划验证就标为“严重排序”或认定内存不足。规则是巡检筛查策略，不是业务性能 SLA。

MySQL/PostgreSQL 对不可测的 Oracle 工作区字段返回空值，不据此判风险、不补零；PostgreSQL 显式声明数值类型，避免空值在 CTE 中被推断成文本后无法比较。查询参数、输出合同、SQL Hash、字段字典与 Agent 引用校验同步更新。Oracle 目标账号需具备 `V_$SQLSTATS`、`V_$SQL_WORKAREA` 的只读权限；权限或查询失败必须显示该项未完成，不能伪装无问题。

### 19.3 报告与交付边界

同一 SQL 的耗时、CPU、IO、等待与工作区问题合为一条，按严重性排序。报告“问题与风险”逐 SQL 展示一项，详细问题 SQL 区域展示该条命中依据和 Agent 初步原因、建议、验证步骤；不再额外生成旧“严重排序 SQL”列表。Agent 可引用真实取得的工作区指标；缺少对应指标或身份、引用校验失败时单独显示分析未完成。完整取数且无问题仍显示“当前没有问题 SQL”。

历史报告及已冻结运行不回写、不在刷新或导出时重新判定。部署后新运行使用当前目录和规则，已有计划无需删除重建；需同步 AIOps Worker、DB Executor 及 `aiops_agent.inspection_sql_review` 的开发基线正文（仍为 `1.0.0`，不覆盖网页手工版本）。本次不改 Schema，不授权线上重启、补权限、触发巡检或 Prompt 数据库同步。

## 20. 跨数据库共享的分区式日常巡检报告（2026-11-03）

### 20.1 范围与统一格式

本节替代日报以“基础检查明细 + 关键运行指标”两张通用表承载全部内容的排版；仅修改日常巡检，月度报告保持现状。借鉴 AWR 的运行概况、目录导航、专题表格和明细定位，不照搬数据库专属字段，也不引入 AWR/ASH 许可依赖。Oracle、MySQL、PostgreSQL 及后续引擎共享同一报告结构、公共合同和渲染流程；引擎适配只负责检查取数、适用性、单位和区域映射。

报告由报告头、十二个正文区域和技术附录组成：01 巡检总览、02 数据库可用性、03 系统资源使用、04 存储与容量、05 连接会话与事务、06 数据库整体性能、07 问题 SQL、08 复制与日志链、09 备份保障、10 对象与维护健康、11 七天基线与变化、12 处置与复查清单。总览固定在前，处置固定在后，其他专题可调整顺序。目录及总览状态可定位到专题和问题；同一检查只归入一个主专题，不复制成多项问题。

共享区域目录维护稳定 ID、标题、说明与监控语义角色；检查目录显式声明区域归属。新引擎接入须声明归属，不能在网页或 PDF 增加数据库类型分支。未知或未映射数据不得静默丢弃，保留为待核查内容，不据此补造正常或不适用结论。

### 20.2 内容与判断

每个专题依次展示区域结论、关键实测、对象明细、问题依据和建议。正常专题保留简洁的检查及数值，不只放绿色状态。对象记录采用结构化表格，不把多行统计拼成长段文字；结果列窄，实测列宽。系统资源明确区分主机、容器/运行环境和实例，不能把不同范围的 CPU 数值混成一条。容量结合自动扩展、配置上限与可取得的物理空间判断。

总览仅显示结论、区域状态和问题定位，问题的完整依据只在所属专题展开。必要检查限制始终在总览及对应专题可见；未纳入、不适用、未完成、仅观测分别表达，不因空专题或缺少证据而标正常。备份缺少有效成功记录继续作为保障问题，不降低已完成核验数。当前快照、监控采集窗口、报告观察区间、此前七天及重置以来累计统计分别标注。

问题 SQL 保留全部已识别问题，按严重性排列；先列索引再逐条显示 SQL 文本、命中依据、自适应耗时、Agent 初步分析、建议、验证及审批边界。无问题的完整检查显示“当前没有问题 SQL”。七天区域独立展示可比值、均值、绝对/相对变化和趋势，不以历史缺测否定本期结果，不重复完整当期指标表。

处置表关联具体问题、优先级和复查依据；无问题时明确无额外事项。原始检查索引、统计方法、来源 ID/Hash 和采样质量进入默认折叠附录；已发现问题和必要限制不能只藏附录。

## 22. 巡检模板中心与发布生命周期（2026-11-03）

- 三个维度独立：来源 BUILTIN / CUSTOM、使用状态 ACTIVE / INACTIVE、新计划默认。内置来源必须由稳定 system_key 标识，禁止按名称推断或回写历史模板。
- 同业务空间、同巡检类型只有一个新计划默认。切换在业务空间事务锁内完成，不生成内容版本，不更新任何计划。默认模板必须先指定替代者才能停用。
- 每个自定义模板有且仅有一份持久化工作草稿。新建先保存草稿；不再提供“基于此创建”的跨模板复制入口；保存不增加版本。首次发布 v1，后续递增；没有内容变化或与历史版本完全重复不能再次发布。
- 卡片只保留一个主操作和更多菜单。内置主操作查看模板；自定义已启用主操作编辑模板；停用主操作查看模板；未发布主操作继续编辑。更多收纳设为新计划默认、启停、放弃草稿或删除模板，按状态与来源展示。版本不单独成卡。
- 模板详情使用独立全页，分模板内容、版本历史、引用计划。展示发布人、发布时间、业务差异及计划绑定版本；技术 JSON 折叠。历史只读，基于此版本编辑只覆盖当前工作草稿，再发布新版本。
- 内置模板不允许保存草稿、发布、停用或删除；需要定制时通过“新建巡检模板”创建独立模板。已有草稿被历史版本替换前由用户确认。放弃已发布模板草稿保留全部版本；未发布模板放弃草稿删除未引用根记录。
- 新计划只能选择已发布且启用的模板，创建时预选真实默认标记；已存在计划不受默认切换、发布或停用影响，升级只能在计划编辑页明确确认。

- API：POST collection 创建草稿；PUT /{id}/draft 保存；DELETE /{id}/draft 放弃；POST /{id}:publish 发布；POST /{id}:default 切换默认；GET /{id}/plans 查询引用；GET versions 只读；DELETE /{id} 物理删除（请求体包含 expected_row_version，权限 aiops:plan_manage / aiops.manage）。列表及详情返回 usage_count、history_count 和 can_delete。删除原 /versions 写端点。

### 22.3 只读模板内容的排版约束

查看模板继续使用全页详情，不回到抽屉。内容区顶部为报告标题与限宽版本选择器；桌面端左侧为紧凑编号目录，右侧将检查按主题组织成自然高度的单列主题行，检查名称以可换行标签列表呈现。取消两列等高大卡片，避免短主题被长主题拉高以及目录侧大量空白；只读内容不改变检查定义、数据库适配或版本绑定语义。

窄屏按目录、检查依次纵向排列，不产生内部横向滚动；无日报目录的版本不保留空白侧栏。模拟效果入口与配置内容用分隔区域区分，并明确不执行真实巡检。“查看报告效果（模拟样例）”使用项目统一的站内宽抽屉，不打开新浏览器标签页，也不在详情内容下方追加报告。抽屉沿用现有遮罩、固定标题栏与关闭按钮，仅内容区纵向滚动；窄屏自适应至全宽，不产生横向滚动。打开时固定所选发布版本的冻结定义，重试保持同一版本，不自动改用最新版本。支持关闭按钮、Esc 和点击遮罩关闭，约束键盘焦点；关闭后恢复原入口焦点、页面滚动位置及版本选择。关闭或离开详情后，未结束请求的迟到响应不得污染后续预览。模拟预览使用正式报告渲染器，清晰标注模拟、不执行真实巡检；目录仅在抽屉内定位，不改变页面 URL 或详情路由。沿用公共表单、按钮、字体和主题变量，两端复用同一份布局样式。

### 22.4 精简入口与安全删除的交付边界

“基于此创建”仅从巡检模板管理移除；版本历史中的“基于此版本编辑”仍用于同一模板内恢复到工作草稿，不新建模板，也不覆盖已发布版本。

本次删除能力复用现有根、版本、计划与批次记录，不新增表或列，不需要额外 Schema 升级。引用由正式仓储查询统一统计根记录和全部版本，卡片展示引用计划数及非零历史批次引用数。卡片共享信息网格保持两列，外框闭合、每行有分隔线；奇数项末项占满整行，不留下空单元格或悬空竖线。巡检计划等使用同一共享样式。无引用模板的发布历史不再单独阻止物理删除；真实计划和历史批次引用始终受保护。

两端生命周期、引用 SQL、公开权限及转发专项各 32 项通过；隔离 SQLite 验证正式引用查询，Oracle/PostgreSQL 方言编译和删除顺序由仓储单测覆盖，不将这些替身测试视为真实数据库并发验收。两端页面在 1440、1024、390 宽度覆盖取消删除、确认删除、防重、409 冲突及受保护模板无删除入口；Portal 生产构建、OpenAPI 快照、两仓架构边界和双向 AIOps 一致性检查通过。未部署、未重启，未删除任何线上模板或其他业务数据。

浏览器回归须覆盖首次从卡片直接查看、编辑后再查看、深浅主题以及 1440/1024/390 三种宽度，检查版本控件宽度、主题行自然高度、检查列表换行和无横向溢出；API 继续隔离，不以截图代替线上验收。
