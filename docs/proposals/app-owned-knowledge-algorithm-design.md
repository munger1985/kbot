# App 独占数据的解析、索引与多模态召回算法设计

日期：2026-11-05。状态：K0/K1 G-A 通过；App/Runtime 基础组件、原生解析/表示端口与可选扫描已编码并通过离线回归，正式产品接入和真实质量未验证。适用：KBot4 与 Ammolite。

本文是底层算法模块的目标设计，不表示现有服务、接口或数据库已经完成替换。两仓库保持本文一致；平台鉴权、数据库、部署方式可以不同，算法合同与产品语义相同。

文档职责与生效顺序见[基础能力设计](../architecture/knowledge-answering-capability.md)。进程、App 物理表、内部传输、Runtime Artifact/实际模型交付合同见[接入与持久化详细设计](app-owned-knowledge-integration-detailed-design.md)，工作包与发布门禁见[实施计划](../operations/app-owned-knowledge-implementation-plan.md)。旧公共 KC 存储和固定助手方案不再是可选目标。

本次补全解析算法说明、召回执行顺序及论文类文内图文双向联动合同，并明确本版不实现独立模型重排，采用 RRF 融合与确定性证据选择，补齐防证据丢失合同。架构、流水线、对象身份与必需行为已经确定；最终解析器路由、复杂版面子算法、质量阈值、检索模型及预算仍须原型评测后冻结，不能把待验证方案表述为已经实现或已取得质量提升。

## 1. 已确定的边界

1. 仅复用算法代码、模型推理能力与标准合同，不建设公共文档库或跨 App 检索服务。
2. 每个 App 只检索自己拥有的文档，正文、图片、引用、检索单元及索引物理隔离。
3. 不提供 App 列表查询、跨 App 路由、联邦检索、跨 App 结果融合或引用跳转。
4. 通用解析器不访问业务数据库，不决定审批、发布、撤回或 App 数据表。
5. 解析结果由 App 接收，再通过其 Repository/UoW 落库；API 和应用编排层不得直接操作 SQLAlchemy Session 或执行 SQL。
6. 通用召回算法通过 App 绑定的存储端口读取本 App 数据，不掌握其他 App 的连接、表名或索引。
7. 不强制全部解析产物常驻内存；支持有界内存、流式交付和任务级临时制品。
8. 文档版本、原始证据、定位与模型快照必须可追溯；同一 App 内的跨文档引用仍然支持。
9. 目标是检索质量，不要求保留 Bundle 两阶段门禁、单向量接口或旧模型配置结构。
10. 新模块从现有 KC 中提取、重构，不复制为第二套长期并行实现，不保留旧接口兼容路径。
11. 已解析、获授权且可用的文内图文引用必须双向关联、成组返回，不依赖文字与图片恰好同时被向量检索命中；预算不足或目标不可用时明确报告。
12. 本版不实现 cross-encoder、跨模态 reranker 或 LLM rerank，不新增模型类别、绑定、配置、接口或占位依赖；独立模型重排不是待补齐的必要模块。保留检索内评分、RRF 融合与确定性覆盖/预算选择，未配置 reranker 不算降级。

“App”指服务端登记的业务模块，不是一个用户、Domain 或每次安装。Tenant、Domain、Agent、资源权限继续在本 App 内生效。

## 2. 总体结构与依赖方向

~~~text
App 入库用例
  -> ParseEngine
  -> ParsedDocument / ParseEvent 流
  -> App 领域增强与合法性校验
  -> App Repository/UoW 保存规范解析数据
  -> ProjectionBuilder 构建检索单元与表示
  -> App 自有检索投影
  -> App 发布并切换可检索快照

App 检索用例
  -> App 授权得到 AuthorizedScope
  -> RetrievalEngine + 本 App 的 RetrievalBackend
  -> 词法 / 文本向量 / 跨模态向量 / 多向量
  -> 对象去重、词法信号族归并、RRF 融合
  -> 覆盖与预算选择、必需图文关联及同 App 引用扩展
  -> EvidenceSet
  -> App 直接展示，或交给 Runtime Document/统一 Composer
~~~

算法模块对 App 的调用只经过注入的端口。端口由 App 组合根绑定，不能从用户提交的 App 名、表名、连接串或任意 Python 路径动态选择。

每个 App 单独构造自己的 RetrievalEngine 实例并固定 AppBoundBackend；不存在接收所有 App 搜索请求再选择数据库的公共检索实例。复用相同 Python 类不代表复用候选池、运行状态或缓存。

共享 GPU 进程不等于共享文档库。模型服务只处理本次获授权的输入，不建立面向所有 App 的搜索入口、全局候选缓存或文档目录。

## 3. 模块组织

新增独立、无业务持久化依赖的包：packages/knowledge_algorithms/src/knowledge_algorithms/。

~~~text
knowledge_algorithms/
  contracts/       # 文档、解析、表示、检索、证据、错误合同
  parsing/         # 路由、规范化、版面、结构、质量修复
  projections/     # 检索单元规划、表示构建、依赖指纹
  retrieval/       # 计划、通道编排、融合、覆盖与预算选择
  references/      # 引用出现提取、同 App 目标匹配规则
  evidence/        # 定位校验、证据集合及来源链
  ports/           # 转换、模型、临时制品、检索存储端口
~~~

依赖要求：

- contracts、retrieval、evidence 不导入 ORM、FastAPI、App、平台 IAM 或 Docling 对象。
- Docling、MinerU、PaddleOCR 等具体适配器位于执行解析的服务侧，转换为中立合同。
- SQL、全文表达式、向量库调用、事务、任务领取和重试状态均位于 App/基础设施侧。
- Model Serving 负责推理；算法包依赖 ModelGateway，不导入具体模型实现或密钥配置。
- 通用检索编排、融合与证据选择不是 platform_clients 的职责；platform_clients 只承载实际存在的进程间客户端。
- 不把 App 审批、领域排名、运维业务、业务表实体移入算法包。
- 解析大依赖按执行器安装，不能因知识检索请求导入而强制加载转换器或 GPU 模型。
- 安装、发布清单和工作区包检查已同步；中立引擎、线合同、资源边界和未实现范围见[实施记录](../operations/app-owned-knowledge-k0-k1-progress.md)。尚未接入生产 App，不表示真实转换器或模型质量已通过。

App 自有知识模块包括 application、domain、repositories、persistence、adapters、workers。App 不必拥有独立微服务：同一进程中的不同 App 模块也必须分别绑定数据适配器。

当前两 App 的检索在各自服务进程内执行。Runtime 不注入 App Repository、不访问 App 数据库，仅按已验证执行规格的 owner App 选择服务端登记的固定 AppRetrievalPort/AppContentPort；不调用知识检索 App 来检索 AIOps 数据。纯解析进程保留受控计算任务与按 App 隔离的临时制品，不保留公共正文库。具体调用与认证按接入详细设计执行。

## 4. 中立合同与身份

### 4.1 文档与解析合同

| 合同 | 核心字段与约束 |
|---|---|
| SourceDescriptor | App 内文档版本引用、内容 SHA-256、真实 MIME、大小、受控读取句柄；不接受任意外网 URL |
| ParseProfile | 配置版本、语言、质量目标、转换/OCR/VLM 策略、资源预算；任务开始冻结 |
| ParseRun | run_id、输入指纹、解析器与模型快照、尝试代次；不等于业务发布版本 |
| Page | 页序、几何尺寸、旋转、原图引用；Office 逻辑定位可不伪造页码 |
| ContentNode | local_key、类型、父节点、阅读顺序、内容、定位、来源；与数据库主键无关 |
| VisualAsset | local_key、PAGE/FIGURE/PHOTO/REGION、原图引用、裁剪变换、图题与邻近节点 |
| ReferenceOccurrence | 源节点与字符跨度、原始引用字符串、引用类型、规范图号/标识符、编号作用域、目标提示及解析状态；解析器不查其他 App |
| FigureIdentity | 文档版本、解析代次、figure_key、原始/规范图号、章节编号作用域、子图身份；图号不是主键 |
| ResolvedRelation | relation_key、关系类型、源/目标对象及版本、引用出现、解析依据、状态与置信信息 |
| ParseManifest | 对象计数、有序分块摘要、模型与解析版本、质量报告、完成状态 |
| ParsedDocument | 规范结构、内容对象、视觉资产、引用出现和 ParseManifest；不包含数据库 Entity |

内容类型至少覆盖 DOCUMENT、SECTION、PARAGRAPH、LIST_ITEM、TABLE、TABLE_ROW、FIGURE、CAPTION、FORMULA、CODE、FOOTNOTE、IMAGE、REGION。PAGE 是物理视图，可与章节树同时存在，不能强制一段内容只有一种层级。

每项表示区分 NATIVE、OCR、MODEL_TRANSCRIPTION、MODEL_DESCRIPTION、APP_DERIVED；模型描述不是原文。结构推断也保存来源、生成器和置信信息。

所有 local_key 在一次确定的解析输出内稳定，基于原生引用/规范位置及算法版本生成；不承诺更换解析器后仍然相同。App 保存 local_key 到自身主键的映射。旧引用必须指向其原解析代次，不能按新主键猜测回填。

### 4.2 位置合同

- 物理页面：document_version、page_no、归一化左上角 bbox，并记录原始坐标、旋转与变换。
- 原生 Office：段落、形状、工作表、单元格等逻辑位置；渲染图另存映射。
- 表格：表、行列、合并单元格、跨页续表关系。
- 图片裁剪：原图身份、父页面和裁剪变换，允许精确返回区域或原图。
- 文本跨度：对应的原始内容节点和字符范围；规范化文本另存映射。

没有可靠页码或坐标时返回逻辑定位及警告，禁止生成假的定位。摘要、图片说明与模型补全只能通过其来源链回到证据。

### 4.3 检索与证据合同

| 合同 | 核心内容 |
|---|---|
| SearchUnit | unit_key、内容对象引用、单元类型、可检索文本、上下文、原始跨度、投影版本 |
| RepresentationSpec | space_id、模型/处理器/权重快照、输入类型、输出形状、归一化、相似度、任务能力 |
| Representation | 单向量或 token 矩阵、mask、来源单元、输入指纹；不把二者混成 list[float] |
| QueryInput | 文本、图片、可选区域、组合方式、输出类型、查询模式、可执行谓词、用户指定数量/顺序 |
| QueryPlan | 通道、查询改写、预算、覆盖目标、确定性证据选择与扩展策略；不能更改授权范围 |
| AuthorizedScope | App 端构造的不可扩大范围、授权快照、允许版本/集合条件与撤回代次 |
| Candidate | unit_key、精确对象身份、通道排名和原始分数、匹配区域、检索快照 |
| CoverageTarget | 目标键、比较对象/子问题/输入图/文档条件、用户约束跨度、必需性、计划版本 |
| CandidateTargetMatch | 目标与证据键、结构字段/锚点/子查询等匹配依据、来源及 MATCHED/UNKNOWN/CONFLICT；不是答案支持分数 |
| LinkedEvidenceGroup | 一个主命中及其必需图文关联、可选上下文、引用边和关联覆盖状态；不等于业务 Bundle |
| EvidenceSet | 有序主命中、关联证据及分组、定位、关系来源、覆盖与通道健康信息；不强制先生成回答 |
| RetrievalTrace | 策略/模型/索引版本、阶段计数与身份流转、排除原因、耗时、预算截断和通道状态；不默认记录原文或图片 |

RepresentationSpec 必须声明支持哪些查询到对象方向，例如 TEXT_TO_TEXT、TEXT_TO_IMAGE、IMAGE_TO_IMAGE、TEXT_TO_PAGE。具有图片输入能力不自动证明适合图搜图；未评测或不支持的方向不能静默启用。

App 归属由服务端固定的 BackendBinding 确定。算法请求没有 app_ids 或目标 App 路由字段。算法包不规定平台必须新增 app_id 鉴权字段；复用各平台已有可信上下文。

AuthorizedScope 必须绑定签发它的服务端 BackendBinding，后端校验绑定及授权快照。即使不同 App 恰有相同的文档 ID，也不能将一个 App 的 scope 或 Candidate 交给另一个 App 的适配器读取。

### 4.4 核心接口

下面是待实现的类型化接口示意，不是现有 Python API；Referenced 类型均为 contracts 中的数据合同，方法不得接收 Session、表名或任意 App 路由。

~~~python
class ParseEngine:
    def parse_events(
        self, source: SourceReader, profile: ParseProfile, run: ParseRun,
    ) -> AsyncIterator[ParseEvent]: ...

class ProjectionBuilder:
    def build(
        self, document: AllowedDocumentReader, profile: ProjectionProfile,
    ) -> AsyncIterator[ProjectionBatch]: ...

class RetrievalEngine:
    def __init__(
        self, backend: AppBoundBackend, model_gateway: ModelGateway,
        text_scan: TextScanPort | None = None,
    ): ...

    async def retrieve(
        self, query: QueryInput, scope: AuthorizedScope,
        profile: RetrievalProfile,
    ) -> EvidenceSet: ...

class AppBoundBackend:
    async def snapshot(self, scope: AuthorizedScope) -> RetrievalSnapshot: ...

    async def search_ordered(
        self, request: OrderedRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def search_lexical(
        self, request: LexicalRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def search_dense(
        self, request: DenseRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def search_multivector(
        self, request: MultiVectorRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def search_near_duplicate(
        self, request: NearDuplicateRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def follow_relations(
        self, request: RelationTraversalRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> RelationPage: ...

    async def expand(
        self, request: ExpansionRequest, scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> CandidateBatch: ...

    async def load_evidence(
        self, keys: tuple[EvidenceKey, ...], scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> EvidenceBatch: ...

    async def revalidate(
        self, keys: tuple[EvidenceKey, ...], scope: AuthorizedScope,
        snapshot: RetrievalSnapshot,
    ) -> ValidationResult: ...
~~~

SourceReader、AllowedDocumentReader 和制品读取都由 App 绑定且受限；AllowedDocumentReader 只提供本 App 已准许用于索引的视图。ProjectionBuilder 注入 ModelGateway，但不写存储。ProjectionBatch 由 App 的写入适配器持久化。

各 SearchRequest 包含对象类型、查询表示/空间、Top-K、超时和分页/预算条件。DenseRequest 明确文本或跨模态空间，MultiVectorRequest 明确矩阵和 mask。每个后端方法均强制传 scope 与 snapshot，禁止“加载上下文时省略权限”。

SearchRequest 还声明查询模式、可执行资格谓词、原生 order_by 与稳定游标；后端必须支持该模式才能受理。跨分片返回的排名/分数必须标明 space、评分合同、统计范围及是否近似，不能把分片局部名次当全局名次。具体线协议及 Scope 大集合持久化见接入详细设计；不传 Python 过滤表达式、Session 或全部 ID 到 JWT。

search_ordered 专门执行 FILTERED_ORDER/EXHAUSTIVE 的结构化资格与排序/分页，可不生成 embedding、不调用 LLM；其排序键和范围完整性不能由 search_dense 的候选后处理替代。OrderedRequest 只允许 App 登记的谓词/字段，不能携带 SQL。

CandidateBatch 包含候选、通道状态、索引身份及是否穷尽；空列表不是故障或能力不足的替代。revalidate 是发布、授权及证据状态的复核，不查询或校验数据库 Schema。

ReferenceCatalog 和 Citation 预览也使用相同的 scope/snapshot 约束。App 接收端自行编排事务，解析器和 ProjectionBuilder 都不调用其 Repository。

TextScanPort 是独立可选端口，默认不注入；核心不依赖具体 ripgrep 实现，也不将扫描加入 AppBoundBackend 的必实现方法。端口只接受结构化扫描请求、当前 scope/snapshot，返回匹配位置而不是伪造相关性分数，详见第 8.11 节。

follow_relations 专门读取已保存的显式关系，不重新用向量推测引用。RelationTraversalRequest 指定锚点、关系类型、正向/反向、分页与预算；RelationPage 返回获授权关系、目标证据键、解析状态和受控续取游标。expand 用于可选邻段等上下文，不能替代必需的图文关系读取。

### 4.5 策略预算与失败合同

| 配置 | 必须显式记录的预算 |
|---|---|
| ParseProfile | 输入大小/页数/像素、并发、内存/时间、修复次数、允许的局部失败策略 |
| ProjectionProfile | tokenizer、单元长度、重叠、表格行组、视觉分辨率、张量/token 上限 |
| RetrievalProfile | 每路线候选数、融合预算、证据选择与覆盖策略、总超时、扩展深度/扇出、证据载荷预算 |

用户结果数量与内部候选预算分开。无效或互相矛盾的参数应拒绝，而不是截断后假装满足；服务上限导致无法满足用户数量时明确说明。参数在实验后冻结，不以本文未验证的数字作为默认质量承诺。

最低错误类别：UNSUPPORTED_INPUT、RESOURCE_LIMIT、PARSE_QUALITY_INSUFFICIENT、ARTIFACT_EXPIRED、MODEL_SPACE_MISMATCH、MODALITY_UNAVAILABLE、SCOPE_CHANGED、SNAPSHOT_STALE、CHANNEL_FAILED。实施时固化完整错误码和重试属性。

检索整体状态区分完整成功、部分/退化、空结果和失败，并另行报告 capability、coverage、channel_status。合法零命中不能包装成失败；必需通道故障不能包装成合法零命中。

无候选、全部候选不合法/不可读、有效单元无法装入预算、映射/组装失败和回答上下文交付失败必须区分，返回真实阶段、原因及可重试性。已有有效证据却在后处理阶段丢失，不能以“知识库没有数据”掩盖。具体防丢失约束见第 8.12 节。

## 5. 解析算法

### 5.1 输入检查与格式路由

App 先保存原始文件和持久化任务，再交给执行器。执行器校验内容哈希、MIME 与大小，限制解压比例、页数、像素、转换时间、外链和主动内容；复杂转换在受限进程中执行。

路由按文件实际能力，而不是只按扩展名：

1. 原生 Office/HTML/结构化文本优先提取逻辑结构，必要时另渲染页面。
2. 数字 PDF 先取原生文字、版面与内嵌对象。
3. 扫描页采用 OCR；混合 PDF 按页或区域判断，不强制全文件 OCR。
4. 自然图片保留原图，OCR 和描述是辅助表示，不把整图等同于文字文档。
5. 表格、公式、代码使用专门结构，不一律转成无类型长文本。

Docling 是首个可保留适配器，不是中立合同。MinerU/PaddleOCR 可作为实验适配器，由同一评测决定具体语料的路由选择。

采用组合式管线：专业解析器提供识别与版面候选，自有算法负责规范化、结构恢复、质量判定及局部修复，不要求自行训练端到端解析模型。

PDF 图片对象不能只来自内嵌位图。矢量绘图、复合图表也须通过版面区域及页面渲染裁剪保留；原生图片、整页与裁剪区域分别建对象，并记录来源及几何变换。

### 5.2 质量检测与局部修复

每页/区域计算质量向量，不只看文字长度：

- 原生字形、文字区域与提取文本覆盖是否一致。
- Unicode 异常、乱码、重复行、页眉页脚重复。
- 多栏阅读顺序、标题层级、正文连续性。
- 表格单元格覆盖、行列结构及续表一致性。
- 文字区域、图题和图片的空间对应。
- OCR/VLM 结果与图像及原生文字的对齐情况。

处理过程：

~~~text
基础提取
  -> 质量检测
  -> 仅对失败区域选择 OCR / 高精度解析 / VLM 转写
  -> 对齐、去重、保留候选来源
  -> 复评
  -> 达标、局部失败或整体失败
~~~

阈值和最多修复次数属于版本化 ParseProfile，须用标注集校准。预算到达或连续无改善后停止，不无限调用模型。OCR 自报置信度、模型输出流畅程度不能单独作为通过条件。

修复结果不能覆盖不可变原始提取记录。VLM 转写、解释、推断分别标注，未知内容保留未知，禁止把推测数值写成表格事实。

质量是多维报告，不把所有模态压成一个未经校准的分数。可计算信号包括文字区域与提取框覆盖、异常字符率、重复率、阅读顺序冲突、表格结构一致性和定位有效性；这些是待验证信号，不等同于识别正确率。结构树覆盖全部已提取节点，也不能证明没有漏掉原文内容。

无文字的照片可以是有效视觉解析结果，不能套用“未提取到正文即失败”的统一门禁。是否达标按内容类型、失败区域和可用模态判定。

局部修复的合并依次进行坐标/跨度对齐、重复识别、缺失补齐及冲突记录。保留原始候选，另标记当前采用视图；无法判定的冲突不得仅按输出长度、模型自报置信度或多数投票直接覆盖。

~~~python
base = extract_native_or_scan(source, profile)
while repair_budget_available():
    issues = assess_regions(base, rendered_pages, profile)
    if not issues.repairable:
        break
    candidates = repair_selected_regions(issues, profile)
    updated = align_and_merge_with_provenance(base, candidates)
    if not measurable_improvement(base, updated):
        base = retain_alternatives_without_replacing_active(base, updated)
        break
    base = updated

structure = reconstruct_structure(base, profile)
local_relations = resolve_local_references(structure, base, profile)
report = evaluate_final(base, structure, local_relations, profile)
emit_parse_result(base, structure, local_relations, report)
~~~

以上为目标伪代码，不是已实现 API。最终报告仍可为局部失败或整体失败，emit 不代表通过发布门禁；修复收益的判定规则必须通过标注集校准。

### 5.3 结构重建

- 结合原生样式、几何布局与阅读顺序识别标题；规则有歧义时可调用受约束模型建议。
- 去除检索文本中的重复页眉页脚，但原始节点仍可追溯。
- 表格保留标题、列头、单位、单元格与跨页关系。
- 图片与图题、正文指向、所在章节关联；独立图片和整页都可检索。
- 解析显式“见图/表/章节”和文献引用的出现位置，不在这一阶段生成全库语义图。
- 所有结构修复保留算法依据，不用单次 LLM 重写整份文档。

阅读顺序综合原生顺序、版面分区、栏结构和块间空间关系，跨栏标题/表格单独约束；不以整页纵坐标简单排序。章节树综合原生标题级别、编号、字体和版面候选，使用有来源的层级决策，歧义保留而不是任意补标题。

跨页表格合并综合列结构、表头、位置与上下文；仅相邻页都有表格不构成续表证据。图题与图片的几何接近只是候选线索，不能替代正文引用解析。

当前代码已有坐标/分栏间隙启发式、标题级别与编号结合的栈式章节构建，以及空文本、重复、乱码、节点覆盖检查。这些是基线，不是已校准的新算法。最终的复杂版面排序形式、跨解析器冲突选择及门槛仍属于待验证决策，不能直接沿用旧经验常量。

### 5.4 流式输出与完成语义

统一使用 ParseEvent 流；小文档的 parse() 只是将同一流汇总为 ParsedDocument。

事件族：RUN_STARTED、PAGE_BATCH、NODE_BATCH、ASSET_BATCH、REFERENCE_BATCH、STRUCTURE_FINALIZED、RUN_COMPLETED、RUN_FAILED。事件包含 run_id、sequence、batch_key、内容摘要及依赖键。

全局阅读顺序、跨页结构在 STRUCTURE_FINALIZED 前允许待定；App 可以暂存批次，但最终 Manifest 校验完成前不能将半成品发布为完整解析结果。结构补充以显式事件交付，不覆盖已提交批次内容。

生产者和消费者使用有界队列与背压。图片、页面和张量以字节流或受控临时制品交付，不将全部二进制 Base64 塞入一个 JSON。

流式接口本身不保证底层转换器低内存。每个适配器必须声明是否支持分段读取及其峰值内存边界；全量物化的转换器应在受限进程中运行，超出预算则切换分段适配器或明确拒绝，不能仅靠逐批发送结果声称已解决大文档内存问题。

同进程可注入临时制品端口；跨进程由标准任务/事件协议传输，不传 Python 回调或 App 数据库会话。临时制品的路径/桶由可信配置确定，调用者只能获得受限句柄。

App 只有在批次落库成功后确认消费。交付语义为至少一次，App 用任务代次、batch_key、摘要和事务内串行化保证幂等；同键不同内容必须冲突。取消和失效任务用租约/栅栏代次拒绝迟到写入。

若恢复时必须重新调用非确定性模型，而不是重放已保存批次，应建立新的 ParseRun；不能复用旧批次键再接受不同内容。局部失败页清单和可用模态进入 Manifest，由 App 的明确质量策略决定是否接收，不能静默跳页后宣称完整成功。

任务元数据和恢复点持久化，不放在唯一的进程内存里。制品完成持久接收后再按确认和保留策略清理；过期不应导致成功任务被宣称可恢复。不同 App 不共用解析缓存或临时制品命名空间。

### 5.5 图号解析、图片身份与显式图文关系

以正文“系统结构如图 1-1 所示”为例，必须区分正文段落、引用出现、图题、逻辑图片与实际载荷：

~~~text
正文段落 P --REFERS_TO〔引用出现“图 1-1”〕--> 逻辑图片 F
图题 C     --CAPTION_OF------------------> 逻辑图片 F
逻辑图片 F --HAS_ASSET-------------------> 原图/裁剪图 A
子图 F-a   --PART_OF---------------------> 逻辑图片 F
~~~

图题不是引用图片的正文，两者不能只保存为一个 description 字段。一个段落可引用多图，一张图可被多个段落引用；每次引用出现均保留字符跨度和源位置。

图片主身份是 document_version + parse_run + figure_key。display_label 如“图 1-1”仅用于展示和目标解析；同一文档章节编号重置时还需 numbering_scope，不能把裸图号做全 App 唯一键。

解析步骤：

1. 从原生 Word/PDF 链接或交叉引用锚点提取候选；核验目标类型、文档版本及图号是否一致。
2. 结合图题、编号和版面建立文档内图片目录，保存原始图号及规范化形式。
3. 识别正文中的显式图/表/章节引用，生成 ReferenceOccurrence；识别规则、语言与编号格式属于版本化解析策略，不写领域特例。
4. 优先按可靠原生锚点解析，再用文档内图号、编号作用域、子图标记和上下文消歧。
5. 无可靠唯一目标时返回 AMBIGUOUS、UNRESOLVED 或 MISSING_TARGET，并保留原文；不能强连最近图片，也不能借助其他 App 补齐。
6. 在同一最终解析代次中输出解析成功的关系与未解析出现，App 通过自己的 Repository 保存。

规范化须保留原文映射。不能无条件把点号、连字符和各种编号体系视为相同；OCR 的“1-l”不能未经核验直接改成“1-1”。原生锚点与图号冲突也要显式报告，不因来源是原生结构便自动忽略冲突。

正文与目标图片可以跨页或跨章节；空间距离只能辅助消歧，不能限制为同页或相邻切片。子图必须关联到对应区域，区分整张复合图与单独的 (a)/(b) 面板；无法分离时保留完整图并说明子图定位不足。

App 为 REFERS_TO、CAPTION_OF、HAS_ASSET、PART_OF 保存可正向和反向查询的关系。物理查询索引按源、目标和文档版本/解析代次建立；反向读取不需要复制一条语义相反的假关系。

不要求引入专用图数据库；App 自有关系表及正反向查询即可实现这组显式关系。关系及节点必须在同一快照中有效，不能把旧版“图 1-1”连到新版图片。

### 5.6 原型评测后才能冻结的解析决策

| 已确定的算法职责 | 仍需验证的具体选择 |
|---|---|
| 按格式/区域路由，不盲目整文档 OCR | 具体解析器、困难页判定和路由参数 |
| 根据版面与结构恢复阅读顺序 | 复杂多栏、跨栏对象的排序子算法与冲突处理 |
| 原文与修复候选分开保存 | 跨解析器文本/表格结果的对齐和采用准则 |
| 多维质量检测及有界局部修复 | 指标校准、阈值、收益判定和修复预算 |
| 明确图文关系、歧义不强连 | 编号策略、子图分割及置信阈值 |

这些是实现前后的受控实验任务，不是已经完成的模型或解析效果验证。

## 6. App 接收、领域增强与存储

App 的接收用例分为四步：

1. 校验任务来源、源文件版本、事件顺序、摘要、引用完整性和资源预算。
2. 经 Repository/UoW 写入本 App 的暂存解析代次及批次，提交后确认消费。
3. 最终校验 Manifest，冻结规范解析结果，运行 App 领域增强与索引构建。
4. 仅当 App 所需通道就绪且业务门禁通过时，切换可检索快照。

App 可提取错误码、产品版本、尺寸、材料等领域信息，追加自己的表和搜索单元；原文及通用定位不可被覆盖。用于过滤的模型推断必须有来源和不确定性，不能无提示地排除可能相关资料。

App 的存储集合至少覆盖：document/version、parse_run、content_node、visual_asset、reference、search_unit、representation、index_generation、ingestion_job，以及需要可靠异步索引时的 outbox。

reference/关系存储要保存引用出现与已解析边，支持正文到图片、图片到引用正文的双向读取。关联图题、原图和子图的映射随同一解析代次提交，不能只落正文与图片向量却丢弃引用关系。

这些逻辑集合已在接入详细设计第 4 节映射为逐 App 物理表清单，包括批次、单元来源、范围快照、回执与历史证据 pin。表映射和访问索引由实施 K0 逐 App 冻结，不能回到“所有 App 共用解析正文表加 app_id”；不把未定义的数据模型作为实现时的隐式自由度。

- PostgreSQL 使用登记的 App 表命名空间；Oracle 遵循 KBot 的规范 DDL。
- 不按用户输入、Domain 或每次安装动态建表，不暴露任意表名参数。
- 各 App 的对象目录、全文/向量/多向量索引和查询结果缓存均物理或引擎原生集合隔离。
- 表隔离之外仍校验 Tenant、Domain、Agent、文档状态、发布资格和安全等级。
- 应用层不执行 SQL；App 适配器实现查询，UoW 拥有事务。
- KBot 的业务幂等与唯一性不得依赖新增 UNIQUE/CHECK 或伪装成唯一索引；使用应用校验和适当锁定。
- 不在启动或业务请求中检测、建造或修复自身表结构；DDL 只在部署与验收流程执行。

脱敏必须发生在所有可检索表示构建之前。若 App 禁止向检索使用某字段，不能仅删除文本，却仍让原始截图、图片说明、向量或回答上下文泄漏它。需要另存带来源映射的允许视图，并让所有相应表示绑定同一视图。

## 7. 索引构建算法

### 7.1 解析与切分解耦

ParseEngine 输出结构事实；ProjectionBuilder 根据版本化 ProjectionProfile 生成 SearchUnit。调整切分、embedding 或证据选择策略通常不重跑转换/OCR。

基础单元策略：

- 正文按章节、段落与语义边界组合，长段落在句子边界分割。
- 标题路径可加入检索文本，但不伪装成原文跨度。
- 表格同时建立表级、带列头和单位的行组单元，保留单元格映射；不把每格无条件独立化。
- 代码与公式尽量保持完整，必要时按可解释边界分割。
- 图片建立 FIGURE/PHOTO 单元，页面另建 PAGE 单元，两者不能用相同键覆盖。
- 区域单元保留父图片和 bbox；跨页内容以来源列表连接。

长度由目标模型 tokenizer 和 Profile 预算约束，不固定一套字符数适配所有语言与模态。上下文重叠保留映射，不能让重复副本在融合中获得多次加分。

SearchUnit 必须保留到 ContentNode、FigureIdentity 和 ReferenceOccurrence 的映射。切分正文后，仍能从命中片段的来源跨度定位其显式图文引用；重切分不重猜图号，也不破坏反向查询。

### 7.2 并行表示

每个 SearchUnit 按已评测能力生成所需表示：

| 路线 | 输入与用途 |
|---|---|
| 词法 | 正文、编号、图题、允许的 OCR/领域字段；保留精确术语 |
| 文本 dense | 文本专用模型，覆盖文搜文与表达改写 |
| 跨模态 dense | 对齐模型的 text/image 两个方向，覆盖文搜图及语义图搜图 |
| 多向量 | 文档页/区域及适用的查询，保留 token/patch 矩阵做细粒度匹配 |
| 近重复 | 原始内容哈希、感知哈希或局部特征，服务找原图/近重复，不冒充语义相似度 |
| 显式关系 | 结构边及同 App 文档引用，为受控扩展服务 |

另可按 App 显式启用独立文本扫描组件，为精确补召回构建带来源映射的 UTF-8 文本投影；该投影不是核心索引必需项，也不替代全文/向量或引用关系。

不是每个单元都强制生成全部表示。必需/可选路线由 App 的能力合同决定，未生成的能力必须可见，不能返回伪装为完整搜图的文本退化结果。

全文查询由数据库适配器安全生成，保留错误码、型号、数字、中文等信息；不将用户字符串直接拼接成 Oracle Text/ParadeDB 表达式。不在算法核中写数据库特有查询语法。

### 7.3 模型空间与张量合同

space_id 覆盖模型权重/适配器、revision、处理器、输入模板、维度、归一化及距离定义。查询只能进入完全匹配且支持当前方向的空间。

多向量表示包含 token_count × dimension、dtype、有效 token mask，必要时包含 token 到页面区域的映射。禁止用对 ColQwen/ColPali 输出直接求均值替代其原生算法。

MRL 截断、量化、token 聚类压缩均属于新表示配置，需要独立指纹与质量验证；不能把压缩后的索引仍标记为原空间的未经压缩输出。

只存向量不足以完成证据检索，必须能加载其对应的原文或图片。生成式描述、摘要和领域信息可以辅助召回，但不能取代原始证据。

### 7.4 依赖指纹与更新

~~~text
原始文件
  -> 规范解析代次
  -> App 允许视图 / 领域增强
  -> SearchUnit 代次
  -> Representation 代次
  -> IndexManifest
~~~

每条依赖记录输入摘要、算法/配置版本和实际模型快照。输入或依赖变化仅失效其下游。

同一 App 的重复计算缓存必须包含授权命名空间和完整指纹；不同 App 即使文件 Hash 相同也不跨 App 复用结果。调整融合权重或上下文预算不要求重做 embedding；换 embedding 必须建匹配的新索引；修改原图裁剪会失效对应视觉表示。

## 8. 召回算法

### 8.1 查询合同与计划

App 先得到 AuthorizedScope，再调用：

~~~text
app_engine.retrieve(QueryInput, AuthorizedScope, RetrievalProfile)
    -> EvidenceSet
~~~

QueryInput 支持纯文本、纯图片、图片加文字、显式区域；指定结果类型如 TEXT、FIGURE、PHOTO、TABLE、PAGE 或 MIXED，并区分语义相似与近重复查找。

查询模式固定区分 RELEVANCE（相关性候选）、FILTERED_ORDER（可执行资格范围内按属性取前 N）与 EXHAUSTIVE（可穷尽谓词的范围枚举）。用户“最新 N 条”不能只在相关性 Top-K 后排序；谓词、排序及稳定分页下推到 App 后端。自然语言语义相关集合无法证明穷尽时，明确返回候选内排序/部分覆盖或请求缩小到可执行条件，不将语义 Top-K 伪装为列全。模式与游标合同见接入详细设计第 5.1 节。

用户指定的数量、排序和版本条件必须进入结构化合同，不能被查询改写、融合或证据选择悄悄覆盖。结构化计划可用受约束 LLM 提议查询词和任务，不允许模型选择 App、扩大权限、删除硬条件或承担逐候选相关性裁决。失败时使用确定性基础计划，返回告警；不借查询规划恢复 LLM rerank。

多图片查询显式声明 ANY、ALL 或 COMPOSED。ANY 可按独立查询融合；ALL 必须检查同一对象或证据集合是否覆盖全部输入；COMPOSED 仅在有已评测组合能力时启用。不能把多张图向量直接平均后声称支持全部语义。

### 8.2 通道选择

| 任务 | 基础召回 | 融合、覆盖与上下文补充 |
|---|---|---|
| 文搜文 | 词法 + 文本 dense | RRF、问题覆盖、章节/表格上下文 |
| 文搜图 | 跨模态 text->image + 图题/OCR 词法 | RRF、显式图文关联；文档图表可加多向量 |
| 图搜图 | 支持该方向的跨模态 image->image | 区域匹配；找原图时加近重复路线 |
| 文搜视觉文档 | 跨模态 dense + 独立多向量召回 + 词法 | 原生 late interaction、RRF、页面/区域原图证据 |
| 图文混合 | 经评测的组合模型，或显式多路策略 | 保留各输入覆盖信息，不宣称与组合模型等价 |

自然照片与文档截图使用各自的能力评测，不能因支持 TEXT_TO_PAGE 就默认支持高质量 IMAGE_TO_IMAGE。

多向量需要独立召回路线；若只对 dense Top-K 做 MaxSim，必须标记为“候选内原生多向量复评分”，不能宣称解决 dense 漏召回。MaxSim 是该检索表示自身的匹配函数，不是新增独立 reranker；实现中不能借此接入专用重排模型。小规模可以授权范围内精确扫描建立质量上限，大规模再评估 ANN/压缩索引。

### 8.3 并行召回、过滤和预算

1. 在同一授权与索引快照内并发执行已启用路线。
2. 每条路线的 App、Tenant/Domain、发布资格、版本和资源权限必须在候选产生前约束。
3. 按稳定 unit_key 合并，保留通道排名、对象类型与原始分数。
4. RELEVANCE 模式按相关性候选预算截断，不先按上传时间裁掉可检索文档；FILTERED_ORDER/EXHAUSTIVE 则在完整可执行资格范围内原生排序/分页，不先取相关性 Top-K。
5. 后端无法在 ANN 中精确处理某授权条件时，须实现具备范围内 Top-K 正确性的执行策略或报告能力不可用，不能仅全库 Top-K 后过滤。
6. 预算、超时及覆盖不完整记录在响应里；不能把“只搜了一部分”伪装成全范围未找到。

在同 App 内搜索多个授权集合是允许的，不等于跨 App 检索。

用户指定数量是主命中数量，不是“正文、图题、附件各算一个结果”。显式日期等排序条件传递到最终主命中排名；相关性融合不能覆盖用户排序。图文附件和反向引用使用独立的载荷/分页预算，不挤掉用户要求的主命中。展示结果数量与实际送给回答模型的证据数量分别记录，不能因模型窗口有限而悄悄减少展示结果。

### 8.4 候选融合

初始使用加权 RRF：

~~~text
fusion(u) = sum_c weight(c) / (rrf_constant + rank_c(u))
~~~

每条路线仅对同一单元计分一次。同一模型的重复改写、同一内容的重叠窗口应先在通道内融合，避免通道数量制造虚假相关性。

rank_c 是同一 App 授权范围内的通道全局名次，不是分片内名次。先将相同 space/评分合同的原生结果跨分片归并，再执行通道间 RRF；分片不成为额外投票。BM25 使用同一统计/评分规则，不按分片分别 min-max 归一化，不先融合每片再只拿片内前 K。精确 fixture 在改变分片数、边界或返回顺序后结果应一致；近似 ANN、候选截断及超时须单独标记，不能保证全集精确融合。

可选 rg 不直接提供 RRF 名次。启用后将全文与扫描的对象映射归并成单一词法候选集合，再按可复现词法族规则产生一份 rank_lexical；规则、扫描独有命中及失败语义见组件设计第 6 节。未启用时使用全文全局排名，不加载或探测扫描组件。

不同模型的 cosine、MaxSim、BM25 原始分数不能直接相加。权重与候选预算按任务版本化并通过离线实验选择，不把某个固定值写死为所有 App 最优。

去重键包括精确来源、对象身份、解析/投影代次。禁止按 Bundle 或“文档+页码”提前去重，PAGE、FIGURE、同页多个区域应保留各自身份。最终可分组展示，但不能吞掉有效独立证据。

### 8.5 多向量评分

采用模型规定的 late interaction，例如：

~~~text
L(Q, D) = sum_i weight_i * max_j similarity(q_i, d_j)
~~~

Q 和 D 是同一兼容模型空间的 token 矩阵；padding 不参与评分。归一化、query 权重和聚合必须遵循模型定义，不能自行用长度平均或对称化改变分数语义。

检验空输入、零范数、NaN、溢出、mask、矩阵维度、截断和批次间一致性。查询图片可否作为 Q 由模型的任务能力决定。匹配热区是定位辅助，不自动成为“结论被支持”的证明。

### 8.6 无模型重排的融合与证据选择

本版以 RRF 作为完整基线，不实现文本 cross-encoder、跨模态 reranker 或 LLM rerank。当前没有配置 reranker，Model Serving 也没有该模型类型；设计不新增对应类别、绑定、配置、API、占位端口或普通 LLM 绕行。不是“默认关闭但上线前必补”，也不因缺少 reranker 标记降级。未来若重新提出，需要独立批准并证明相对当前基线的收益，不列入本版实施阶段。

必须区分三种职责：

- 检索内评分：BM25、cosine、模型原生 MaxSim 等，在各自兼容空间内产生候选及排名。
- 排名融合：RRF 汇总各通道名次，保留稳定对象身份与来源；调整顺序，不执行相关性删除。
- 证据选择：为有限上下文选择可交付的证据组，依据问题覆盖和载荷成本工作；未选中项保留在结果/Trace 中并标注预算或覆盖选择原因，不伪装成无命中。

确定性选择基线：

1. 使用 CoverageTarget 与 CandidateTargetMatch 保存覆盖目标、候选对应的结构/锚点/子查询命中依据及来源，不用硬编码领域词表猜测任务，也不调用 LLM 逐条裁决候选。无法判定时为 UNKNOWN，不声称已满足，也不因此清空候选；语义命中不等于已支持结论。
2. 先为可判定的必需目标预留最小有效证据组，再按用户排序（若有）或融合排名、稳定对象键补选；显式排序在其模式的完整资格范围内执行。高位大组阻塞其他必需目标时，可在有界次数内替换成同目标较小有效组；没有明确多证据目标时沿融合顺序装入预算，不承诺全局最优。
3. 精确重复内容不重复占用上下文；覆盖已满足后，再按融合顺序补充。不得强制“一文档一条”，也不以固定文档配额或未验证的 MMR/相似度阈值删除同文档内必要的不同证据。对象去重仍遵守第 8.4 节。
4. 选择前估算正文、必要表头/单位、直接图文关联的载荷成本，组装后核对实际成本；为必需附件预留预算。模型上下文上限来自 Model Serving 的真实能力配置，并扣除系统/问题、工具信息及回答输出预留；与 App 载荷上限取有效交集，图片成本按实际模型输入规则计算。
5. 单组过大时，只能沿可定位结构边界形成仍有用的单元，或标记 DEFERRED/预算不足并提供续取；不能任意截断到失去含义，不能因某一超大项放弃全部可装入的有效项。实际成本超限后有界重选，按目标记录预算/召回/载荷缺口，策略与重选上限须通过消融验证。

预算选择、授权/版本/可读性过滤与排名是独立阶段。不设置未经校准的统一相关性分数门槛清空候选，不把 RRF 分数当作答案置信度。领域业务排序增量仅可在 App 登记并单独验收，不得删除候选、扩大权限或把业务标签当作事实证据。

文本/视觉检索能力真实不可用时仍按任务报告通道或能力不足；这与本来就不实施独立模型重排无关。

### 8.7 上下文和引用扩展

以融合排名及覆盖/预算选择确定的锚点扩展同章节邻段、表格列头、图题、原图，以及同 App 内的明确引用目标。每条扩展边都经过相同授权、版本和撤回校验。

扩展分为必需图文关联与可选上下文两类。已解析且获授权、可用的直接图文关联按第 8.9 节成组带出，不能因没有独立分数或分数低而丢弃。可选邻段和多跳引用扩展按明确优先级及预算选择，不能因被引用就自动变成主要答案证据。

两类都设边类型、深度、扇出、次数和 token/图片预算，保留锚点及原因；达到预算必须报告关联不完整并提供受控续取能力。关联证据保留角色，不因必须带出就提升为 PRIMARY 或宣称支持答案。

若覆盖不足，可在同一 App 与授权范围内做有界补充检索；达到预算后报告不完整。模型建议不能跳到其他 App，也不能将外部文献解析成其他 App 的资源。

### 8.8 证据组装

输出保留 PRIMARY、CONTEXT、REFERENCED 等角色，以及每个证据的版本、位置、内容类型和实际可读载荷。

- 找图片直接返回图片对象、受控预览和精确来源，不要求先生成自然语言答案。
- 图片问答将实际原图/区域送入获授权的 VLM；不能只传图片说明。
- 多证据问题保留一组或多组可用证据，不能强制一文档一引用而丢失细节。
- 相关性分数与答案支持判断分开；答案生成/claim 校验属于上层能力。
- 检索阶段没有答案，因而不能宣称某候选已支持一个尚未生成的结论。
- 结构化返回完整排名；App 最终展示的回答 Reference 应与实际使用的证据一致。
- 主命中、已确认图文关联和可选上下文分别标记，正文与图片按 LinkedEvidenceGroup 组装；不能只返回一张脱离引用文字的图片或一个裸图号。
- 预览句柄、实际图片载荷和是否提供给回答模型分别记录。存在图片引用或预览地址，不代表 VLM 已读取图片。

### 8.9 图文双向带出是必需返回规则

在关系已解析、目标获授权且可用的前提下，以下是基础合同，不是可选实验功能：

| 主命中 | 必须关联返回 |
|---|---|
| 正文片段包含“如图 1-1” | 对应图片对象、图题、受控原图/区域预览及正文和图片位置 |
| 图 1-1 被文搜图或图搜图命中 | 图题、显式引用该图的正文段落及必要局部上下文 |
| 子图 1-1(a) 被命中 | 对应子图/区域及父图身份、匹配的引用正文，必要时完整复合图 |
| 图题被命中 | 对应图片，并按上述反向关系提供正文引用，不把图题当作正文解释 |

执行顺序：

1. 主命中按融合顺序和覆盖目标进入预算选择时，通过 SearchUnit 的来源映射定位实际内容对象；预读关联清单以估算组成本。
2. 正文命中时，按其来源跨度读取明确的 REFERS_TO；图片命中时反向读取 REFERS_TO，并读取 CAPTION_OF、HAS_ASSET 和必要的 PART_OF。
3. 关系读取和目标加载均执行本 App scope/snapshot 校验；返回前再次复核发布、撤回和权限。
4. 在单独记录的载荷预算内加载明确关系目标，不要求图片/正文再独立通过向量分数或相关性阈值。没有独立检索分数时保留为空，不能伪造分数；预算不足按下文清单/续取合同处理。
5. 组装 LinkedEvidenceGroup；相同图片/段落可复用载荷，但每个锚点到目标的关联与引用出现仍保留。
6. 之后再做可选的邻段或多跳补充，避免它们先耗尽直接图文关联预算。

必需联动限定为主锚点的一跳 REFERS_TO 及其图题、资产和必要子图结构关系，不沿“正文→图→其他正文→其他图”无限递归。扩展目标必须读取 App 已允许的原图或脱敏视图，不能因属于必需附件就绕过内容脱敏。

跨页图片必须能够带出；没有 REFERS_TO 时，仅“离图最近的一段文字”只能作为可选邻近上下文，不能冒充引用该图的正文。

同一图有多处引用时，关系存储保留全部出现。优先返回已有 CandidateTargetMatch 明确命中的段落，其后按显式关系出现顺序与稳定身份排序；没有相关性依据时不伪造相关分数、不新增模型重排。提供剩余获授权引用的游标/展开入口。一个段落多次引用同图可合并展示正文，但不能丢失出现位置；正文引用多张图则分别关联。

reverse_reference_count、分页和覆盖只统计可向当前用户披露的内容，不泄漏不可访问段落或其他 App 的存在。文档原有的引用字符串可展示，但不能因此披露被拒绝目标的身份、位置或预览。

预算不足时至少明确返回已确认且获授权的关联清单或其受控分页入口，以及关联覆盖状态；实际图片字节、反向正文和模型上下文受载荷预算限制。剩余项不得静默消失，也不能把未加载图片描述成已被模型阅读。

第 8.9 节中的“必须带出”不绕过权限、撤回、失败或资源上限。目标缺失、歧义或不可用时保留可披露的原文引用和原因类别，结果标记不完整；不临时找一张语义相似的图替代“图 1-1”。

返回结构示意如下，不是当前已发布 API：

~~~json
{
  "primary_hits": [
    {"evidence_key": "paragraph-p", "rank": 1, "group_key": "group-p"}
  ],
  "linked_evidence": [
    {
      "evidence_key": "figure-f",
      "kind": "FIGURE",
      "display_label": "图 1-1",
      "document_version_ref": "doc-version-x",
      "parse_run_ref": "parse-run-x",
      "preview_handle": "opaque-authorized-handle",
      "payload_materialized": false,
      "provided_to_answer_model": false
    },
    {"evidence_key": "caption-c", "kind": "CAPTION"}
  ],
  "groups": [
    {
      "group_key": "group-p",
      "anchor_key": "paragraph-p",
      "linked_keys": ["figure-f", "caption-c"],
      "relation_keys": ["ref-p-f", "caption-c-f"]
    }
  ],
  "association_coverage": {
    "manifest_status": "COMPLETE",
    "payload_status": "DEFERRED",
    "omitted": []
  }

~~~

实际合同还必须包含正文引用跨度、关系解析依据及各证据完整 locator。preview_handle 由 App 的受控内容接口解析，不能暴露存储 URI 或永久绕过撤回校验。

manifest_status 表示已确认且可披露的关联是否列全，payload_status 表示图片/正文载荷是否已加载；二者不能混淆。omitted/续取清单只包含可披露条目和原因，未授权目标不进入清单。provided_to_answer_model 仅由 Runtime 统一交付管线依据实际发出的图片载荷计算；App 检索响应不得自行置为 true。模型接收/理解与答案支持仍须分开。

### 8.10 端到端执行顺序与参数成熟度

~~~text
App 授权并固定检索快照
  -> 生成受约束查询计划
  -> 按任务并行词法/文本/跨模态/多向量/近重复召回
  -> 按精确对象去重、归并词法信号族，校验合法可读性
  -> RRF 融合（不调用独立重排模型）
  -> 读取必要关联清单，按问题覆盖和实际载荷预算选择证据组
  -> 加载必需的双向图文关联与有效载荷
  -> 预算内可选上下文及同 App 引用扩展
  -> 检查多输入/多证据覆盖，必要时在原范围有界补搜
  -> 按用户数量与排序组装主命中及关联组
  -> 复核权限与撤回，返回 EvidenceSet 和真实覆盖状态
  -> Runtime Document 经 AppContentPort 读取并验证载荷
  -> Runtime 统一 Composer 序列化、核对并实际交付上下文（需要生成回答时）
~~~

多路召回负责覆盖，RRF 负责排名融合，确定性选择负责问题覆盖与预算分配，关联与上下文负责完整性，原始证据和定位负责可验证性；这些职责不能用一个向量分数互相替代。算法核与 App 内容适配器不调用回答模型，最后一跳只由 Runtime 统一 Composer 管线负责，不能仅以 EvidenceSet 非空证明模型已收到证据。

算法框架采用词法+语义互补、加权 RRF、原生 late interaction/MaxSim 及确定性覆盖/预算选择，不包含独立模型重排。每路线候选数、RRF 常数和权重、检索模型、证据载荷预算、覆盖判定及补搜策略仍须受控实验确定。未验证的参数不写成“所有 App 最优”，没有跨 App 候选池或结果融合。

### 8.11 独立可选的 ripgrep 文本扫描组件

已决定将 ripgrep 作为默认关闭、按 App 显式启用的独立可选组件，设计见 [可选 ripgrep 文本扫描组件设计](optional-ripgrep-text-scan-design.md)。只复用组件代码，不建设跨 App 文件搜索服务。

- 提供 EXACT_RECALL（授权范围内精确补召回）和 WITHIN_CANDIDATES（候选内细查），不强制每次查询全量扫描。
- 通过 TextScanPort 注入，独立安装/移除；核心导入、部署和正常解析/召回不要求安装或探测 ripgrep。
- 只扫描 App 的已授权、满足发布门禁的文本投影，映射回标准证据；不直接扫原始二进制文件或任意目录。
- 与全文索引按词法信号族归并，避免重复加分；输出顺序不是相关性 Top-K，预算不足明确报告未穷尽。
- 未启用不构成退化；实际调用后不可用/失败须报告通道状态，但不阻断其他核心路线。
- 图文双向联动仍读取已解析的关系，不能用 grep 图号替代图片身份消歧和反向引用索引。

这是一项可选组件设计，不表示现已安装、接入或验证其质量提升。

### 8.12 防证据丢失、阶段诊断与交付合同

“已经召回”不等于“模型实际收到了证据”。以下规则同时约束算法输出、App 内容端口与 Runtime 交付管线，不以恢复旧版 fallback 或绕过权限实现兜底：

1. 各通道返回候选后，保留精确 EvidenceKey 与来源映射。去重必须记录归并到哪个对象，过滤必须记录阶段与原因；不得用列表下标、临时排名或 LLM 输出序号替代稳定身份。
2. 排名阶段的输入、输出身份集合应一致，每个身份恰出现一次。非法或丢失身份视为阶段错误，保留已验证的融合排名；只能在同一 scope/snapshot 内有界重试，不能悄悄返回空数组。通道/融合预算造成的截断单独记账，不冒充排名删除。
3. 权限、撤回、精确版本、损坏/不可读原文等可以硬过滤；不得为追求非空保留越权或不可验证载荷。对外仅披露允许的原因类别，内部诊断也受 App 权限与留存策略约束。
4. 如果仍存在授权、可读、可定位的候选，且剩余预算能容纳至少一个有效证据单元，不能因排序、键映射、组装或序列化异常静默交付零条。应保留已验证的可用结果并标记 PARTIAL；无法安全交付时返回明确失败阶段，不宣称没有数据。不得无关填充、超预算硬塞或绕过原文读取。
5. 没有候选、全部被合法过滤、无有效单元可装入预算、上下文交付失败分别报告。必要时提示扩大预算/缩小问题或受控续取；不能用“至少一条”保证替代合法性和证据质量。
6. 不使用未经校准的统一分数阈值、LLM 的 yes/no 判断或解析其输出失败来清空候选。高 RRF 名次不证明足以回答；即使交付了证据，回答层仍可说明问题覆盖不足，不能强迫生成结论。
7. 多路结果合并与必需附件读取均保留已有成功结果；某一通道/可选组件失败不能清空其他通道候选。必需视觉载荷不可用时如实报告能力/关联缺口，不以文本描述伪装已读图。

每次请求至少记录以下阶段的数量与身份流转，关联证据和主命中分开统计：

~~~text
各通道召回
  -> 合并/去重（重复对象映射、预算截断）
  -> 合法且可读候选（过滤/读取失败原因）
  -> RRF 融合（输入/输出身份核对）
  -> 覆盖与预算选中（未选原因、覆盖缺口）
  -> 组装（新增关联、载荷加载/延后/失败）
  -> Runtime 序列化（保留的身份、实际 token/图像/字节成本）
  -> 实际交给回答模型的请求（证据身份、文本/图像数量、发送状态）
~~~

关联扩展可能增加对象，所以不要求各阶段计数单调下降；必须能解释每一次新增、归并、过滤与延后。按请求关联策略版本、索引/授权快照、阶段耗时与预算，日志不默认记录原文、图片、用户敏感字段或凭据。

实际交付记录由构造/发送模型请求的 Runtime 统一 Composer 管线补齐，App 仅提供核权内容读取。文本证据被序列化为空、图片仅剩预览 URL、受控句柄未解析或模型不支持该输入，均不能计作有效载荷已交付。区分 PREPARED、SENT、FAILED 和网络状态不明的 UNKNOWN_DELIVERY；未调用回答模型的纯搜索为 NOT_APPLICABLE，不算失败。发送成功不证明模型理解了图像或证据支持了答案，不能把 App 内容读取成功当作模型发送成功。

检索质量、上下文交付可靠性、答案支持性分别评测。用户过去遇到的“有数据但最终零证据”只作为回归风险，不在没有当前运行 Trace 的情况下归因为某个模型或具体故障。

## 9. 同 App 文档引用算法

引用分两类：文内结构指向和跨文档原文引用。文内图号解析及双向带出分别遵循第 5.5、8.9 节，不能用跨文档标题相似匹配替代。模型推断 RELATED_TO、SUPPORTS、CONTRADICTS 不是默认必建索引，后续须证明对真实任务有增益。

解析器提取 ReferenceOccurrence；App 绑定的 ReferenceCatalog 只在本 App 授权目录内解析目标：

1. 优先精确 DOI、ISBN、文档号、稳定业务标识。
2. 使用标题、作者、年份、文件名等组合召回候选。
3. 校验版本、章节/图表锚点及引用上下文。
4. 不确定时保留 AMBIGUOUS、UNRESOLVED 或 EXTERNAL，不硬连到最相似文档。
5. 记录匹配算法、候选依据和源位置，允许 App 人工确认。

关系身份同时包含源文档版本/解析代次和目标文档版本/位置。目标入库、修改或撤回后，App 驱动待解析引用重试或标记失效，不悄悄把历史引用改到最新版。

文档引用字符串可以指向未入库的外部文献，但不会查询其他 App，也不生成 target_app 路由或从其他 App 取正文。查询不到的授权内目标和不可访问目标不能通过响应泄漏存在性。

同 App 支持反向引用查询。显式引用边、模型语义关系、答案支持边分别保存，禁止混为一种“可信关系”。

## 10. 快照、一致性与任务恢复

源文件版本、解析代次、投影代次、表示空间、索引代次分开管理。检索快照引用完整 IndexManifest，并声明当前可用通道。

App 持久任务状态建议覆盖：RECEIVED、PARSING、PARSED、PROJECTING、INDEXING、SEARCHABLE、FAILED、CANCELLED；审批/发布状态另属 App，SEARCHABLE 不自动等于可被最终用户检索。

- 数据库变更与可靠索引事件在同一 App UoW 提交；外部引擎更新不与数据库伪装成一个分布式事务。
- 外部索引按 generation 幂等写入；必需表示核验完成后，App 原子切换活动指针。
- 新代失败不替换上一成功且仍获授权的快照；禁止原地半覆盖已发布索引。
- 可选视觉增强建立新可用性快照；不得混用不同源版本或不匹配的模型空间。
- 查询固定本次快照，取证和返回前复核发布/撤回权限，失效时拒绝或有界重试。
- 撤回首先在权威 App 读取门禁阻断，随后异步删除索引；所有读取端口都必须执行门禁，不能只靠陈旧向量 payload。
- 历史回答引用的原始解析与图片按审计策略保留；删除与法务要求由 App 明确协调，不默认重解析后直接销毁全部旧证据。
- 垃圾回收仅处理已确认无引用且达到保留期的本 App 产物，绝不扫描或清理其他 App 目录。
- 无全局 exactly-once 承诺，通过至少一次交付、代次、摘要、租约栅栏和幂等写入恢复。

## 11. 定制化规则

允许三类 App 扩展：

| 扩展 | 输入/输出 | 禁止事项 |
|---|---|---|
| ParseProfile | 路由、语言、质量与预算 | 修改其他 App、任意插件代码执行 |
| DomainEnricher | 不可变解析数据 -> 带来源的领域增量 | 覆盖原文，生成虚假 bbox |
| RetrievalProfile/DomainRanker | 授权候选 -> 受限计划与确定性业务排名增量 | 删除候选、扩大授权、跨 App 读取、调用模型重排、把标签当证据 |

扩展是开发时登记的实现，不从请求加载脚本。DomainRanker 只是可选的确定性业务排序规则，不代表独立模型重排接口，也不允许借扩展绕行调用 LLM 做相关性裁决。扩展版本、输入指纹、失败和退化进入 Trace；结果身份核对遵循第 8.12 节。

App 只选择经验证的模型与参数组合，不需要各自复制 RRF、MaxSim、结构切分或证据组装。通用默认能力必须可直接使用，不能接入一个新 App 就要求重写所有算法。

## 12. 模型与索引实验矩阵

首轮比较候选，而不是把论文排名写成固定部署结论：

- 文本：Qwen3 Embedding 等文本专用编码模型，比较文搜文效果。
- 统一跨模态：Qwen3-VL-Embedding 等对齐编码模型，对照文搜图、图搜图和截图；不纳入同系列 Reranker。
- 多向量：原生 ColPali/ColQwen 路线、ColEmbed V2 等；先修正均值池化合同。
- 解析：当前 Docling、自适应 OCR，以及 MinerU/PaddleOCR 的困难页对照。
- 压缩：先保留高质量未压缩基线，再试 MRL、量化、token 聚类，分别测质量损失和成本。
- 图：先显式引用/结构关系，语义图仅在多跳任务消融实验通过后考虑。

模型选择要核对许可证、中文/业务覆盖、GPU 内存和 P95 延迟。自然照片、视觉文档分别评测，不能只依据一个截图检索榜单。

本轮不部署或评测专用 reranker/LLM rerank，不新增相应 Model Serving 类型或绑定。研究文献涉及重排不代表当前实现计划包含该能力。

Oracle/PostgreSQL 继续作为各自 App 事务真源。是否使用独立多向量引擎由能力与压测决定；不得未经验证声称现有数据库天然满足大规模多向量 ANN。任何独立引擎仍按 App 独立索引，都是可重建投影。

## 13. 评测与验收

### 13.1 数据集

首批建议 200–500 条人工审核真实查询，包含中英文、数字 PDF、扫描、Office、图表、自然照片、近重复、版本冲突与同 App 跨文档问题。另建权限和故障集，不让它们被平均质量分掩盖。

评测允许一个问题有多组等价证据；标注文档、页面、具体图片/区域和完整证据集，不能只认一个黄金 chunk。训练、调参和验收数据按文档/近重复来源隔离，防止泄漏。

每个 App 的质量评测只使用其自己的数据。隔离测试可以在不同 App 放入相同或更相关的诱饵文档，但目标检索响应不得返回、访问、引用或缓存其他 App 的候选。

### 13.2 指标

- 解析：结构、阅读顺序、表格结构、公式、图片对应、locator 准确性及局部失败率。
- 检索：按任务统计 Recall@K、nDCG、MRR，单独报告精确术语与语义任务。
- 视觉：独立图片命中、区域定位、原图/近重复与语义相似分别统计。
- 多证据：证据集合覆盖、输入约束覆盖、同 App 引用扩展收益。
- 引用：目标解析 P/R、错链、歧义处理、版本锚定及反向关系一致性。
- 图文联动：正文到图片/图片到引用正文的双向覆盖、图题绑定准确率、子图定位及反向正文分页完整性。
- 关联交付：关联清单完整率、载荷实际加载覆盖、预算省略披露、提供给回答模型的图像证据覆盖分别统计，不能以一个预览链接计作模型已读图。
- 交付可靠性：各阶段候选/证据计数、非空有效候选到实际零载荷的异常率、身份丢失/错配率、序列化失败率及原因可解释率；统计全部请求，不能只报告成功子集。
- 上层答案：claim 支持率、引用完整性；不能用召回分数替代。
- 工程：P50/P95、峰值内存、索引大小、模型成本、重试恢复、删除/撤回一致性。
- 安全：跨 App 访问与泄露为零，Tenant/Domain 越权为零，缓存/融合/选择/组装/预览同样覆盖。

### 13.3 消融顺序

A 当前实现；B 新结构单元与词法/文本 dense + RRF；C 加跨模态 dense；D 加独立多向量召回；E 比较融合顺序直接装入与确定性问题覆盖/上下文预算选择；F 测同 App 显式引用与双向图文关联的收益。可选 ripgrep 在固定核心配置上另作单独实验，不将其和多项策略同时改变。

涉及图文关系的消融用于测量收益，不代表最终可省略第 8.9 节的必需合同；所有配置都必须遵守权限、防证据丢失及真实能力提示。

使用相同语料、查询、授权范围、生成器和受控候选/上下文载荷预算，另报告各配置实际算力预算。先跑检索指标，再评估固定回答器，不能靠更换生成模型或扩大模型上下文掩盖召回/选择问题。

验收阈值和各任务权重必须在看验收结果前冻结。质量优先也需要给定资源上限；本设计不宣称任何新模型已经取得本地提升，不以 LLM 自评单一分数作为验收。

### 13.4 图文联动专项验收

| 用例 | 必须观察到的行为 |
|---|---|
| 命中“系统结构如图 1-1 所示” | 返回对应真实图片、图题、关系及双方定位，不要求图片独立语义命中 |
| 图搜图命中图 1-1 | 返回显式引用它的正文，不只返回图题或图片邻段 |
| 图在下一页/远处章节 | 精确引用仍可解析，不能被相邻切片窗口限制 |
| 不同文档或编号作用域都有图 1-1 | 不串图，目标身份限定原文版本/解析代次与作用域 |
| 同图多处引用、一段引用多图 | 全部关系保留，展示去重不丢出现；分页完整且不挤占主命中数量 |
| 图 1-1(a)/(b)、复合矢量图 | 子图/父图及实际区域正确，无法分离时明确局限 |
| OCR 错号、原生锚点冲突、图缺失 | 显式歧义/缺失，不强连最近或语义相似图片 |
| 同页多图及 PAGE/FIGURE 同时命中 | 各对象身份保留，图题不绑定到错误图片 |
| 必需关联的向量分数很低或不存在 | 仍按确认关系附带，不伪造相关分数或直接升级为答案支持 |
| 关联超出图片/token/正文预算 | 标记 PARTIAL/DEFERRED 并提供受控续取；不能宣称全量读图 |
| 只有预览句柄、尚未送图给模型 | provided_to_answer_model 为 false，回答不得声称已读取图像证据 |
| 权限变化、撤回、同号新版图片 | 两端复核并拒绝错误目标，不泄漏受限计数，也不自动替换历史图片 |
| 其他 App 有相同图号或更相似图片 | 零读取、零关联、零结果、零缓存复用 |

在可控小型 fixture 中，已人工标注、已解析、获授权且可用的直接图文关系必须全部按合同交付；在真实语料上另外衡量解析漏链、错链及载荷预算造成的缺口。不能只用召回 nDCG 代替该专项验收。

### 13.5 无模型重排与防丢失专项验收

| 用例 | 必须观察到的行为 |
|---|---|
| 未配置 reranker、Model Serving 不支持该类型 | 核心检索可完成，不探测或调用该能力，不因其缺席标记退化 |
| BM25、cosine、MaxSim 分数尺度不同且绝对值低 | 按通道排名融合，不因统一阈值清空；分数不作为答案支持证明 |
| 各路命中重复、全文与可选 rg 同时命中 | 按对象归并并保留来源，词法族不重复投票 |
| 自定义排序规则返回丢失、重复或未知身份 | 检出阶段错误，保留已验证融合顺序；不错误映射或返回伪空结果 |
| 部分候选撤回/无权限/原文损坏 | 只过滤不合法项并记录原因，保留其余可交付项；无权项不泄露 |
| 所有候选均不可读或已无权 | 返回真实原因，不强塞一条或伪装成相关性不足 |
| 首条超大、后续有可装入的有效单元 | 不因首条超预算交付零条；对延后项、预算与覆盖缺口明确记账 |
| 比较、多条件、多文档问题，同文档有大量重复窗口 | 覆盖目标参与选择；重复不挤占所有上下文，同文档不同必要证据不被强删 |
| 身份映射/载荷组装/序列化失败 | 各阶段可定位；有安全可交付项时保留并标记部分结果，否则明确失败，不报“没有数据” |
| 模型请求文本为空、仅有图片句柄或图片未解析 | 不能把 EvidenceSet 非空计作已交付；给出实际载荷与发送状态 |
| 用户指定数量/日期排序、附件多于主命中 | 展示数量与顺序保持，模型上下文子集和附件预算分别披露 |
| 有效候选实际送达，但不足以回答 | 如实说明覆盖不足，不因非空保证强迫生成结论 |

受控 fixture 中，在合法、可读且预算能容纳有效单元的前提下，静默零交付与身份丢失必须为零；故障注入结果须覆盖全量请求，不能以成功请求的平均排名掩盖失败。

## 14. 必须覆盖的自动化测试

1. 算法包无 ORM、App、服务 API、数据库和平台 IAM 导入；依赖方向可做 AST 守卫。
2. 解析不获取业务 UoW；同输入/配置的规则部分输出稳定，模型实际输出按摘要记录而非假定确定性。
3. 坐标旋转/裁剪往返、Office 逻辑定位、跨页表格和图题关系正确。
4. ParseEvent 乱序、重复、同键异内容、取消后迟到、进程崩溃、临时制品过期。
5. 流式大文档峰值内存和背压；使用合成负载，不通过固定 sleep 掩盖问题。
6. space_id 不匹配、图片方向不支持、mask/NaN、MaxSim 与参考实现一致。
7. 同页多图、PAGE/FIGURE 并存，不能被页或 Bundle 去重吞掉。
8. 混合查询 ANY/ALL/COMPOSED、用户数量/排序、候选预算截断和部分通道失败。
9. App 绑定固定，恶意 App 参数、跨 App 引用、其他 App 缓存和临时制品不可访问。
10. Domain/Agent 授权改变、撤回、发布变更发生于召回/融合/选择/组装/预览及实际模型发送前。
11. 索引新代失败、重放、原子切换及历史引用可读；无双写兼容依赖。
12. 前端/回答适配器保留图片原图、排名、证据身份和真实能力警告。
13. 第 13.4 节全部图文联动用例；正反向关系查询、主命中/附件数量、关联清单与载荷状态独立校验。
14. 第 13.5 节全部防丢失用例；阶段身份核对、预算不足/合法空结果/交付失败区分，且无 reranker 类别、绑定或调用依赖。
15. 原生通道分片数/边界/返回顺序变化不改变精确基线融合；FILTERED_ORDER 不漏掉相关性 Top-K 之外的最新合资格项；EXHAUSTIVE 不伪装语义全集。
16. CoverageTarget/匹配依据/UNKNOWN、有界预算重选；rg 独有命中可复现进入词法族，不使用遍历顺序投票。

测试放 tests/unit、tests/contract、tests/integration、tests/evaluation；环境验收放 tests/acceptance，不放部署 scripts。

| entities/repositories/persistence | 解析/证据等业务数据迁入明确的 App 归属，不能继续使用公共正文表 |

## 17. 研究依据与采用边界

截至 2026-11-05 已查阅的主要公开依据：

- [Qwen3-VL-Embedding/Reranker](https://arxiv.org/abs/2601.04720)：仅采纳 embedding 部分作为跨模态检索候选，不纳入独立 Reranker；不承诺对所有文本任务最优。
- [ColPali](https://arxiv.org/abs/2407.01449)、[ColEmbed V2](https://arxiv.org/abs/2602.03992)：保留多向量与 late interaction 的依据。
- [MinerU2.5-Pro](https://arxiv.org/abs/2604.04771)、[PaddleOCR-VL-1.6](https://arxiv.org/abs/2606.03264)、[Docling](https://github.com/docling-project/docling)：可替换解析与困难区域优化候选。
- [ViDoRe V3](https://arxiv.org/abs/2601.08620)：真实文档、多粒度证据及定位评测参考。
- [EVIE](https://arxiv.org/abs/2610.11553)：证据感知多向量与压缩研究，近期预印本，不能当作本地成本承诺。
- [GraphRAGProv](https://arxiv.org/abs/2610.37237)：来源约束与关系可追溯，借鉴原则，不默认引入 RDF/SPARQL 全栈。
- [Pix2Evidence](https://arxiv.org/abs/2610.41335)（2026-10-30）：图像/文字证据融合研究。无 rerank 版本已有较强结果；增加 rerank 对 NQ、NQ-Tables、SimpleQA 有收益，但无 rerank 在 MMSearch、EVQA 上仍表现更好，说明收益依任务而定。近期预印本，代码与部署成熟度需另行核验。
- [Can System-1-Style Decision Models Replace Dedicated Rerankers in RAG? A Systems Evaluation](https://arxiv.org/abs/2610.34816)（2026-10-26）：长候选集可能导致失败，截断能改善稳定性；启发是在固定候选集下联合评估可靠性、质量、延迟/显存，不能只看成功请求排名。不是所有 reranker 无效的证明，也不是用户历史故障的已确诊根因。
- [Anthropic Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)（2024，较早工程实践，非最新论文）：上下文 embedding 与 contextual BM25 在不增加 rerank 时已可改善检索；rerank 是额外增强。借鉴改善检索输入与词法/向量互补的方向，不把其效果直接外推到本 App。

这些资料不支持“重排普遍必须”，也不支持“重排一律无用”。本版依据现有能力边界、历史可靠性风险及可验证基线，选择不实现独立模型重排，先改善解析质量、表示、召回覆盖、融合及上下文交付；是否值得另立重排方案必须由未来独立实验决定。

论文与开源实现提供候选算法和评测启发；真正上线的模型、索引和参数以本 App 实测、许可证与资源约束为准。本文没有新增跨 App 检索，也没有承诺未经验证的召回提升。
