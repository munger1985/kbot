# 业务系统删除与资源退役

## 用户操作

业务系统目录的“更多”菜单提供删除入口。已上线系统只有下线入口，必须先下线，才能删除。删除使用统一危险操作确认框和 If-Match 行版本校验；取消确认不会发送删除请求。

| 对象 | 处理方式 |
| --- | --- |
| 曾发布的已下线系统 | 设置 DELETED，保留系统身份、拓扑、冻结授权及诊断、巡检、审批等历史，不提供重新上线 |
| 从未发布的已登记 DRAFT 系统 | 物理删除系统、本系统关系参与者、关系和资源关联；全局资源不物理删除 |
| 未发布 CREATE 草稿 | 物理删除草稿、草稿变更和已结束的发现任务，不影响正式系统或已有资源 |
| EDIT 草稿 | 仅删除未发布修改，不删除原系统或退役原系统资源 |
| 无其他系统引用的资源 | 设置 RETIRED，停用资源监控绑定；独占 Target 停用只读、变更和周期采集 |
| 共享资源 | 保留资源、监控绑定及其他系统关联，不撤销其他系统的访问能力 |

## 发布身份与历史边界

系统发布直接进入 ENABLED，上下线只允许 ENABLED 与 DISABLED 之间迁移，DRAFT 只能首次上线，禁止任何接口把已发布系统回退成 DRAFT。因此不新增冗余的发布状态列，也不需要 Schema 升级。

删除还会核对发布事件、Agent 冻结版本和巡检计划引用。即使异常数据的当前状态为 DRAFT，只要已有这些历史，也不能走物理删除。旧系统逻辑删除后，使用新 ID 创建的同名系统不继承旧授权。

逻辑删除保留原拓扑，但将本系统资源关联置为 INACTIVE。冻结版本和资源动作策略不改写；运行时授权必须同时核验系统仍为 ENABLED、关联 ACTIVE、资源 ACTIVE。共享 Target 仍在线不意味着已删除系统的旧 Agent 可以访问。

重新编辑 Agent 时，会提示并从编辑草稿移除目录中已删除或不可用的系统，防止不可见 ID 被再次提交。只有用户重新确认并保存时才创建新版本；打开编辑页面不修改冻结授权，也不自动转授给新资源。

## 资源引用与凭据

资源是否共享按同一租户／Domain 内其他未删除系统的 ACTIVE 关联判断，包含 ENABLED、DISABLED 和已登记 DRAFT，不能只统计上线系统。已删除系统的关联不再保留资源使用权。

先按资源 ID、Target ID 的稳定顺序锁定并刷新记录，再重新判断引用。最后一个系统引用删除后，资源逻辑退役；仍有未退役资源使用同一 Target 时，不停用共享 Target。

只撤销独占 Target 的专属受管凭据。凭据若被其他 Target、监控源或发现任务引用则保留。监控源、共享 Agent 和真实 Oracle／MySQL／PostgreSQL、主机、容器均不删除。

Target 的单独物理删除入口也拒绝删除任何仍有受管资源配置（包括 RETIRED）的端点，避免绕过历史保留规则。

## 调度、草稿与事务

- 仍有未结束运行、巡检批次或有效调度租约时拒绝删除，不强制终止任务。
- 删除正式系统时停用所属巡检计划（DISABLED），清除下一次调度与租约，但保留计划及执行历史。
- 删除正式系统时清理其未提交编辑草稿，已提交草稿不作为当前配置重新发布。
- 草稿仍有 PENDING／RUNNING 发现任务时拒绝删除；任务结束后才可物理清理。
- 草稿发布与 COMMITTED 标记在同一事务中完成，锁内再次核验草稿状态、版本和有效期，防止删除与发布竞态留下孤儿系统。
- 配置事件仅记录系统身份、删除模式、退役／保留资源 ID、停用 Target、停用计划及清理草稿 ID，不记录密码或草稿连接载荷。

所有修改由应用用例控制同一 Unit of Work 事务，仓储不提交事务。异常时回滚本次全部退役、绑定停用与配置清理；不复用会删除运行历史的 Target 全量删除方法。

## 验证边界

事务与授权回归使用本地 SQLite 和真实应用／仓储方法；它们不替代 Oracle、PostgreSQL 的真实驱动、外键与并发验收。浏览器回归覆盖两端生产目录、共享卡片菜单、确认／取消、DELETE 路由和 If-Match。此变更不自动升级远程数据库或重启服务。
