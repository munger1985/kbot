# AIOps 数据保护实施计划

状态：两仓已接入 RMAN、pgBackRest、XtraBackup 的定时备份及独立演练主机上的原生空库恢复，默认不启用。配置、调度、恢复门禁与报告链路已做离线验证；三库整库定时备份和端到端演练尚未实测。本计划取代旧 D0/D1，以[新版设计](../proposals/aiops-data-protection-design.md)为范围基线。真实验收和 Debug 由用户统一组织。最新执行位置与验收清单见第 5 节。

## 2. 实施顺序

### 0. 收口现场假设（只做确认，不接环境）

按库列一行：数据库及工具版本、执行位置/可用通道、存储与日志来源、演练环境形态、获准恢复模板和支持的恢复场景。备份脚本模板由程序编写和维护，不向用户索要备份脚本。Oracle 定向 RMAN；PostgreSQL/MySQL 首选现场已有工具，pgBackRest/XtraBackup 是候选，不自动引入依赖或承诺所有版本。参数校验、备份模板生成、Job 触发及结果处理可用假执行器做离线开发；未确认的现场能力不启用，不自行切换到逻辑导入或升级只读诊断通道。

### 1. 独立数据保护入口、配置与预检

1. 以现有数据库资源 ID 为关联，定义最小配置与记录：保护目标、身份和存储引用、备份/演练计划、运行记录及报告引用。默认未纳入；同一资源被多个业务系统使用也不重复保护。源、目标、脚本、存储或凭据等关键配置变更后，受影响计划须重新检查和确认再继续。
2. 独立页面编辑配置。备份计划填写保存目录/仓库、并行度、周期/时区、超时等受支持参数，不要求填写备份脚本名或路径。业务系统只显示摘要并跳转：单库直达，多库按系统筛选。期望 RTO/RPO 只在数据保护填写；可引用重要程度、主备关系、同步方式给出经验建议，用户确认后才保存，不把推荐当 SLA 或实测。2026-11-19 用户反馈：独立入口参照监控页，先展开业务系统，再搜索并选择其下数据库；沿用已有系统目录、资源详情和数据保护接口，不改权限、调度或存储。
3. 接好托管凭据与权限帮助。按库种/工具/备份或恢复操作分别列出数据库、主机、存储、网络工具和验证权限；预检返回通过、缺失或未验证，不能用连通成功代替权限证明。不代建账号、不提权。预检实现和测试用模拟环境；开发时不连接任何真实目标。
   - 2026-11-19 用户确认：权限说明从「保护配置」的 `?` 图标打开只读抽屉；重要程度自动带入当前业务系统的值，只读展示，无须选择或点击引用。只调整页面交互，沿用现有接口。
4. **离线完成证据**：两入口同权限；未纳入不阻塞业务；同资源不重复；跨资源不可访问、接口不回传秘密、缺权提示有据；原人工恢复/工作项流程不变。

### 2. 公共执行路径与 Oracle 首个离线闭环

1. 在现有 Worker 中接入两类持久化计划：周期备份、一次性/周期演练。同一计划时点只产生一条运行；演练同一目的地互斥，错过窗口记跳过，不积压补跑。按现有 UoW 事务完成认领并记录快照，执行外部工具时不持有数据库长事务。超时或重启后不确定外部进程状态，保留现场并阻止再次写入，不按失败自动重跑。
2. 先实现内置 RMAN 备份模板：用受校验的目录、并行度等参数生成命令文件。确认后保存模板版本和参数，使用既有调度及 Worker 生成和认领备份 Job，不建系统 Cron。以假执行器验证参数生成、定时触发、路径和并行度异常拒绝、源端只走备份入口；记录退出信息、脱敏日志、备份产物引用、可读性及归档覆盖。退出成功但缺产物不是成功；日志断链不标为可按任意时间点恢复。
3. 接入独立的辅助实例登记与恢复门禁。保存时检查，实际调用前再次核验用途、实例身份、解析后的目录、空状态、隔离、当前权限和产物可用性；目标不是独立隔离空环境、是生产主库/备库、证据不足或配置发生变化即拒绝，无强制继续。仅用已存在的备份及归档，验证实际恢复坐标和关键对象。生产恢复不提供 Agent 执行入口，仍由 DBA 根据现有文档流程操作。
4. 让一次模拟演练走到正式报告输入：冻结 T0、计划及目标版本、来源和产物；收集阶段时间、恢复坐标、验证与拒绝原因。
5. **离线完成证据**：用模拟脚本/返回值跑通从计划到验证结果；对生产主/备、非空、未知、路径或身份不符、凭据撤销、任务冲突、缺产物逐项断言恢复写入口从未调用。用并发与重启模拟验证防重复、占用及超时结果。此时只能称 Oracle 代码链路已验证，不称 RMAN 实库验收通过。

### 3. 按同一合同补齐 PostgreSQL 和 MySQL

- **PostgreSQL**：以同一 Job 合同实现所选工具的内置备份模板；演练走批准的独立恢复入口，核对 PGDATA、表空间、基础备份、WAL 和时间线范围；按证据记录实际 Timeline/LSN。测试缺段、位置不符、目标非空以及恢复验证失败。
- **MySQL**：以同一 Job 合同实现所选工具的内置备份模板；演练走批准的独立恢复入口，核对工具版本及独立实例和数据目录；按工具准备产物，并在支持场景用已归档 Binlog 按完整事务边界回放。记录实际 GTID 或 Binlog 边界，测试不兼容、缺段和副本隔离。
- **离线完成证据**：每库都通过备份记录、隔离空环境、模拟恢复、验证证据的同一套合同测试。首批场景是恢复到 T0 时已可证明的最近恢复点；指定时间点仅在已确认工具及日志链支持时启用，不单独扩展工具体系。Oracle 的完成不抵消另两库的缺项。

### 4. 固化指标、正式报告和两仓回归

1. 按 T0 到验证完成生成演练 RTO，单列排队、取回、恢复/回放和验证；报告耗时不计。按 T0 与可信恢复点计算 RPO；证据不足显示区间或未测得，不用备份完成时间冒充数据恢复时间。把期望、估算、实测、实测减期望分开；指定点主动回退不当作日常 RPO。
2. 所有已受理演练（含失败、拒绝和证据不足）关联报告。结构化保存验证等级、证据及时间线，由 Agent 基于事实撰写带责任方、验证方法和复演口径的整改建议。报告生成失败可独立补生成，不再执行恢复或改变实测事实。确认报告中心、PDF 与原始证据下载授权。
3. **离线完成证据**：验证指标临界值、缺测、区间、恢复成功但指标超标、报告重试及脱敏；回归备份检查、人工证据和 DBA 文档；两仓分别做定向单元/合同测试、架构边界检查，以及不连接真实数据库的 Schema 工件和合同校验。进度列出实际通过、失败与未执行项，既有无关差异不借机整改。

### 5. 最后统一进行用户实测和 Debug

前四个编码步骤完成之后，由用户提供三库及隔离目标环境并统一组织：每库至少验证一次备份、定时空库演练、数据校验、指标及报告；用安全的非生产测试端点或预检验证拒绝路径，不对生产目标尝试任何恢复写入。逐库记录工具和版本、可验证场景、实际时间与恢复点、限制及待修项。未实测的组合不标记为已验证。

[本地 Schema 历史记录](local-schema-alignment-20261117.md)显示，之前试行的表及旧配置缺列不随源码回退。现场测试如果使用该环境，由用户另行确认处理方式；本计划不授权自动迁改、回填、清空或初始化任何真实库。

## 3. 推进与变更纪律

每步只记录四项：交付结果、已跑的验证及结果、当前待确认项、下一步。项目只有这条主线：独立配置 → 原生工具备份 → 隔离空库演练 → 指标、报告和整改。未经确认不新增守护进程、C helper、Linux 命名空间、pidfd/seccomp/cgroup/密封 FD、传输/凭据协议、交付门槛或无关重构。现有能力不满足时，先列出证据、最小选项、替代方案和工期影响；仅停下依赖它的事项，其它已批准工作继续。不能简化或绕过生产恢复禁令。

全程在开发工作分支。未经用户明确指令，不编译、构建、部署、发布或重启。真实验收与 Debug 统一后置，不能成为前面各编码阶段的隐含前置条件。后续仅 Ammolite 可按用户明确指令编译/发布，且仅针对已推送到 `main` 的受版本管理代码；KBot4 不编译。

### 本机 Oracle RMAN 适配代码与验证（2026-11-18）

- **交付结果**：复用既有 API 和 Worker。只在部署明确登记的执行位置调用本机 SQL*Plus 和 RMAN；页面在数据保护中登记已有的 OS 备份用户名，不建号、不提权、不要求用户上传脚本。Worker 只认领已登记资源的备份，不认领演练。预检核验数据库资源、Target、DBID、DB_UNIQUE_NAME、Oracle 19c 单实例主库身份、ARCHIVELOG、SPFILE 和独立备份路径。固定模板输出到每次运行的独立目录；按控制文件中的备份记录检查数据文件覆盖及归档、控制文件、SPFILE，再用 RMAN 读回校验。归档件存在不等于连续归档已证明。
- **实际验证**：Ammolite 266 项代码/配置回归通过（另 13 个子测试）；KBot4 261 项通过（另 18 个子测试），另 1 项为原有 Knowledge Core 配置测试仍引用已移除的 `storage` 属性，不在本功能内修改。两仓各 3 项定向前端合同、各自 OpenAPI 和架构边界检查通过，KBot4 页面脚本语法检查通过。本机 Oracle 容器中验证了适配使用的只读实例和备份清单查询，以及 RMAN 对既有两份元数据备份的读回；元数据备份没有覆盖数据文件，实例仍为 `NOARCHIVELOG`。未启动产品定时 Job。
