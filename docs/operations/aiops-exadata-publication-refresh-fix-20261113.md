# Exadata 硬件提交前候选刷新修复（2026-11-13）

## 取证结论

用户提供的 `KBot_4.1.1_提交失败取证_2026-11-13.tar.gz` 指向一套独立 Docker 现场。现场基线是 KBot `53073cdd`；包中部署 JS 的 SHA-256 与该提交的两份前端源码一致：

- `aiops-hardware-resources.js`：`033169f02c9413eb88e2a6740a243f26007957648fda589103eb2607b3c7dc2c`。
- `aiops-business-system-workspace.js`：`79b03bf8863b688f88c575eb7802ed8a2d6dd88973063b510a26519917308fc1`。

包内访问日志可见 Exadata 发现 HTTP 200；相关时间窗没有草稿 POST/PUT 或正式提交请求。根因是 Exadata 发现成功后无条件清空所选 `candidate_ref`，而工作区提交前先刷新发现、随后检查该字段，导致在浏览器内拒绝提交。不能用反复重新发现绕过；也不是该次提交触发数据库写入失败。

Ammolite 的 `hardwareResources.ts` 与 Vue 工作区具有同样逻辑，存在同源缺陷，已同步修复。包内其他数据库连接测试错误是独立问题，不在此修复中猜测或修改连接参数。

## 修复语义

1. 手动发现仍只展示候选，必须由用户明确选择整机；不自动选择第一项。
2. 发布前为 Exadata 启用严格刷新，冻结原选定整机 GUID、已展示成员与显式导入清单；请求带 `root_id`，不按名称匹配或切换整机。
3. 只有同一 GUID 唯一返回、成员身份及归属证据均未变化时，才将新的短期引用用于草稿和发布。成员比较覆盖 GUID、类型、名称、父节点、归属来源和证据引用；成员顺序及对象字段顺序不影响结果。
4. 整机消失/歧义、成员变化、导入清单编辑、缺失旧成员证据或 OEM 请求失败时不继续发布；清除无效旧引用，保留输入供用户重新发现、复核并选择。
5. 请求期间监控源、整机、导入清单、选择或发现代次变化时，旧响应不能使提交继续。
6. 现有普通主机发现、数据库发现、来源合同、后端候选签名及保存时成员摘要复核保持不变。没有改库、扩容、清理数据、修改 OEM 或重启后端。
7. KBot 工作区两份 JS 的缓存版本同步更新为 `20261113_exadata_refresh`。
