# 空间趋势任务边界与实施文档修复（2026-11-09）

## 线上事实

本次原始三轮会话均在 Ammolite，依次为 ERP/Oracle、MES/PostgreSQL、WMS/MySQL：

- Oracle：`01a1bf0c-11b4-7dfe-adf7-5d44dd5bc386`
- PostgreSQL：`01a1bf0e-b991-7dcb-8ef4-c2b58138180f`
- MySQL：`01a1bf11-58a4-75d0-afc3-d3ec1e860241`

用户请求的是最近 7 天空间变化趋势，没有请求归档、分区或监控配置实施。
MySQL 数据库用量时序有 120 点、覆盖率为 1；空间使用率两次查询均无样本。
实例身份、当前容量及表统计工具均成功。不能把辅助使用率缺失等同于趋势证据缺失。

实施文档原先由非空 recommendations 自动触发，与数据库类型无关。
这次 Oracle 和 PostgreSQL 的 recommendations 为空，所以没有附加文档；
更早 Oracle 会话也曾因包含建议而生成文档。

另发现原 MySQL 正文用约 82 MiB data_free 和日增长率推算约 6 天余量，
该口径不成立：内部可复用空间并非文件系统可用空间。

## 修改

1. 仅冻结任务有 ADVISORY/EXECUTE 动作意图或 PLAN 目标时，才把建议编译为实施文档。
   普通观察、诊断及预测保留建议，不自动升级为需要用户填参数的实施任务。
2. 按冻结标准指标目录的语义角色与资源范围区分数据库主用量和辅助容量指标。
   有效主用量时序满足请求窗口时，辅助指标无样本等有限缺口不再阻断已完成的趋势；
   原始缺口仍在证据中保留，不改写为正常，不再追加补证卡。
3. 继续保留主用量缺失、覆盖不足、时间窗口不足、源故障、认证失败及显式完成义务。
   明确要求未来预测时，历史不足和低置信度判断仍然生效。
4. 生成前加入空间分析口径与任务边界，定向同步重规划、充分性评估和诊断回答 Prompt。
   MySQL data_free/free_mb、对象分配量以及 InnoDB FILE_SIZE/ALLOCATED_SIZE
   均不能替代磁盘总容量或余量。耗尽时间仅使用服务端同源同对象计算字段，
   不将数据库逻辑增长与未经核验归属的主机挂载点拼接。
5. 本次没有添加跨资源主机查询、扩大授权、改变 Schema 或事后替换模型正文。
   缺少必要容量证据时仍须先尝试当前已授权的只读路径，不能猜参数。
