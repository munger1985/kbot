# 统一资源监控绑定与硬件接入

日期：2026-11-05。KBot4 与 Ammolite 使用相同产品语义。

## 模型与边界

业务系统关联资源，资源关联监控源；数据库 Target 不再承担主机身份或主机监控绑定。
绑定统一存储在 KBot 的 `KBOT_OPS_RESOURCE_SOURCE_BINDING` /
Ammolite 的 `aiops_resource_source_binding` 中，不为每种资源创建一张绑定表。

| 对象 | 负责内容 |
| --- | --- |
| ManagedResource | 资源 ID、类型、名称、责任组、资产属性及生命周期 |
| BusinessSystemResource | 资源属于哪个业务系统、展示层和排序 |
| DatabaseResource / Target | 数据库连接、凭据、引擎版本及诊断和执行能力 |
| ResourceSourceBinding | resource_id、监控源、定位键及定位 JSON、状态、版本、优先级和查询预算 |
| ResourceRelation | 数据库运行于主机、使用存储、依赖网络设备等显式关系 |

统一绑定的物理外键只有资源和监控源，不再保存 target_id。数据库接口所需的
target_id 由 DatabaseResource 关系只读投影获得，不存在旧绑定表兼容或双写。

权限继续跟业务系统：有系统访问权限即可访问其关联的活跃资源，不增设数据库、主机、
网络设备的资源类型 ACL。Agent 仍必须受已授权系统、能力、执行策略及审批边界约束。
看到某个监控源中的候选，不代表它已加入业务系统或已获授权。
本轮支持硬件配置与实时监控，不新增硬件 SQL 诊断或受控执行工具。

## 配置流程

1. 在业务系统的“系统构成”中添加数据库、物理服务器、虚拟机、容器、存储或网络设备。
2. 数据库只选数据库候选；物理服务器和虚拟机独立选择 Prometheus 或 OEM，再发现、选择主机候选。容器可独立绑定 OEM 的容器内 `host`，不允许借用 Node Exporter 的宿主机身份。
3. 在硬件抽屉勾选其关联数据库，分别建立 RUNS_ON、USES_STORAGE 或 DEPENDS_ON。
4. 在拓扑确认中查看硬件节点及连线，再发布。修改配置沿用系统先下线的规则。

硬件新增、回显和修改共用同一字段模型。候选引用由服务端签发，限定 Domain/Tenant、
操作人、监控源及有效期；发布前刷新引用，服务端保存前再次从 Provider 验证。
变更已有绑定需提交绑定 ID 和版本。拒绝把同一个主机定位重复创建为两个资源。
本阶段界面不提供跨系统复用已有硬件资源，也不提供删除已有主机绑定的操作。

存储和网络设备目前支持资产及拓扑，不提供专用采集或虚假的健康状态。
不能把监控源连接成功、资源配置完成、系统上线解释为真实资源健康。

OEM 主机候选只接收真实 `host` 类型，按 GUID 保存及再次核验；数据库 GUID 不能绑定为主机。
候选展示主机名称，不把长 GUID 作为主要显示信息。OEM 数据库的 `hostName` 仅是属性，
不会自动把 OEM 可见的主机或其他系统资源纳入当前业务系统；承载关系需明确关联。
容器内主机名不等同宿主机身份。已有系统补配置时必须核实实际资源类型和承载层级。

硬件、资源目录及只读资源抽屉统一使用 `admin-drawer-body` 滚动正文；
标题和操作区保留在视口内，不依赖整个页面滚动访问下半部分。
数据库架构判断忽略 `RUNS_ON / USES_STORAGE / DEPENDS_ON / LOAD_BALANCES` 等基础设施关系；
单实例数据库挂接主机后仍显示“单实例”，不因承载关系回退为“待推导”。

## 指标拆分与实时监控

数据库总览只包含 DATABASE 指标，不再复制 host 或基于主机推算的 runtime 指标。
主机资源使用独立 host-overview：CPU、内存、文件系统、磁盘 IO、网络吞吐。
Prometheus 主机查询只使用主机自身绑定的定位键，不读取数据库 locator 中的 host_target_key。
同一主机承载多个数据库只保留一份主机身份，通过多个运行于关系表达。

实时监控按资源类型加载相应 Profile，不为硬件伪造数据库引擎或 Target。
主机当前不显示数据库专用诊断入口及未实现的历史均值基线。
无采样明确展示缺口，不按零或健康处理。每次查询核对已上线系统内活跃资源归属，
查询返回前复核源配置、绑定版本及归属；已撤销的资源不能返回采集中结果。
主机视图遵守实例数、Series、面板和响应字节预算，不复用旧授权状态的缓存。
Agent 配置摘要统计全部资源的监控，只统计数据库的只读及变更能力。

## Schema 与交付范围

Oracle 规范 DDL、ORM、Manifest、重建与验证 SQL 已同步为资源绑定模型；
PostgreSQL 规范由当前 ORM 和初始化实体注册生成。公共合同与 OpenAPI 同步更新。
初次代码交付阶段只改代码及规范工件，未执行数据库变更或部署；后续获批的定向升级见下文。
旧库不能直接运行新代码，部署时必须协调 Schema 与应用版本切换。
历史升级文件不作为本轮迁移入口，生成的重建 SQL 也没有执行。

OEM 指标扩展、ODA/Exadata 专用采集及硬件诊断编排留到下一阶段。
本次 OEM 主机发现与资产绑定不代表 OEM 实时主机指标或 Node Exporter 指标映射已实现。

## 已有环境的定向升级

已有部署使用 `scripts/deployment/upgrade_aiops_resource_bindings.py`，不执行全库初始化或重建。
该脚本是部署工具，不接入启动、readiness 或业务请求。

1. 核验实际仓库、服务进程、旧绑定与数据库资源的唯一关联及系统归属；备份部署版本。
2. 准备受保护的主机类型 JSON（主机定位键到 `PHYSICAL_SERVER` / `VIRTUAL_MACHINE`），
   用 `--backend oracle` 或 `--backend postgresql` 试算。不按 IP 或名称猜硬件类型。
3. 停止该仓库的 AIOps API、Worker、Scheduler、DB Executor、Main API 及其通知进程；
   保留无关服务和数据库实例运行。部署与资源模型对应的新代码。
4. 指定 `--apply --backup-dir <0700目录> --host-types <文件>` 执行。
   脚本先保存 0600 的数据快照、结构元数据、受保护对象摘要和拆分计划，再升级。
5. 旧绑定表改名为 `KBOT_BAK_RESOURCE_BINDING_57` /
   `aiops_upgrade_archive.aiops_bak_resource_binding_57`（PG 使用独立归档 Schema），
   新建规范资源绑定表并录入数据。归档表只作恢复点，不参与应用读写。
   原数据库绑定 ID、状态、版本、预算和审计字段保留；资源 ID 通过数据库扩展表关联，
   不假设它等于 Target ID。数据库 locator 移除 `host_target_key`。
6. 同域、同源、同主机定位只建一个硬件身份和 HOST 绑定，按旧数据库的系统归属创建
   基础设施层关联以及 RUNS_ON 关系。新绑定健康状态为 UNKNOWN，不伪造健康结果。
7. Oracle 从 56 升至 57，定向更新事件外键及三个相关视图；PG 在同一事务内加锁、
   升级和验证。核验新绑定内容、历史 ID、资源拓扑数量，确认系统状态、Target、监控源、
   Agent 及其授权记录未改变后，再启动服务和验收接口。

无法核验类型的历史测试节点默认阻止升级；若经评估明确暂存，可传
`--defer-unknown-hosts`。它的数据库绑定照常迁入，主机引用保存在旧表、备份和
`plan.json` 的 deferred 清单中，不自动伪造硬件资源。上线时须明确报告暂存数量。

Oracle DDL 隐式提交，不能依靠事务回滚整个升级。发生失败时保持相关服务停止，
根据备份、归档表和已执行阶段恢复或继续；不要直接重跑、删除归档或启动旧代码。
PG 失败时事务回滚；仍须核验数据库和代码版本一致后恢复服务。
备份包含业务配置，应保持目录 0700、文件 0600，不提交 Git 或输出到日志。
