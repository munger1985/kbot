# AIOps 运维知识库对齐实施计划

来源：2026-11-20《AIOps 运维知识库：新版知识底座对齐方案》。本计划在 KBot4 与 Ammolite 同步维护，算法边界以[知识解析、检索与问答基础能力设计](../architecture/knowledge-answering-capability.md)为准。

实施记录：[阶段 0 基线与合同冻结](aiops-knowledge-alignment-stage-0.md)；[阶段 1 配置与审批](aiops-knowledge-alignment-stage-1.md)；[阶段 2、3 实施与阶段 4 验收交接](aiops-knowledge-alignment-stage-2-4.md)。真实数据库、模型服务、真实资料及端到端验收只在最终阶段、获得指定环境授权后执行。本文不授权存量写入、切换或部署。

最新产品决议：[按知识库绑定模型与三档文档解析](../product/knowledge-library-parse-strategies.md)。下列阶段及关联记录保留为当时基线；其中「建库只配置标签模型」和「App 共用实际解析、表示方案」已被本决议取代。建库／编辑绑定模型、不选档；运维资料审批时选择当前库可用的档位并冻结执行快照。独立诊断案例治理不变。

## 范围与执行原则

- 保留库卡片、上传/审核、案例资格、Agent 工作台及诊断流程。资料、解析、投影和检索仍属 AIOps App；不访问知识检索 App 的数据接口，不新增独立问答、方案管理服务或模型重排，不改变诊断、处置、审批职责。
- 两仓业务语义、公共/内部合同、验收用例一致；只在可信身份作用域、Oracle/PostgreSQL 持久化和静态页面/Portal 前端处适配。HTTP 经客户端和应用层进入 UoW/Repository，应用层不直接查数据库。
- 每阶段成套更新业务代码、合同、调用方和测试。保留已有未提交修改；不为旧配置加兼容写入口、双读写、自动回填或旧代次回退。

## 阶段 0：基线与合同

1. 记录两仓工作区根、提交、远端跟踪状态和重叠文件；不切分支、拉取或清理。
2. 按配置、上传审批、检索、Runtime、Agent 绑定和删除追踪调用方；核对旧手册库模型入口、不同前端及独立案例配置。
3. 冻结三份目标合同：有效能力与索引状态；主命中、关联与覆盖；删除保护与并发。附正反例和纯离线校验。阶段 0 不改变运行 API，也不把示例通过称为实际产品验收。
4. 输出存量只读盘点清单和后续评审项；没有指定环境与授权，不连数据库或模型服务。退出条件：计划、双仓基线、调用图、合同用例齐备，待决数据项明确。

## 阶段 1：配置与审批

1. 收敛建库和编辑合同：名称、说明、可选标签识别模型；更新时区分省略（保留）、显式清空和替换。新增与改名共用名称规范化，在可信作用域内串行化同名检查。仅改元数据不查无关模型、不重算方案、不触发索引重建。
2. 从实际装配的解析、投影、检索方案和运行证据派生只读能力。原生解析、OCR/视觉补强、词法与实际语义方向分别报告未启用、待验证、可用、异常；索引状态另报，空库不告警也不宣称可检索。
3. 上传在对象写入前检查状态、文件与实际方案；登记事务内持库行锁复核作用域、启用状态、方案身份与幂等。移除旧 OCR、检索规划、向量角色门槛；缺标签能力只提示，不阻止待审资料登记。事务未登记成功时沿用原暂存回收机制，不误删共享对象。
4. 审批转入标签处理前校验有效模型、Prompt、词表；失败保留待审，不登记失败已可预见的任务；成功时冻结执行所需的模型版本、Prompt 版本、词表与精确来源。执行与重试读取冻结规格；拒绝审批、已发布查询、独立的案例脱敏治理不变。
5. 固定实际解析方案、表示空间及索引代次；变更模型版本、处理器、维度或方向先验证新代次，再走既有批准发布动作；失败不清空旧代次，不混用不兼容表示。既有配置、代次或无冻结规格的在途任务单独评审。
6. 修改应用、Repository、服务契约、Main API、客户端、OpenAPI、静态页面与 Portal 抽屉及上传提示，收敛手册库旧模型入口。模型引用检查只保留真实标签绑定、任务与受保护运行方案/代次；保留独立案例治理。

验收：无向量空库可建可改；缺标签能力可上传待审但不能开始标签处理；变更标签设置不影响已登记任务；缺 OCR 不会声称扫描正文已识别；无索引与异常分开。

## 阶段 2：检索与证据交付

1. 从当前 Agent 版本、启用库、Target、发布状态、安全级、来源及案例资格冻结有界版本集合。区分资格集合和实际可检索集合；记录预算、索引缺口和授权范围，在内容读取及组装前复核精确文档/解析运行/代次及当前授权。范围变更不回退旧版本，不露出无权查看资料。
2. 以 `primary_hits` 为排名来源，`evidence` 仅按键查取。原始检索名次与适用性/权威度/用途约束后的业务排名分开。优先完整有界快照；只有同一逻辑查询按共同通道口径全局归并并融合才称全局。独立分片保留合法证据，标记排序受限；实际漏检另标部分覆盖。
3. 主命中的文字/表格占结果名额；引用正文、图题、图像等按锚点归为关联证据，带原文、精确身份、页/段或表格定位、可读性和缺口。视觉仅在当前授权、管线及模型共同支持时交付；关联不自动成为依据。
4. 在现有预览与诊断响应保留业务结果、精确引用和业务排名，添加可机读结论、覆盖摘要、关联缺口及通道失败原因。区分有证据、资格充分检查后无资料、有效范围和通道充分覆盖后零匹配、本次未能验证。主证据可读时保留有效部分，不由 UI 用数组长度猜状态。
5. 同步预览、诊断引用 UI、工作器与 Runtime 父子执行；父执行覆盖结论随冻结证据传递，子执行成功不升级覆盖；精确读取不重做 Top-K。手册/案例不作为现场已验证事实；不暴露 Scope、Ticket 或游标。

验收：重排 `evidence` 不改原始名次，关联不占主名额；部分失败保留合法证据；未就绪不冒充零匹配；撤权/换代不泄漏旧正文；预览、诊断和 Runtime 对同一缺口一致。

## 阶段 3：生命周期与并发

1. 管理员可读写停用库的基本信息和治理配置，并查看只读能力；新上传、新检索和新 Agent 版本绑定仍要求启用。启停不改索引、资料或历史。
2. Repository 按可信作用域汇总仍存在的资料记录（含草稿、未发布、退役）、Agent 当前版本及历史版本的绑定和经核实的其他保留依赖；列表只是预警。前端保留删除入口并显示明确原因和现有相关入口，不提供自动解绑或抹掉历史。
3. 公共 `DELETE` 按 `If-Match` 获得预计版本；同一事务核权、锁库行、核验版本、重新检查依赖、删除。无前置版本、版本过期、有依赖分别处理；新上传登记和新建/绑定 Agent 版本使用同一库行锁，多库按稳定 ID 顺序。前端冲突后刷新，不自动重试。
4. Oracle 核对既有非级联外键，PostgreSQL 核对规范实体、初始化和真实约束；若确有缺口，先报告孤立记录和最小非级联约束方案，经确认才补齐。只将明确匹配的保护约束冲突转为业务冲突，其他数据库错误不能吞掉。

验收：空库可删；仅资料、仅当前引用、仅历史引用分别不能删；停用可管理但不能新使用。Oracle 和 PostgreSQL 各验证两种提交顺序下的删除 vs 上传、删除 vs Agent 绑定；无悬挂记录。

## 阶段 4：验收与发布交接

1. 双仓各在自己的环境运行定向单元、合同、前端、架构、Schema 离线和对齐检查；登记执行命令、基线失败、通过项和未覆盖项。
2. 获授权后分别验证 Oracle/PostgreSQL 约束、锁等待、并发与回滚；用获授权的多页中文手册、表格、扫描件、图文和案例验收真实解析、质量、覆盖及引用，覆盖不同 Agent、Target 和授权状态。离线通过不等于实库或质量通过。
3. 交付双仓变更清单、合同例子、实际测试结论、各环境存量处置和发布/回滚条件。处理后端、客户端、前端的协同切换；旧代码无法证明与新数据兼容时不擅自回切。存量写入、切换、构建、部署、发布按仓规和单独授权处理。
